## Баги

Находки полного ревью 2026-09-24 помечены номером (V1…) и важностью. Где
написано «воспроизведено» — проверено на настоящих документах VEX.

- **V1 [критично] `RHEL severity` берётся по всему документу, а не по
  продукту** (`vex.py`, `aggregate_severity`). У Red Hat есть severity по
  каждому продукту (`vulnerabilities[0].threats`, `category=impact`), и она
  расходится с общей. Воспроизведено: CVE-2023-44487, nginx под RHEL 9 —
  у продукта Moderate, в таблице Important (то же у grafana, git-lfs…).
  Строки `not listed` тоже получают severity, хотя Red Hat компонент не
  оценивал. Брать impact выбранного продукта, общую — только если своей нет;
  для `not listed`/`no VEX record` — `-`. Поправить README («общая severity»).
- **V2 [важно] имя пакета из purl не декодируется** (`vex.py`, разбор purl).
  `pkg:rpm/redhat/gcc-c%2B%2B` даёт имя `gcc-c%2B%2B`, поэтому любой пакет
  с `+` (`libstdc++`, `libsigc++20`, `dbus-c++`…) всегда `not listed`.
  Воспроизведено: CVE-2023-4039, `libstdc++` под RHEL 8 — `not listed`
  вместо `Not affected`. Нужен `urllib.parse.unquote`.
- **V3 [важно] из нескольких фиксов одного продукта берётся самый свежий,
  а не тот, что закрыл CVE** (`vex.py`, `_errata_for` и выбор кандидата).
  Воспроизведено: CVE-2023-44487, стрим `nginx:1.22` под RHEL 9 — в
  колонке «Advisory (RHSA)» `RHEA-2023:6562` (ребейз 9.3) вместо
  `RHSA-2023:6120`; nodejs:16 под RHEL 8 — `RHSA-2024:1444` вместо
  `RHSA-2023:5850`. Более поздний NVR фикса делает билд SL «отстающим»,
  хотя фикс в нём может уже быть. Решить правило: самый ранний
  `vendor_fix`, приоритет RHSA над RHEA/RHBA, или все через `|`; описать в
  README.
- **V4 [важно] неизвестный репозиторий в CPE считается RHEL, а
  предупреждение — одно на весь прогон** (`vex.py`, `_warn_unknown_repo`).
  Это тот же класс риска, что и баг с Fast Datapath: новая надстройка
  попадёт в кандидаты, код возврата 0, и назван будет только первый CVE.
  Варианты: по умолчанию не учитывать неизвестный репозиторий
  (`not listed (unknown repo: X)`) или помечать строку; предупреждать на
  каждую затронутую строку; давать код 1; списки репозиториев вынести в
  конфиг — README сейчас предлагает править `vex.LAYERED_REPOS` в коде
  пакета, что после `pip install` неудобно.
- **V5 [важно] файл отбраковки может совпасть со входом или таблицей и
  стереть их** (`cli.py`, `rejects_path`, `_write_rejects`). README советует
  «поправьте файл отбраковки и подайте на вход ещё раз»: вызов
  `--blocks report.rejected.txt -o report.csv` удалит исправленный вход
  (если битых блоков нет) и заменит отчёт одними исправленными строками.
  Воспроизведено. `--rejects`, указывающий на `--table`, тоже её затрёт.
  Сравнивать `realpath` отбраковки с `--blocks`, `--table`, `-o` и падать;
  поменять совет в README (дописывать исправленные блоки в основной вход).
- **V6 [важно] у клиента koji нет таймаута** (`kojiclient.py`, `connect`).
  `koji.ClientSession(hub_url)` без `opts` ждёт ответа до 12 часов
  (`DEFAULT_REQUEST_TIMEOUT`). Передавать `opts={"timeout": …}` из конфига
  (например `koji.timeout`, по умолчанию 60).
- **V8 [мелочь] остаётся временный файл выхода, `-o <каталог>` падает только
  после сети** (`cli.py`, `_run`). Проверка каталога `--rejects` идёт после
  открытия выхода и вне `try`; `os.replace` — тоже вне очистки.
  Воспроизведено оба. Проверять `--rejects` до открытия выхода, `replace`
  внести в `try`, каталог в `-o` отвергать сразу.
- **V9 [мелочь] таблица из Excel с пустой колонкой в конце не читается**
  (`table.py`). Строки с `;` в конце (21 ячейка, последняя пустая) дают
  «заголовок не как у vulnsheet». Воспроизведено. Отбрасывать пустые
  ячейки сверх 20 — данных не теряем; в сообщении называть число ячеек.
- **V12 [мелочь] Ctrl-C печатает трейсбек** (`cli.py`, `main`).
  `KeyboardInterrupt` не перехватывается. Ловить и возвращать 130.
- **V13 [мелочь] `--rejects` в режиме 2 молча игнорируется** (`cli.py`).
  Предупреждать или отвергать флаг.
- **V15 [мелочь] ключ-список в YAML даёт невнятную ошибку** (`config.py`,
  `_StrictLoader`). `? [a, b]` — «фатальная ошибка: cannot use 'list' as a
  set element» вместо `ConfigError` с путём и строкой. Воспроизведено.
- **V20 [мелочь, безопасность] ячейки CSV могут стать формулами в Excel**
  (`report.py`). Текст из тасктрекера и Red Hat пишется как есть: ячейка,
  начинающаяся с `=`, `+`, `@`, при открытии в Excel исполнится как
  формула. Оба источника доверенные, риск низкий.

## Фичи

- **V14 компонент не проверяется** (`tasks.py`). `CVE-… vim (vim-enhanced)`
  даёт компонент `vim (vim-enhanced)` — `NOT_FOUND` и `not listed` с кодом 0.
  Отбраковывать блок, если компонент не похож на имя RPM
  (`^[A-Za-z0-9._+-]+$`).
- **V18 кэш VEX** (`vex.py`). Кэш не чистится (документы бывают десятки МБ:
  CVE-2023-44487 — 33 МБ); ответ 404 не кэшируется; при сетевой ошибке не
  используется даже устаревший документ из кэша (с предупреждением) — в
  режиме 1 это `fetch error` вместо данных.

## Технический долг

- У логгера `koji` (заводит его сам модуль `koji`, который `kojiclient.py`
  импортирует изнутри `connect()`) нет собственного хендлера. У vulnsheet
  настроен только логгер `vulnsheet` (см. `logs.py`), поэтому предупреждения
  и ошибки из самой библиотеки koji идут не через него, а через
  `logging.lastResort` — неотформатированной строкой прямо в stderr, без
  общего вида остального журнала vulnsheet. Стоит либо подключить к
  логгеру `koji` тот же хендлер, что ставит `logs.configure`, либо, если
  такие сообщения не нужны, повесить на него `logging.NullHandler()`.

- **V7 [важно] фейки в тестах не похожи на настоящий CSAF**
  (`tests/fakes.py`, `csaf()`). Нет purl, `threats`, `cvss_v4`, нескольких
  `vendor_fix` на компонент, реальных product id вида `…MAIN.EUS` — поэтому
  V1–V3 и прошли незамеченными: основной путь «имя из purl» тестами не
  покрыт. Добавить это в `csaf()` и маленькую обрезанную фикстуру из
  настоящих документов (nginx из CVE-2023-44487, libreswan из
  CVE-2026-12413), тесты на случаи V1–V3.
- **V16 README местами устарел.** Раздел «Выход» говорит, что Разработчик и
  Комментарий «всегда `-`» и строка «на каждый блок, с повторами» — это
  верно только для режима 1; обещание удалить временник нарушено (V8);
  `RHEL severity` описана как общая (V1); у кода 2 не упомянуты
  непредвиденные ошибки; stdout пишется в кодировке локали, а README обещает
  UTF-8.
- **V17 шум в debug** (`vex.py`, строка «надстройка, не RHEL»): пишется на
  каждый product id — в примере с libreswan 20 одинаковых строк. Писать раз
  на платформу.
- **V19 память и скорость** (`vex.py`, `fetch_all`; `cli.py`). Все индексы с
  полным `vuln` живут до конца прогона: один CVE-2023-44487 — около 140 МБ
  памяти. koji и VEX идут последовательно. Можно считать lookup в воркере и
  отпускать документ; koji запускать параллельно с VEX.

## Идеи

- **V10 `Missing` стирает прежний `Task state`** (`merge.py`). Последнее
  известное состояние (Закрыт / Отменен / В работе) теряется; при неполной
  выгрузке из тасктрекера это касается сразу многих строк, а код возврата 0
  и в журнале только счётчик. Писать `Missing (<прежнее>)` или
  предупреждать, когда доля Missing велика.
- **V11 `--rhel 9.4` не видит фиксы в продуктах `*.MAIN.EUS`.** CVE-2024-6387,
  openssh, `--rhel 9.4` — `not listed (present for 9, 9.0, 9.2)`, хотя фикс
  el9_4 (RHSA-2024:4312) лежит в `BaseOS-9.4.0.Z.MAIN.EUS` с CPE
  `enterprise_linux:9`. По правилу «без откатов» это верно, но по product id
  продукт относится и к потоку 9.4 EUS. Считать `X.Y.0.Z.MAIN.EUS` также
  потоком `X.Y` или хотя бы называть его в подсказке.
- Строка таблицы с Task ID `-` или пустым при валидном CVE в режиме 3 всегда
  получает Missing и никогда не совпадёт с блоком (совпавший блок добавится
  отдельной новой строкой). Возможно, такие строки стоит считать строками,
  по которым нечего спрашивать — решить пользователю.
