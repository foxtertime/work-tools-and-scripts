# vulnsheet

Собирает рабочую таблицу по задачам на устранение уязвимостей. На вход —
блоки задач, скопированные из тасктрекера; для каждой пары «CVE — компонент»
тулза берёт у Red Hat (CSAF/VEX) статус в нужной версии RHEL, severity, CVSS
и данные фикса, а у koji — последний билд компонента в теге, и пишет CSV из
27 колонок в том виде, в каком таблицу ведёт процесс. Если задан GitLab,
тулза ещё и ищет патч под CVE строки в каталоге `PATCH` коммита, из
которого собран этот билд, и ставит `+` в колонку `P` (см. «Проверка
патчей в GitLab»). Если заданы диапазоны, тулза сверяет апстрим-версию
билда с уязвимыми диапазонами CVE из NVD и CVE.org и ставит `+` в колонку
`D`, если версия вне них (см. «Апстрим-диапазоны версий»). Если подан JSON
с AI-вердиктами (`--ai`), тулза раскладывает его результаты по колонкам
`ai_*` строк с той же парой CVE + компонент (см. «Файл AI»). `Комментарий`
тулза не трогает.

Заменяет три отдельных скрипта: разбор блоков, запрос к VEX и запрос к koji.

Умеет и обновлять уже ведущуюся таблицу, не трогая колонок, которые
заполняют люди: освежить в ней данные koji и VEX или сверить её с новой
выгрузкой блоков (см. «Режимы»).

**Версия:** 4.0.0 (номер — в `vulnsheet/__init__.py`, выводится по
`--version`; история — [CHANGELOG.md](CHANGELOG.md)).

## Требования

- Python 3.9+
- `koji` — клиент koji-хаба, ставится системным пакетом (`python3-koji`) или
  `pip install koji`. Импортируется только при обращении к хабу.
- `PyYAML` — только если задан конфиг (`--config` или `VULNSHEET_CONFIG`):
  системный пакет `python3-pyyaml` или `pip install pyyaml`. Без конфига не
  нужен.
- Сеть до koji-хаба (только чтение: `getTag`, `getLatestBuilds`, а при
  проверке патчей ещё и `getBuild`) и до `https://security.access.redhat.com`.
- Только для проверки патчей: сеть до GitLab (REST v4, только чтение) и
  токен с правом `read_api` в `GITLAB_TOKEN`. Имя переменной задаётся
  `gitlab.token_env`. Без токена видны только публичные проекты.
- Только для диапазонов версий: сеть до `https://services.nvd.nist.gov` и
  `https://cveawg.mitre.org`. Ключ NVD API (бесплатный, выдаёт nvd.nist.gov)
  необязателен, лежит в `NVD_API_KEY` (имя задаётся `ranges.nvd_key_env`);
  без него NVD спрашивается в десять раз медленнее (это лимит самого NVD).

Из переменных окружения читаются `VULNSHEET_CONFIG` — путь к конфигу, если
не задан `--config`, — токен GitLab, если в конфиге есть секция `gitlab`, и
ключ NVD, если есть секция `ranges`. Кэш VEX по умолчанию лежит в
`$XDG_CACHE_HOME/vulnsheet` (иначе `~/.cache/vulnsheet`) и живёт час; и то и
другое меняется в конфиге.

## Установка

Из каталога тулзы, без установки:

```bash
python3 -m vulnsheet --version
```

Или пакетом, тогда появляется команда `vulnsheet`:

```bash
pip install --no-build-isolation -e .
```

`--no-build-isolation` — чтобы pip не ходил в сеть за свежим `setuptools`.
Метаданные лежат в `setup.cfg`: `setuptools` в RHEL 9 (53-й) не понимает
`[project]` в `pyproject.toml`.

## Запуск

```bash
python3 -m vulnsheet --rhel 9 --koji-url https://koji.example.com/kojihub \
    --tag sl9-updates --blocks tasks.txt -o report.csv
```

| Аргумент | Смысл |
|---|---|
| `--blocks` | файл с блоками; `-` — stdin |
| `--table` | прежняя таблица vulnsheet, только файл (см. «Режимы»). Нужен `--blocks`, `--table` или оба |
| `--ai` | JSON с AI-вердиктами, только файл (см. «Файл AI»); без него колонки `ai_*` новых строк — `-`, прежних — как есть |
| `--config` | YAML-конфиг (см. «Конфиг»); без него — из `VULNSHEET_CONFIG`, иначе без конфига |
| `--rhel` | версия RHEL: `9` — только 9, `9.2` — только 9.2; `RHEL 9`, `el9` тоже годятся. Обязательна — флагом или `rhel` в конфиге |
| `--koji-url` | URL kojihub. Обязателен — флагом или `koji.hub` в конфиге |
| `--tag` | koji-тег. Обязателен — флагом или `koji.tag` в конфиге |
| `-o`, `--output` | CSV; без него — stdout |
| `--rejects` | файл для битых блоков (см. ниже) |
| `--log-level` | `error` / `warning` / `info` / `debug`, по умолчанию `info` |
| `--version` | версия тулзы |

Из буфера обмена:

```bash
xclip -o | python3 -m vulnsheet --rhel 9 --koji-url https://koji.example.com/kojihub \
    --tag sl9-updates --blocks - -o report.csv
```

С конфигом, где заданы хаб, тег и версия, хватает входа и выхода:

```bash
python3 -m vulnsheet --config vulnsheet.yaml --blocks tasks.txt -o report.csv
```

## Режимы

Режим задаётся тем, что подано на вход:

| Вход | Режим | Что делает |
|---|---|---|
| `--blocks` | новая таблица | строит таблицу с нуля |
| `--table` | обновление koji и VEX | в прежней таблице обновляет только данные koji и VEX и колонки `P` и `D` |
| `--table` и `--blocks` | синхронизация с блоками | обновляет данные задач из блоков, koji и VEX; пропавшие задачи помечает, новые дописывает |

```bash
# освежить koji и VEX в той же таблице
python3 -m vulnsheet --config vulnsheet.yaml --table report.csv -o report.csv

# сверить таблицу с новой выгрузкой задач
python3 -m vulnsheet --config vulnsheet.yaml --table report.csv --blocks tasks.txt -o report.csv
```

`-o` может совпадать с `--table`: таблица читается целиком до работы, а
выход заменяется атомарно, поэтому при сбое прогона прежняя таблица
остаётся цела. Права существующего файла сохраняются, а если `-o` —
символическая ссылка, обновляется её цель, сама ссылка остаётся ссылкой.

Что происходит с колонками:

| Колонки | Новая таблица | Обновление koji и VEX | Синхронизация: строка совпала | Синхронизация: `Missing` | Синхронизация: новая строка |
|---|---|---|---|---|---|
| Разработчик … Принятая мера | `-` | как есть | как есть | как есть | `-` |
| Task ID … Компонент | из блока | как есть | из блока | как есть, `Task state` → `Missing` | из блока |
| `P`, `D` | GitLab, диапазоны | GitLab, диапазоны | GitLab, диапазоны | GitLab, диапазоны | GitLab, диапазоны |
| `SL NVR` | koji | koji | koji | koji | koji |
| RHEL NVR … Advisory | VEX | VEX | VEX | VEX | VEX |
| `CVE link` | по CVE | по CVE | по CVE | по CVE | по CVE |
| `ai_nvr` … `ai_run` | файл AI | файл AI | файл AI | файл AI | файл AI |
| `Комментарий` | `-` | как есть | как есть | как есть | `-` |

- **Синхронизация** сопоставляет строку и блок по тройке (Task ID, CVE ID,
  Компонент). Пробелы по краям и регистр CVE при этом не важны.
  - Строка, чьей тройки нет в блоках, не удаляется: в `Task state` ставится
    `Missing`.
  - Тройка, которой нет в таблице, становится новой строкой в конце, в
    порядке блоков.
  - Порядок прежних строк не меняется.
  - Если тройка повторяется в блоках, действует первый блок.
  - Строка с битым блоком тоже получает `Missing`: битый блок виден в
    файле отбраковки и по коду 1.
  - Если в блоках нет ни одного годного (все битые), синхронизация
    отказывается работать — код 2: иначе все строки таблицы молча стали бы
    `Missing`.
- **Сбой сети.** Если koji вернул `ERROR` или VEX — `fetch error`, у прежней
  строки остаются прежние значения этой группы колонок, а в журнале
  появляется предупреждение. `NOT_FOUND` и `not listed` — это ответы, они
  перезаписывают прежние значения. Так же с `P` и `D`: если патчи или
  диапазон проверить не удалось, у прежней строки остаётся прежнее
  значение, у новой — `-`.
- **`P` и `D` без секции в конфиге** не проверяются: у прежней строки
  остаются прежними, у новой — `-`. Прежнее значение, которое не `+` и не
  `-` (например, пустая ячейка), становится `-`.
- **`P` и `D` ведёт тулза:** что в них поставлено руками, следующий прогон
  обновления перезапишет.
- **`ai_*` без файла AI или без результата по паре строки** у прежней
  строки остаются прежними, у новой — `-`. Результат по паре перезаписывает
  все пять колонок, и правку руками тоже.
- **Строка, по которой нечего спрашивать** (в `CVE ID` не CVE-ID или нет
  компонента), остаётся целиком как есть и не получает `Missing`.
- **Таблица на входе** — ровно то, что пишет vulnsheet: UTF-8 (BOM
  допускается), `;`, кавычки по правилам CSV, тот же заголовок, 27 ячеек в
  каждой строке. Иначе это фатальная ошибка с номером записи: строку с
  ручными данными выбросить нельзя.
- **Таблица vulnsheet 2.x** (22 колонки, без `ai_*`) читается как есть:
  колонки `ai_*` вставляются перед `Комментарий` со значением `-`, а с `--ai`
  заполняются тем же прогоном. Переводить её руками не нужно.
- **Таблица vulnsheet 1.x** (20 колонок, без `P` и `D`) не читается — код 2
  с подсказкой. Чтобы перевести её, вставьте перед `SL NVR (latest build)`
  колонки `P` и `D` со значением `-` и прогоните обновление: тулза
  проставит их сама. Пометки 1.x в `Комментарий` (`патч найден: …`, `спек,
  …`, `версия … в уязвимом диапазоне …`) она не убирает — их чистят руками.

  Вставлять колонки надёжнее не в редакторе таблиц (он может перекавычить
  многострочные комментарии или превратить `01.09.2026` в дату), а так:

  ```bash
  python3 - old.csv new.csv <<'PY'
  import csv, sys
  with open(sys.argv[1], encoding="utf-8-sig", newline="") as f:
      rows = list(csv.reader(f, delimiter=";"))
  for i, row in enumerate(rows):
      if any(cell.strip() for cell in row):
          row[11:11] = ["P", "D"] if i == 0 else ["-", "-"]
  with open(sys.argv[2], "w", encoding="utf-8", newline="") as f:
      csv.writer(f, delimiter=";", lineterminator="\n").writerows(rows)
  PY
  ```

## Конфиг

YAML; все поля необязательные. Образец со всеми полями и комментариями —
[vulnsheet.example.yaml](vulnsheet.example.yaml). Подключается `--config
PATH` или переменной `VULNSHEET_CONFIG` (флаг главнее). Значение берётся так:
флаг командной строки, иначе конфиг, иначе встроенное.

| Поле | Смысл | Встроенное | Допустимо |
|---|---|---|---|
| `koji.hub`, `koji.tag`, `rhel` | то же, что `--koji-url`, `--tag`, `--rhel` | — | непустые строки; `rhel` — строка или целое, версия с точкой — только в кавычках |
| `vex.cache_dir` | каталог кэша VEX, `~` раскрывается | `$XDG_CACHE_HOME/vulnsheet` или `~/.cache/vulnsheet` | непустая строка |
| `vex.cache_ttl` | сколько секунд документ живёт в кэше; `0` — кэш не читать | `3600` | целое ≥ 0 |
| `vex.jobs` | параллельных загрузок | `8` | целое ≥ 1 |
| `vex.retries` | попыток на документ | `3` | целое ≥ 1 |
| `vex.timeout` | секунд на запрос | `30` | число > 0 |
| `vex_streams` | стримы VEX по версиям RHEL, см. ниже | — | версия → {пакет: стрим}, непустые строки |
| `vex_names` | другие имена пакета в VEX, см. ниже | — | пакет → имя или список имён, непустые строки |
| `gitlab.hosts` | серверы GitLab: хост из `original_url` → `api` (адрес REST v4). Ключ `web` допускается и не используется — чтобы блок хостов можно было взять из конфига `dashboard` как есть. Секция `gitlab` включает проверку патчей | — | хотя бы один хост, `api` — непустая строка |
| `gitlab.default_host` | у какого сервера спрашивать хост, которого нет в `hosts` | — | ключ из `gitlab.hosts` |
| `gitlab.token_env` | переменная окружения с токеном | `GITLAB_TOKEN` | непустая строка |
| `gitlab.patch_dir` | каталог патчей в репозитории | `PATCH` | непустая строка |
| `gitlab.jobs` | параллельных запросов | `8` | целое ≥ 1 |
| `gitlab.retries` | попыток на запрос | `3` | целое ≥ 1 |
| `gitlab.timeout` | секунд на запрос | `30` | число > 0 |
| `ranges` | секция есть (хотя бы `ranges: {}`) — апстрим-диапазоны сверяются, см. ниже | — | словарь |
| `ranges.names` | имена продукта в NVD и CVE.org сверх имени пакета | — | пакет → имя или список имён, непустые строки |
| `ranges.nvd_key_env` | переменная окружения с ключом NVD | `NVD_API_KEY` | непустая строка |
| `ranges.cache_ttl` | сколько секунд ответы NVD и CVE.org живут в кэше; `0` — не читать | `86400` | целое ≥ 0 |
| `ranges.jobs` | параллельных запросов к каждому источнику; старты запросов к NVD ещё и разнесены под его лимит | `8` | целое ≥ 1 |
| `ranges.retries` | попыток на запрос | `3` | целое ≥ 1 |
| `ranges.timeout` | секунд на запрос | `30` | число > 0 |

Версию RHEL пишите строкой в кавычках (`"9.2"`): YAML прочитал бы `9.10` как
число `9.1`, поэтому число с точкой — ошибка конфига.

Конфиг проверяется целиком до работы: неизвестный ключ (опечатка вроде
`vex.cache_tll`), ключ, записанный дважды в одном словаре, неверный тип или
значение вне границ — фатальная ошибка с путём файла и полным именем ключа.

### Стримы VEX

Некоторые пакеты собираются из модульного стрима Red Hat: наш `nginx` — это
`nginx:1.26` у Red Hat. Для таких пакетов в `vex_streams` задаётся стрим:

```yaml
vex_streams:
  "9":
    nginx: nginx:1.26
    npm: nodejs:20      # пакет внутри чужого модуля
```

- Стрим можно писать целиком (`nginx:1.26`) или короткой формой — только
  частью после двоеточия (`"1.26"`): Red Hat сравнивает по этому суффиксу
  варианта пакета. Оба варианта — строки в кавычках: без кавычек `1.26` YAML
  прочитает как число, и конфиг будет отклонён с подсказкой про кавычки.
- Маппинг влияет только на VEX: koji по-прежнему спрашивается про пакет из
  входа (`nginx`), и в колонке `Компонент` — тоже он.
- Набор берётся только для версии, ровно равной `--rhel`: для `9.2` набор
  `"9"` не применяется, и наоборот. Общий набор переиспользуют якорем YAML;
  ключ, пришедший из якоря, можно переопределить:

  ```yaml
  vex_streams:
    "9": &base
      nginx: nginx:1.26
    "9.2":
      <<: *base           # nginx: nginx:1.26
      npm: nodejs:20
  ```
- Пакет без записи в маппинге — только обычный пакет: его стримы у Red Hat
  не учитываются никогда, даже если обычного пакета нет.
- Какие подмены сработали, пишется в журнал строкой вида
  `стримы VEX для RHEL 9: nginx → nginx:1.26 (3)`.

### Имена пакетов в VEX

Во входе и в koji пакет называется по исходнику (`rust-afterburn`), а Red
Hat для неисправленных продуктов пишет в VEX бинарные пакеты (`afterburn`,
`afterburn-dracut`). На портале при этом видно `rust-afterburn`, а тулза без
подсказки получит `not listed`. Такие имена задаются в `vex_names`:

```yaml
vex_names:
  rust-afterburn: [afterburn, afterburn-dracut]
  rust-coreos-installer: coreos-installer   # одно имя можно без списка
```

- VEX ищется и по самому пакету, и по всем его именам отсюда; если нашлось
  несколько вердиктов, побеждает самый опасный. У исправленных продуктов
  Red Hat обычно пишет исходник, у неисправленных — бинарники.
- Действует для всех версий RHEL и вместе с `vex_streams`.
- koji по-прежнему спрашивается про пакет из входа, в колонке `Компонент` —
  тоже он.
- Сработавшие имена пишутся в журнал строкой вида
  `имена VEX: rust-afterburn → afterburn, afterburn-dracut (2)`.

Это не `vex_streams`: стрим выбирает модульный вариант того же пакета
(`nginx::nginx:1.26`), а имя здесь — другой пакет в записи VEX.

### Проверка патчей в GitLab

Включается секцией `gitlab`; без неё GitLab не спрашивается и колонка `P`
не проверяется.

```yaml
gitlab:
  default_host: gitlab.example.com
  hosts:
    gitlab.example.com:
      api: https://gitlab.example.com/api/v4
```

```bash
export GITLAB_TOKEN=glpat-...
python3 -m vulnsheet --config vulnsheet.yaml --table report.csv -o report.csv
```

Для каждого компонента, у которого в koji найден билд:

1. У koji берётся `getBuild` этого билда. Из `extra.source.original_url`
   берутся сервер, проект и ветка.
2. Коммит сборки — хеш из `original_url`, а если там ветка, то хеш из
   верхнего поля `source` билда, но только если проект в нём тот же.
3. В коммите сборки рекурсивно читается каталог `PATCH`, и CVE ищутся в
   путях файлов.

В колонке `P` строки — `+`, если CVE строки нашлась в `PATCH` её билда, и
`-`, если нет. Ветка, с которой билд собран, не спрашивается: `P` говорит о
билде из `SL NVR`, а не о том, что лежит в ветке сейчас. Спек не читается:
упоминания CVE в нём на практике совпадают с `RHEL state`.

- Хеша коммита нет или коммита в репозитории уже нет (ветку переписали):
  читается `PATCH` на вершине ветки. Во втором случае в журнал пишется
  предупреждение.
- Под одну CVE может быть несколько файлов, и один файл может закрывать
  несколько CVE (см. ниже) — `+` получает каждая из них.

Как в имени файла узнаются CVE (регистр не важен):

| Имя файла | CVE |
|---|---|
| `nginx-1.26-cve-2026-12345.patch.new` | `CVE-2026-12345` |
| `nginx-1.26-cve-2026-12345-67890.patch.new` | `CVE-2026-12345`, `CVE-2026-67890` |
| `cve-2026-12345-67890-11111.patch` | три CVE 2026 года |
| `cve-2025-1111-cve-2026-2222.patch` | `CVE-2025-1111`, `CVE-2026-2222` |
| `nginx-cve-2026-12345-1.patch` | `CVE-2026-12345`: `-1` слишком короткое для номера |
| `cve-2026-12345-20260115.patch` | `CVE-2026-12345`: восемь цифр — скорее дата |
| `PATCH/CVE-2024-1234/fix.patch` | `CVE-2024-1234`: имя каталога тоже считается |

После первого номера каждая группа `-NNNN` из 4–7 цифр — ещё одна CVE того
же года. CVE другого года пишите со своим `cve-`: в
`cve-2025-1111-2026-2222` «2026» прочитается как номер. `CVE-2024-12345` с
`CVE-2024-1234` не совпадает.

На билд GitLab спрашивается о дереве `PATCH` коммита сборки, а если коммита
уже нет — ещё и ветки. Длинное дерево приходит постранично, по запросу на
каждые 100 файлов. На `404` уходит ещё один запрос, к `commits/<ref>`: он
отличает «каталога нет» от «нет коммита или ветки». Ответы внутри прогона
кэшируются.

Не проверяются, и это не ошибка: компонент `NOT_FOUND` в koji (`P` — `-`),
`ERROR` в koji (`P` как у `SL NVR`: у прежней строки прежнее, у новой —
`-`), билд без `original_url` и сборка из готового SRPM (`P` — `-`).
Ошибка — код 1, у прежней строки остаётся прежнее `P`, у новой — `-`,
причина с именем компонента пишется в журнал. Так бывает, если koji не дал
деталей билда, `original_url` не разобрался, GitLab не ответил или отказал,
нет проекта, ветки или коммита, или хост неизвестен.

### Апстрим-диапазоны версий

Включается секцией `ranges` (хотя бы `ranges: {}`); без неё ни NVD, ни
CVE.org не спрашиваются.

```yaml
ranges:
  names:
    nginx: nginx_open_source
    httpd: http_server
```

Для каждой строки апстрим-версия билда — `Version` из `SL NVR` без эпохи и
релиза (`nginx-1.26.3-2.sl9` → `1.26.3`) — сверяется с уязвимыми диапазонами
CVE для этого продукта. В колонке `D` строки — `+`, если версия вне всех
уязвимых диапазонов, и `-`, если она в одном из них или диапазон неизвестен.

| Версия билда | Диапазоны CVE | `D` |
|---|---|---|
| `1.26.2` | `>=1.11.4 <1.26.3` (NVD) | `-` |
| `1.26.3` | `>=1.11.4 <1.26.3`, `>=1.27.0 <1.27.4` (NVD) | `+` |
| `1.26.3` | `>=1.11.4`, верхняя граница не указана (CVE.org) | `-` |
| любая | нет ни в NVD, ни в CVE.org | `-` |

«В уязвимом диапазоне» — не «уязвим»: RHEL и SL держат старую апстрим-версию
и бэкпортят в неё фиксы. Читайте `D` вместе с `P` и `RHEL state`. Сколько
строк в диапазоне, вне его и с неизвестным диапазоном, видно в итоге
прогона.

Откуда диапазоны:

1. **NVD** — CPE-конфигурации, отмеченные уязвимыми, у которых продукт
   (`vendor:product`) — одно из имён пакета. Диапазоны объединяются, точная
   версия — диапазон из одной точки.
2. **CVE.org** — если у NVD для продукта ничего нет (свежие CVE NVD
   разбирает с опозданием, часть откладывает). Сначала данные CNA, затем
   ADP. Берутся `version` с `lessThan`/`lessThanOrEqual` и текст в `version`
   вида `< 9.0.2106` или `>= 2.43.0, < 2.43.4`; `lessThan: *` — верхней
   границы нет. Версии сборок дистрибутивов (`versionType: rpm`) и
   `unaffected` пропускаются, пустые диапазоны вроде `8.4.0 < 8.4.0` — тоже.
3. Нигде нет — диапазон неизвестен, `D` — `-`.

Имена: по умолчанию продукт ищется по имени пакета; `ranges.names`
добавляет другие. Регистр и `_` вместо пробела не важны, вендор не
учитывается. В NVD, например, nginx бывает и `nginx`, и `nginx_open_source`,
httpd — `http_server`, python3 — `python`, expat — `libexpat`, curl — ещё и
`libcurl`.

Версии сравниваются, как в `rpm` (`rpmvercmp`): `1.9.15 < 1.11.4`,
`1.1.1za > 1.1.1x`, `9.7p1 < 9.8`.

- Пакета в koji нет (`NOT_FOUND`) — сверять нечего, `D` — `-`. koji не
  ответил (`ERROR`) — `D` как у `SL NVR`: у прежней строки прежнее, у новой
  — `-`.
- Один источник не ответил — используется другой. Оба не ответили, или не
  ответивший мог знать то, чего не знает другой, — диапазон не сверен:
  у прежней строки остаётся прежнее `D`, у новой — `-`, предупреждение,
  код 1. «Неизвестен» было бы неправдой.

NVD пускает 5 запросов в 30 секунд без ключа и 50 с ключом. Запросы к нему
идут параллельно (`ranges.jobs`), но их старты разнесены под лимит: не чаще
раза в 6 с без ключа и раза в 0,6 с с ключом. Медленный ответ NVD при этом
не тормозит остальные. 100 новых CVE — около 10 минут без ключа и около
минуты с ключом. CVE.org — параллельно, без ограничений. Ответы обоих
кэшируются на сутки в подкаталоге `ranges` кэша VEX, так что повторный
прогон в сеть почти не ходит.

На запрос с неверным ключом NVD отвечает 404 (для существующих и
несуществующих CVE — 200). Поэтому 404 с ключом — ошибка «ключ отклонён»:
предупреждение одной строкой, NVD до конца прогона больше не спрашивается,
диапазоны берутся из CVE.org, а где их там нет — код 1.

В журнале — строка в начале фазы NVD со сроком
(`диапазоны: CVE.org — CVE 859 за 41 с; NVD — CVE 859, из кэша 0, в сеть 859,
~8 мин 35 с с ключом`), прогресс не реже раза в 30 секунд
(`диапазоны: NVD 240/859, ~6 мин осталось`) и итог фазы
(`диапазоны: NVD 859/859 за 8 мин 50 с`).

## Вход

Блоки по шесть строк, между блоками — пустая строка. Других разделителей
нет. Пробелы по краям строк, `\r\n` и BOM в начале файла допускаются.
Кодировка — UTF-8.

```text
Состоит из
TASKID-181229
CVE-2026-73070 vim
Отменен
22.09.2026
КМ
```

Строки: тип связи (не используется), Task ID, `CVE-ID компонент`, статус
задачи, дата задачи, исполнитель.

### Файл AI

Необязательный вход `--ai`: JSON с AI-вердиктами по парам CVE + пакет, в
UTF-8 (BOM допускается). Его пишет плагин `rhel-security` (`results.json`
в корне его результатов); формат — в контракте плагина
`contracts/cve-pipeline.md`, раздел «results.json».

```json
{
  "format": 2,
  "plugin": "4.1.0",
  "run": "2026-10-27T14:30",
  "completed": [
    {
      "cve": "CVE-2026-6368",
      "package": "glibc",
      "nvr": "glibc-2.34-270.el9_8",
      "verdict": "affected",
      "confidence": "high",
      "remediation": "vendor update available",
      "run": "2026-10-21T12:04"
    }
  ],
  "problems": [
    {
      "cve": "CVE-2026-60021",
      "package": "libpq",
      "nvr": "libpq-13.23-1.el9_7",
      "verdict": "not processed",
      "confidence": null,
      "remediation": null,
      "reason": "prep failed",
      "run": "2026-10-21T12:04"
    }
  ],
  "sources_not_found": [
    {
      "package": "gzip",
      "nvr": "gzip-1.12-1.el9.2",
      "cves": ["CVE-2026-60030", "CVE-2026-60031"],
      "nearest_builds": ["gzip-1.12-1.el9", "gzip-1.12-2.el9_8"],
      "run": "2026-10-21T12:04"
    }
  ]
}
```

- `format` — обязательно `2`; `completed`, `problems` и
  `sources_not_found` — обязательно списки. Иначе, как и если файл не
  читается или не JSON, — код 2 до запросов в сеть. Файл прежнего формата 1
  (один список `results`) не читается: плагин перепишет его в формат 2 при
  следующей финализации.
- `plugin` и `run` верхнего уровня (время файла; если его нет —
  `generated`) только выводятся в шапку журнала вместе с числом записей в
  каждом разделе.
- Записи `completed` (разобранные пары) и `problems` (необработанные, с
  `verdict: "not processed"`) — результаты по паре CVE + пакет. Запись
  `sources_not_found` — пакет, исходники которого не нашлись: на каждую
  CVE из её `cves` она даёт результат с `verdict: "not processed"`, `nvr`
  и `run` записи; `confidence` и `remediation` у него `-`. Причины
  (`reason` у `problems`, `nearest_builds` у `sources_not_found`) в таблицу
  не попадают — их можно посмотреть в самом файле.
- Результат ложится на все строки таблицы, у которых `CVE ID` и
  `Компонент` совпадают с его `cve` и `package`. Сравнение — как при
  синхронизации: пробелы по краям и регистр CVE не важны, компонент
  сравнивается точно. Task ID не участвует: одна пара в нескольких задачах
  получает один и тот же результат.
- Поля `nvr`, `verdict`, `confidence`, `remediation`, `run` пишутся в
  `ai_nvr`, `ai_verdict`, `ai_confidence`, `ai_remediation`, `ai_run` как
  есть, без пробелов по краям. Только `run` переводится в дату
  `dd.mm.yyyy`, как остальные даты таблицы: `2026-10-21T12:04` →
  `21.10.2026`, время отбрасывается; не дата ISO — как есть. Нет поля,
  `null`, пустая строка или `—` (так плагин пишет «нет значения») — `-`.
  Число, `true`/`false`, список или объект пишутся так, как они записаны в
  JSON (`0.9`, `true`, `["a", "b"]`). Другие поля результата не
  используются.
- Результат без `cve`, с `cve` не в виде CVE-ID или без `package`
  пропускается, как и запись `sources_not_found` без списка `cves`:
  предупреждение с разделом и номером записи в нём и код 1.
- Если пара повторяется (в том числе в разных разделах — например, у
  разных NVR одного пакета), действует самый свежий результат по `run`;
  время с поясом (`+03:00`, `Z`) сравнивается в UTC, без пояса — как
  записано. Результат с разобранным `run` свежее результата без него; при
  равном или неразобранном `run` действует первый в порядке `completed`,
  `problems`, `sources_not_found`. О повторах — предупреждение.
- Результат, пары которого нет в таблице, ни на что не влияет: их число
  есть в итоге.

## Выход

CSV в UTF-8 без BOM, разделитель `;`, первая строка — заголовок. Одна строка
на каждый годный блок, в порядке входа, с повторами. Пустая ячейка — `-`.

Файл выхода заменяется атомарно: тулза пишет во временник рядом с ним и
подменяет им прежний файл, только когда таблица дописана до конца. Если
прогон падает (недоступен хаб, неизвестный тег, сеть и т. п.), временник
удаляется, а прежний отчёт по тому же пути остаётся нетронутым. На вывод в
stdout это не влияет.

| Колонка | Откуда |
|---|---|
| `Разработчик`, `Статус`, `Start date`, `End date`, `Принятая мера` | всегда `-` — их заполняют люди |
| `Task ID`, `CVE ID`, `Task state`, `Task date`, `Исполнитель`, `Компонент` | из блока |
| `P` | `+` — патч под CVE лежит в каталоге `PATCH` коммита, из которого собран билд `SL NVR`; `-` — нет, или проверить не удалось, или нет секции `gitlab` (см. «Проверка патчей в GitLab») |
| `D` | `+` — апстрим-версия билда `SL NVR` вне уязвимых диапазонов CVE; `-` — в диапазоне, диапазон неизвестен, сверить не удалось или нет секции `ranges` (см. «Апстрим-диапазоны версий») |
| `SL NVR (latest build)` | последний билд компонента в теге; `NOT_FOUND` — пакета в теге нет, `ERROR` — koji не ответил по пакету |
| `RHEL NVR (if fixed)` | билд RHEL с фиксом; только при `Fixed`, несколько — через `\|` |
| `Fix date` | дата errata, `dd.mm.yyyy`; только при `Fixed` |
| `RHEL state` | `Fixed`, `Affected`, `Will not fix`, `Fix deferred`, `Out of support scope`, `Under investigation`, `Not affected`; см. маркеры ниже |
| `RHEL severity` | общая severity CVE по Red Hat |
| `RHEL CVSS` | базовая оценка CVSS (v4, иначе v3) |
| `Advisory (RHSA)` | ссылка на errata; только при `Fixed` |
| `CVE link` | `https://access.redhat.com/security/cve/<CVE ID>` |
| `ai_nvr`, `ai_verdict`, `ai_confidence`, `ai_remediation`, `ai_run` | поля `nvr`, `verdict`, `confidence`, `remediation`, `run` (датой `dd.mm.yyyy`) результата из файла AI с той же парой CVE + компонент; без файла или без результата — `-` (см. «Файл AI») |
| `Комментарий` | всегда `-` — его заполняют люди |

Маркеры в `RHEL state`:

- `not listed` — у Red Hat есть запись по CVE, но компонента под этой версией
  RHEL в ней нет. Это не «Not affected»: Red Hat перечисляет только то, что
  оценил.
  Если на портале компонент есть, а здесь `not listed`, скорее всего, в VEX
  он записан под именем бинарного пакета — см. «Имена пакетов в VEX».
- `not listed (present for 9.2, 9.4)` — компонент оценён только в соседних
  минорных потоках.
- `not listed (streams: nginx:1.24, nginx:1.26)` — под этой версией у Red Hat
  есть другие варианты пакета: стримы или, если спрашивали стрим, обычный
  пакет (`(no stream)`). Обычно значит, что нужен или устарел маппинг в
  `vex_streams`.
- `no VEX record` — у Red Hat записи по CVE нет.
- `fetch error` — документ VEX не получен (подробности — в журнале).

Как выбирается вердикт: версия RHEL сравнивается точно (`9` — только 9, не
9.2); имя компонента сравнивается точно (`vim` не совпадает с
`vim-enhanced`); без маппинга берётся только обычный пакет, с маппингом —
только заданный стрим; если под одной версией RHEL вердиктов несколько
(BaseOS и AppStream расходятся), побеждает самый опасный; эпоха в NVR
срезается, чтобы он сравнивался с `rpm -q`. Подсказки в скобках у
`not listed` только объясняют, почему ничего не нашлось, — данных из других
потоков и стримов в строку они не подставляют.

RHEL — это продукты с CPE семейства RHEL и репозиторием RHEL (часть CPE после
`::`: `baseos`, `appstream`, `crb` и т. п.). Надстройки под тем же CPE — со
своими сборками, как Fast Datapath (`…:9::fastdatapath`, сборки `el9fdp`), —
за RHEL не считаются. Неизвестный репозиторий учитывается как RHEL, но в
журнал пишется предупреждение с продуктом и CPE: если это надстройка, её
надо добавить в `vex.LAYERED_REPOS`.

## Битые блоки

Блок, в котором не шесть строк, третья строка не начинается с CVE-ID или в ней
нет компонента, в CSV не попадает. Такие блоки дословно, через пустую строку,
пишутся в отдельный файл — поправьте его и подайте на вход ещё раз. Причина
отказа — в журнале, строкой вида:

```
14:02:11 WARNING cli: блок 7 «Состоит из» отбракован: в блоке 5 строк, ожидается 6
```

Путь файла — `--rejects`, по умолчанию он рядом с выходом: `report.csv` →
`report.rejected.txt`; при выводе в stdout — `vulnsheet.rejected.txt` в
текущем каталоге. Файл создаётся, только если битые блоки есть; оставшийся
от прошлого прогона файл по тому же пути удаляется.

Если `--rejects` указан явно, каталог для него проверяется сразу же, вместе
с выходом — до обращения к koji и Red Hat: неверный путь падает сразу, а не
после всей сетевой работы.

Файл отбраковки ведётся только при `--blocks`: обновление по одной таблице
его не трогает.

## Журнал

Журнал идёт в stderr, поэтому `-o` и `2>run.log` друг другу не мешают.

Прогон начинается шапкой. Она выводится до первого запроса в сеть: версия,
конфиг, режим со входом и выходом, источники и их настройки, план запросов.
По ней сразу видно, подхватились ли конфиг и GitLab, не дожидаясь конца
прогона:

```
14:02:11 INFO    cli: vulnsheet 4.0.0
14:02:11 INFO    cli: конфиг: vulnsheet.yaml
14:02:11 INFO    cli: режим: синхронизация с блоками — таблица report.csv (строк 120) + блоки tasks.txt → report.csv
14:02:11 INFO    cli: вход: блоков 130, отбраковано 1 → report.rejected.txt
14:02:11 INFO    cli: koji: хаб https://koji.example.com/kojihub, тег sl9-updates
14:02:11 INFO    cli: VEX: RHEL 9, кэш /home/user/.cache/vulnsheet (живёт 3600 с), потоков 8
14:02:11 INFO    cli: стримы VEX для RHEL 9: nginx → nginx:1.26 (3)
14:02:11 INFO    cli: GitLab: gitlab.example.com (по умолчанию), каталог PATCH, токен из $GITLAB_TOKEN, потоков 8
14:02:11 INFO    cli: диапазоны: NVD с ключом из $NVD_API_KEY, CVE.org, кэш /home/user/.cache/vulnsheet/ranges (живёт 86400 с), потоков 8
14:02:11 INFO    cli: AI: results.json (plugin 4.1.0, прогон 2026-10-27T14:30), completed 120, problems 12, sources_not_found 3
14:02:11 INFO    cli: план: koji — пакетов 60, VEX — CVE 95, GitLab — каталог PATCH по билдам из koji (до 60) → P, диапазоны — CVE 95 → D
```

- `вход:` есть, только если поданы блоки. Путь файла отбраковки пишется,
  только если битые блоки есть.
- Кэш VEX с `cache_ttl: 0` — `(не читается)`.
- Строки со стримами и именами VEX выводятся, только если что-то сработало.
- Без секции `gitlab`: `GitLab: не задан в конфиге — колонка P не
  проверяется`. Без секции `ranges`: `диапазоны: не заданы в конфиге —
  колонка D не сверяется`. Без `--ai`: `AI: файл не подан — колонки ai_* не
  обновляются`.
  Без токена: `без токена ($GITLAB_TOKEN пуст) — видны только публичные
  проекты`. Сам токен в журнал не пишется никогда.
- Если спрашивать нечего (например, в таблице один заголовок): `план:
  спрашивать нечего — в сеть не идём`.

Предупреждения о битых блоках и пропущенных результатах AI идут сразу после
шапки.

Заканчивается прогон итогом — последним блоком журнала, после всех
предупреждений по отдельным строкам и компонентам. Итог — список, каждый
пункт — своя строка журнала; метки те же, что в шапке:

- Первый пункт — куда записан результат (`выведено в stdout` при выводе в
  stdout) и сколько в нём строк. «совпало, Missing, новых» — только при
  синхронизации.
- `koji:` и `VEX:` считают строки выхода, по колонкам `SL NVR` и `RHEL state`.
  Строки, по которым нечего было спрашивать, не считаются. «оставлен
  прежний SL NVR» и «оставлены прежние данные VEX» — сколько строк при сбое
  сохранили прежние значения, выводятся, только если такие есть.
- `GitLab, колонка P:` — сколько строк получили `+` и `-`. «не
  проверено» — строки, где патчи проверить не удалось (сбой GitLab или
  koji): в новых стоит `-`, в прежних оставлено прежнее значение; выводится,
  только если такие есть. `GitLab, компоненты:` — исходы проверки по
  компонентам; «ошибок» — компоненты, где koji не дал деталей билда или
  GitLab не прочитал `PATCH`. Без секции `gitlab` вместо них одна строка:
  `GitLab: не задан — колонка P не проверялась`.
- `диапазоны версий, колонка D:` — сколько строк получили `+` и `-`,
  «не проверено» — как у `P`; затем сколько строк в уязвимом диапазоне, вне
  его и с неизвестным диапазоном, и из какого источника взяты диапазоны
  (строки, где диапазон не сверен, здесь не считаются). Без секции `ranges`
  — `диапазоны версий: не заданы — колонка D не сверялась`.
- `AI, колонки ai_*:` — сколько строк получили результат из файла и
  сколько результатов не нашли своей строки. Без `--ai` — `AI: файл не
  подан — колонки ai_* не обновлялись`.
- «отбраковано блоков» — только если битые блоки есть.
- `код возврата 1:` — с причинами (см. «Коды возврата»), при нуле — `код
  возврата 0`. При фатальной ошибке (код 2) итога нет, есть только строка
  ошибки.

| Уровень | Что видно |
|---|---|
| `error` | фатальная ошибка — одна строка |
| `warning` | неизвестный репозиторий в CPE продукта RHEL, битые блоки, пропущенные и повторённые результаты AI, пакеты `NOT_FOUND`, ошибки koji по пакету и билду, ошибки загрузки VEX, ошибки NVD и CVE.org, отключённый кэш; строки таблицы, где при сбое оставлены прежние koji, VEX, `P` или `D`, и строки, по которым нечего спрашивать; компоненты, чьи патчи не проверены, патчи, снятые с ветки вместо коммита, подменённый хост GitLab, повторы запросов к GitLab |
| `info` (по умолчанию) | шапка и итог (см. выше); прогресс загрузки VEX; удалённый файл отбраковки от прошлого прогона |
| `debug` | каждый запрос к VEX, koji, GitLab, NVD и CVE.org (без токена и ключа), попадания в кэш, пояснения к вердиктам (проигнорированные стримы, несколько вердиктов), почему компонент не проверялся на патчи, трейсбек фатальной ошибки |

## Коды возврата

| Код | Когда |
|---|---|
| `0` | CSV записан, ошибок нет. `NOT_FOUND`, `not listed` и `no VEX record` — ответы источников, не ошибки |
| `1` | CSV записан, но есть битые блоки, `ERROR` от koji, `fetch error` (в том числе там, где оставлены прежние значения), компоненты, чьи патчи в GitLab проверить не удалось, CVE, диапазоны которых не известны из-за сбоя NVD или CVE.org, строки таблицы, по которым нечего спрашивать, или результаты AI без `cve` или `package`. `Missing` — не ошибка |
| `2` | фатально: неверные аргументы (в том числе нет ни `--blocks`, ни `--table`, или `--table -`); нет версии RHEL, хаба или тега ни во флагах, ни в конфиге; конфиг не найден, не читается или не проходит проверку; нет PyYAML при заданном конфиге; блоки не читаются, не в UTF-8 или пусты; при синхронизации нет ни одного годного блока; таблица не читается или не в формате vulnsheet; файл AI не читается, не JSON или не в формате `format: 2`; выход не пишется; хаб koji недоступен, тега нет или не установлен `koji` |

## Разработка

Устройство пакета:

| Модуль | За что отвечает |
|---|---|
| `tasks.py` | разбор блоков, отбраковка |
| `kojiclient.py` | последние билды тега и их детали (`getBuild`) одним `multicall` |
| `vex.py` | загрузка CSAF/VEX с кэшем и выбор вердикта |
| `config.py` | чтение и проверка YAML-конфига, выбор стрима VEX |
| `sourceurl.py` | разбор `extra.source.original_url` в сервер, проект и ref |
| `httpclient.py` | GET на urllib с повторами и вычисткой токена из сообщений |
| `gitlabclient.py` | дерево каталога патчей в GitLab, разбор 404 «ветки нет» и «каталога нет» |
| `cveid.py` | CVE-идентификаторы в имени файла |
| `rpmvercmp.py` | сравнение версий, как в `rpm` |
| `ranges.py` | апстрим-диапазоны: загрузка из NVD и CVE.org с кэшем и ограничением частоты, разбор в интервалы, сверка версии |
| `patches.py` | билд koji → коммит сборки → CVE в его `PATCH` |
| `report.py` | строка из 27 колонок, запись CSV |
| `table.py` | чтение и проверка прежней таблицы, колонки `ai_*` для таблицы 2.x |
| `ai.py` | чтение и проверка файла AI, результаты по парам CVE + компонент |
| `merge.py` | слияние прежней таблицы, блоков, ответов koji, VEX, GitLab и диапазонов и результатов AI, значения `P` и `D` — без файлов и сети |
| `cli.py` | аргументы, выбор режима, связывание, файл отбраковки, коды возврата |
| `logs.py` | единственное место, где ставится хендлер журнала |

Тесты — без сети: koji подменён `tests/fakes.py:FakeKojiSession`, VEX —
подменой `vulnsheet.vex.download` и документами из `tests/fakes.py:csaf`,
GitLab — `tests/fakes.py:FakeTransport`.

`sourceurl.py`, `httpclient.py`, `gitlabclient.py` и выбор коммита в
`patches.py` перенесены из тулзы `dashboard` копией, вместе с тестами: тулзы
общего кода не делят. Исправление там стоит проверить и здесь.

```bash
python3 -m unittest discover -s tests -v
```

Версия тулзы независима от версии репозитория. Номер живёт в
`vulnsheet/__init__.py` и поднимается тем же коммитом, что и изменение:
сломали формат входа, выхода или флаг — старший, новая возможность —
средний, исправление — младший. Вместе с номером — запись в
[CHANGELOG.md](CHANGELOG.md) тулзы и строка «`vulnsheet` (X.Y.Z): …» в
корневом `CHANGELOG.md`. Что запись есть, сторожит `tests/test_version.py`.
