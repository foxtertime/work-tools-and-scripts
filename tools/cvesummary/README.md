# cvesummary

Собирает из xlsx или CSV таблицы процесса устранения CVE одну HTML-страницу сводки:
состояние задач, что можно закрыть, риски, разрезы по критичности и принятым
мерам, темп и прогноз со сканфризом, карточки разработчиков с часами работы,
аномалии в данных, вердикты AI и remediation. Таблицу ведёт процесс: строки делает
тулза `vulnsheet`, колонки `Разработчик`, `Статус`, даты и
`Принятая мера` заполняют люди.

Тулзу применяют, когда нужно показать, где встала работа, на ком сколько
висит и успеваем ли к релизу. Страница — один файл, его можно переслать или
открыть без сервера.

**Версия:** 1.14.0 (номер — в `cvesummary/__init__.py`, выводится по
`python3 -m cvesummary --version`; история — [CHANGELOG.md](CHANGELOG.md)).

## Требования

- Python 3.9+, только стандартная библиотека. `openpyxl` не нужен: xlsx
  разбирается своим кодом.
- Для просмотра страницы — браузер. Шрифты подключаются с Google Fonts; без
  сети страница открывается на запасных шрифтах и остаётся читаемой.

## Запуск

Из каталога тулзы:

```sh
python3 -m cvesummary таблица.xlsx
python3 -m cvesummary таблица.xlsx -o сводка.html
python3 -m cvesummary таблица.xlsx --as-of 2026-10-19
python3 -m cvesummary таблица.xlsx --release 9.3.2
python3 -m cvesummary таблица.csv
```

- Таблица с расширением `.csv` (регистр не важен) читается как CSV, любая
  другая — как xlsx. Что и как берётся из CSV — в разделе «Что читается из
  CSV».

- Без `-o` страница ложится рядом с таблицей: `таблица.html`. Существующий
  файл перезаписывается, с `-o` или без него; в журнал идёт предупреждение. Писать поверх самой
  таблицы тулза отказывается.
- `--as-of` — дата отчёта, по умолчанию сегодня. От неё считаются часы
  открытых задач, окно темпа и прогноз.
- `--release` — название релиза: в шапке пишется перед датой отчёта
  («9.3.2 на 19.10.2026») и попадает в заголовок вкладки. Без него — только
  дата.
- Код возврата `0` — страница записана; `2` — таблица не читается, нет
  шапки или обязательных колонок, неверная дата в `--as-of`, страницу не
  удалось записать.
- В stderr идёт журнал: лист и строка шапки (для CSV — разделитель,
  кодировка и строка шапки); найденные («колонки: …») и
  отсутствующие необязательные колонки; сколько строк прочитано, сколько
  пропущено без `CVE ID`, сколько дат не разобрано; дата отчёта и релиз,
  если задан; куда записана страница.

## Что читается из xlsx

Только первый лист. Шапка — первая строка листа, где есть ячейка `CVE ID`;
всё выше (например, строка группировки `AG21` / `SberLinux` / `RedHat`)
пропускается.

Колонки ищутся по имени: регистр и крайние пробелы не важны, пробелы и
переносы строк внутри имени считаются одним пробелом (`SL NVR⏎(latest build)`
— та же колонка). Порядок любой, лишние колонки игнорируются. Если имя
повторяется, берётся первая колонка, в журнал идёт предупреждение.

- **Обязательные:** `CVE ID`, `Компонент`, `RHEL state`, `RHEL severity`.
  Без любой из них код 2 и список недостающих.
- **Необязательные:** `Разработчик`, `Статус`, `Start date`, `End date`,
  `Принятая мера`, `Task ID`, `Task date`, `Исполнитель`, `P`, `D`,
  `SL NVR (latest build)`, `RHEL NVR (if fixed)`, `Fix date`, `RHEL CVSS`,
  `Advisory (RHSA)`, `CVE link`, `Комментарий`, `ai_verdict`,
  `ai_confidence`, `ai_remediation`, `ai_run` (их пишет `vulnsheet --ai`,
  см. «AI и Remediation»). Отсутствующая читается
  пустой, журнал называет её.
- `Task state` не читается и нигде не используется.

`-`, `—` и пустая ячейка означают «нет значения». Полностью пустая строка
пропускается молча; строка без `CVE ID` пропускается и считается (число — в
журнале и в блоке аномалий).

**Даты** (`Task date`, `Start date`, `End date`, `Fix date`, `ai_run`) принимаются как
дата Excel (ячейка со стилем даты, учитывается `date1904`), как текст
`дд.мм.гггг` (допустимо время после даты: `дд.мм.гггг чч:мм`) или
`гггг-мм-дд` и как серийный номер Excel. Время в дате отбрасывается.
Правдоподобными считаются даты с 01.01.2000 по 31.12.2099 включительно;
остальные (опечатка вроде `01.10.0206`, число `5` вместо даты) не
разбираются. Нераспознанная дата остаётся текстом и попадает в аномалии.

## Что читается из CSV

CSV читается так же, как первый лист xlsx: шапка — первая строка с `CVE ID`,
колонки по именам, те же обязательные колонки, пустые значения и даты. Все
значения в CSV — текст, поэтому даты нужны в виде `дд.мм.гггг` или
`гггг-мм-дд`; CSV из `vulnsheet` читается как есть.

- **Кодировка:** UTF-8, с BOM или без; если файл не читается как UTF-8 —
  cp1251, в ней сохраняет CSV русский Excel.
- **Разделитель:** `;`, `,` или табуляция — тот, при котором в файле
  находится шапка с ячейкой `CVE ID`, а если таких несколько — с большим
  числом колонок в шапке. Шапки нет ни при каком — берётся `;`, как пишет
  `vulnsheet`.
- Длина поля не ограничена: длинный комментарий читается целиком.
- Поле в кавычках может содержать разделитель и перевод строки. Номер строки
  в журнале и аномалиях — номер записи, как его покажет Excel.
- Файл с нулевыми байтами (xlsx с расширением `.csv`, «Юникод-текст» Excel в
  UTF-16) не читается: код 2.

## Роли статусов

Роль задачи определяется только по `Статус`, без учёта регистра и крайних
пробелов.

| Роль | Правило |
|---|---|
| не взята | `Разработчик` пуст, статус не «Готов» |
| готово (закрыта) | «Готов», с разработчиком или без |
| на ревью | «Ожидает ревью» |
| на паузе | «На паузе» |
| требует внимания | «Есть проблема», «Нужна доработка» |
| в работе | разработчик есть, статус не «Готов» (включая ревью, паузу, внимание, пустой и неизвестный статус) |

Открытая задача — любая, кроме «Готов». «Ожидает ревью» открыта и для часов
не отличается от «В работе». Статус вне набора показывается как есть.

## Можно закрыть

Открытую задачу можно закрыть по одному или нескольким основаниям:

| Основание | Правило |
|---|---|
| фикс в RHEL | `RHEL state` = Fixed |
| устранено ранее | `P` = `+`: патч лежит в `PATCH`, последний билд собран с ним |
| вне диапазона | `D` = `+`: версия вне уязвимых диапазонов |
| дубликат | та же пара `CVE ID` + `Компонент`, что у основной строки |

Задача — пара `CVE ID` + `Компонент` (регистр и крайние пробелы не важны);
строк с одной парой может быть несколько. Основная строка группы — «Готов»,
если такая есть, и тогда дубликаты все открытые строки группы. Иначе
основная — взятая разработчиком с самой ранней `Start date`, а если не взял
никто — с самой ранней `Task date`; строка без даты (или с неразобранной)
идёт после датированных, при равенстве — первая в таблице; взятая строка
без `Start date` всё равно основнее невзятой. Остальные
открытые строки группы — дубликаты, даже если в них кто-то работает. Строка
без компонента в группы не попадает. Какая строка основная, показывает
подсказка у пилюли «дубликат».

Строки оснований в блоке «Можно закрыть» считают каждое основание
отдельно, одна задача может стоять в нескольких; число в подписи блока и
над общей полосой шапки («можно закрыть») — задачи, у которых есть
хоть одно основание, каждая один раз. В общей полосе шапки и в легенде под
ней задача стоит в одном сегменте: готовая — в «Готово», открытая с
основаниями — по первому из них в порядке таблицы выше (Фикс в RHEL →
Устранено ранее → Вне диапазона → Дубликат), остальные — в «Без решения».
Слева направо: готово, без решения, можно закрыть. Часы дубликат ест как
обычная задача.

## Часы

Скорость меряется в часах работы, а не в календарных днях.

- Задача попадает в расчёт, если у неё есть разработчик и `Start date`.
  Интервал — от `Start date` до `End date` включительно; без `End date` — до
  даты отчёта; конец позже даты отчёта обрезается по ней.
- День разработчика рабочий, если это будний день или если в этот день у
  него `Start date` или `End date` какой-либо задачи: взял или закрыл задачу
  в выходной — значит, работал.
- 8 часов рабочего дня делятся поровну между задачами, которые в этот день
  на нём висят. Часы задачи — сумма её долей. У закрытой это итоговая
  трудоёмкость, у открытой — «вложено пока».

Пример. Разработчик берёт A в понедельник и закрывает в среду, берёт B во
вторник и закрывает в следующий понедельник, берёт C в пятницу и закрывает в
субботу.

| День | Висят | A | B | C |
|---|---|---|---|---|
| пн | A | 8 | | |
| вт | A, B | 4 | 4 | |
| ср | A, B | 4 | 4 | |
| чт | B | | 8 | |
| пт | B, C | | 4 | 4 |
| сб (закрыта C) | B, C | | 4 | 4 |
| вс | B | | нерабочий | |
| пн | B | | 8 | |
| **итого** | | **16** | **32** | **8** |

Понедельник в последней строке — понедельник следующей недели.

Время закрытия внутри дня неизвестно, поэтому день закрытия делится наравне
с остальными задачами. Разработчик взял первую задачу в понедельник (8 ч),
во вторник взял ещё три (по 8 / 4 = 2 ч на каждую), в среду сдал первую —
висят те же четыре, ей ещё 2 ч. Итого первая задача — 12 ч.

Часы дают среднее и медиану часов на задачу (в целом, по разработчику, по
критичности, по мере), скорость разработчика (сколько задач он закрывает за
8-часовой рабочий день) и колонку «часов» в таблицах. В прогнозе часов нет.

В аномалии (с причиной и номером строки листа) уходят задачи, которые в
часы не попали:

- `End date` раньше `Start date`;
- «Готов» без `End date`;
- нераспознанная `Start date` или `End date`;
- разработчик есть, `Start date` нет.

`Start date` позже даты отчёта аномалией не считается: интервала нет, часов 0.

Нераспознанная `Task date` или `Fix date` тоже попадает в блок «Аномалии», но
на часы не влияет: в расчёт идут только `Start date` и `End date`.

## Прогноз

Прогноз считается в задачах, не в часах. Три поля на странице управляют им:

- **период темпа** — две даты, «Темп с» и «по» (по умолчанию последние 14
  дней): за него берутся среднее поступление задач в календарный день и
  среднее закрытие в рабочий день (закрытые за период делятся на число
  рабочих дней в нём). Конец позже даты отчёта прижимается к ней, начало
  раньше начала работы — самой ранней `Start date` у взятых задач — к
  началу работы: заведённые раньше задачи — стартовый бэклог. Перепутанные
  даты меняются местами. Период может кончаться и раньше даты отчёта —
  прогноз всё равно идёт от неё;
- **сканфриз** — дата, после которой новые задачи поступать не будут; без
  неё поступление считается бессрочным;
- **целевая дата** — к какому сроку нужно закрыть остаток.

Остаток открытых задач плюс поступление до сканфриза минус закрытие в
текущем темпе даёт дату, когда остаток дойдёт до нуля, или «не завершится».
Для целевой даты считается, сколько задач в рабочий день нужно закрывать,
против текущего темпа.

Новые задачи приходят каждый календарный день, и в выходные; закрывают
только по рабочим дням — Пн–Пт, праздники не учитываются. Поэтому дата
окончания всегда рабочая. Задачи, закрытые в выходной, в темп закрытия всё
равно входят. Число баланса показывает, сколько за выбранный период
поступило минус сколько закрыто: «+4 — бэклог вырос за 14 дней»; сами
поступление и закрытие — средние за период, в подсказке — сколько это
задач.

График темпа переключается: «Поток» — поступило и закрыто по дням со
скользящим средним за 7 дней; «Burn-up» — всего поступило и всего закрыто
нарастающим итогом, расстояние между линиями — открытый бэклог; «Burn-down»
— сколько открыто на каждый день. После даты отчёта линии продолжаются
пунктиром по той же модели, что строки прогноза (до нуля или до горизонта в
год); на burn-down ещё и идеальная прямая от сегодняшнего остатка к нулю в
целевую дату. Отмечены дата отчёта, сканфриз и цель; на всех трёх видах
закрашено окно расчёта — выбранный период темпа. Задача без `Task date`
считается в бэклоге с самого начала, «Готов» без `End date` — закрытой, как
только поступила, поэтому остаток на дату отчёта совпадает с «открыто
сейчас».

Режим и вид графика темпа, период темпа, сканфриз, целевая дата,
разработчики и темп на одного для «Когда начать», разбивка «Компонентов» (по
критичности, вердикту RHEL или принятой мере) и шаг «Поступления задач» и
сжигания в «Разработчиках» (по дням или по неделям) запоминаются в браузере (`localStorage`)
и остаются при следующем открытии страницы. Если хранилище недоступно, поля
просто не запоминаются.

### Когда начать

Переключатель справа в шапке «Темпа и прогноза» — «Прогноз» или «Когда начать».
Второй режим нужен, пока работа не началась: вместо периода темпа во
второй строке задаются «Людей» и «На одного» — сколько разработчиков и
сколько задач в рабочий день закрывает каждый (по умолчанию — сколько людей
закрывали задачи в периоде темпа и их средний темп; никто не закрывал — 1
человек по 1 задаче). Плановый темп закрытия — их произведение в рабочий
день. Поступление — реальное, за период темпа (он в этом режиме спрятан, но
не сбрасывается), до сканфриза; без сканфриза новые приходят всё время.

Галка «Без задач с готовым решением» рядом с ними считает, что открытые
задачи с готовым решением (см. «Можно закрыть») закрываются сразу: весь
прогноз (три колонки под числами темпа) и симуляция на графике считаются
по остальным, на
burn-графиках остаток падает ступенькой в день после отчёта. Сколько таких
задач — в подсказке у галки; числа темпа по-прежнему по факту.

До старта задачи только поступают, со старта закрываются плановым темпом.
Справа три строки:

- **Начать не позднее** — самый поздний день старта (не раньше завтра), при
  котором открытые и новые до сканфриза закрываются к целевой дате; «не
  успеть», если не выйдет и со старта завтра; цель дальше чем через 10 лет
  не считается;
- **Если начать завтра** — когда закончим и какой запас или опоздание
  относительно цели;
- **Разработчиков нужно** — сколько людей при заданном темпе на одного
  нужно, чтобы со старта завтра успеть к цели.

Плитки «по плану в рабочий день» и «бэклог за неделю по плану» (насколько бэклог
меняется за неделю работы по плану) считаются по заданному темпу,
поступление и «открыто сейчас» — по факту. Графики те же три вида: до даты
отчёта факт, после — симуляция пунктиром от дня старта, с отметкой «старт».
Остальные блоки страницы режим не трогает — они считаются по фактическим
данным и периоду темпа.

## AI и Remediation

Два последних блока страницы — по данным AI: колонкам `ai_*`, которые
`vulnsheet --ai` переносит из `results.json` плагина `rhel-security`.
Считаются пары `CVE ID` + `Компонент`, как в счётчике задач шапки: повторы
пары — одна пара, строка без компонента — отдельная. Если у строк одной
пары разные данные AI, берётся строка с самой поздней `ai_run`, при равной
или неразобранной — первая строка с вердиктом. Значения сравниваются без
учёта регистра.

Обе полосы разбиты на три группы по вердикту пары, слева направо:
«возможно затронуто» (`affected`, `unclear` и незнакомые вердикты), «не
затронуто» (`not affected`, `invalid CVE`, `rejected CVE`) и «не прогнано»
(`not processed` и пары без вердикта). Над полосой — скобки групп с числом
пар и долей, как в шапке: скобка встаёт ровно над сегментами своей группы,
подпись рисуется, только если влезает, иначе уходит в легенду под полосой.
Строки под полосой идут в том же порядке, что и сегменты.

**AI** — что сказал AI и сколько ещё не прогнано. Крупно — сколько пар
осталось прогнать из всех, рядом — сколько прогнано и доля. Прогнана пара с
настоящим вердиктом; `not processed` (пара была в прогоне, но AI её не
разобрал) и пара без вердикта ещё остались. Полоса — сегмент на каждый
вердикт, затем `not processed` и серое «не прогнано». Под ней строки в
порядке `affected`, `unclear`, незнакомые значения (серым, как пришли),
`not affected`, `invalid CVE`, `rejected CVE`, `not processed` и «не
прогнано»; в каждой — пары, уверенность `high` / `medium` / `low`
(`ai_confidence`) и доля от всех пар. Пара с другой или пустой уверенностью
входит в число пар, но ни в одну из трёх колонок. В подписи — последний
прогон, самая поздняя `ai_run` в таблице.

**Remediation** — что делать по парам, по `ai_remediation`. Полоса — та же
серая часть «не прогнано», а прогнанная поделена по значениям remediation,
и в конце — `not processed`, у которого remediation нет. Remediation пары
стоит в группе её вердикта, поэтому скобки здесь той же ширины, что в
блоке AI. Внутри группы строки — пары и доля от всех, в порядке: сначала
фикс есть или готов (`backport prepared`, `vendor update available`,
`rebuild required`), потом ручная работа (`manual integration required`,
`manual remediation required`), блокеры (`upstream fix unavailable`,
`pending`), затем `not determined` и `not required`; незнакомые — следом,
«не указана» — у прогнанной пары без remediation, последней в группе.

Если колонки `ai_verdict` (для Remediation — и `ai_remediation`) в таблице
нет, блок пишет «В таблице нет данных AI», остальная страница строится как
обычно.

## Строка разделов

Под шапкой — строка с якорями на все разделы страницы; при прокрутке она
прилипает к верху окна. У «Требует внимания», «Можно закрыть» и «Аномалий» —
бейдж с числом задач, тем же, что в самом разделе. Подсвечен раздел, чей верх
уже ушёл под строку; внизу страницы — последний; пока видна шапка — ни один.
По клику подсвечен выбранный раздел сразу. Якоря стоят по центру; на узком
экране строка листается вбок, и подсвеченный якорь сам встаёт в её середину.

## Графики по времени

Дневные и недельные графики (темп, поступление, сжигание, закрытия в
карточке разработчика) показывают весь период: от первой даты в данных до
даты отчёта. Если период в карточку не помещается, график листается внутри
неё по горизонтали, без видимой полосы прокрутки: перетаскиванием мышью,
Shift+колесом, тачпадом или пальцем. Вертикальное колесо без Shift
прокручивает страницу как обычно.

При открытии график стоит в конце, на последних днях. При изменении ширины
окна он сохраняет расстояние до правого конца, на которое его промотал
пользователь.

Графики показывают, на что указывает курсор: на линейном графике темпа —
пунктирная направляющая дня и точки на всех линиях; в столбиках и полосах
блок под курсором остаётся ярким, соседние приглушаются (неделя целиком, день
в карточке разработчика, сегмент полосы, строка разреза). Подсказка с
числами — как раньше.

## Разработка

Все команды — из каталога тулзы:

```sh
python3 -m unittest discover -s tests -v
node --test tests/js/*.test.js
python3 -m tests.example пример.xlsx
python3 -m tests.example пример.csv
```

Первая команда запускает тесты Python, вторая (нужен Node.js) — тесты чистых
JS-модулей без браузера. Третья пишет пример таблицы на 100 вымышленных строк
(с колонками `ai_*`: примерно половина пар прогнана через AI, вердикты и
remediation — токены плагина) для ручной
проверки страницы, четвёртая — те же строки в CSV через `;`.
Страницу из примера собирает `python3 -m cvesummary пример.xlsx --as-of 2026-10-19`
(или `пример.csv`); результат открыть в браузере.

| Модуль | Назначение |
|---|---|
| `cvesummary/xlsx.py` | zip → лист → строки ячеек, типы, даты по стилю |
| `cvesummary/csvfile.py` | CSV → те же строки ячеек: кодировка, разделитель |
| `cvesummary/table.py` | шапка, колонки по именам, нормализация строк, ошибки входа |
| `cvesummary/page.py` | сборка HTML из `assets/` и JSON с данными |
| `cvesummary/cli.py` | командная строка, журнал, запись файла |
| `cvesummary/assets/js/` | роли, часы, темп и прогноз, даты, ширина графиков, строка разделов, подписи полос, данные AI, отрисовка |
| `tests/`, `tests/js/` | тесты Python (`unittest`) и JS (`node --test`) |

Python отдаёт странице нормализованные строки, все расчёты делает JS.
Подробности и принятые решения — в
[спеке](docs/superpowers/specs/2026-10-19-cvesummary-design.md). Соглашения
репозитория (ветки, коммиты, changelog, задачи) — в
[CLAUDE.md](../../CLAUDE.md).
