# cvesummary

Собирает из xlsx или CSV таблицы процесса устранения CVE одну HTML-страницу сводки:
состояние задач, что можно закрыть, риски, разрезы по критичности и принятым
мерам, темп и прогноз со сканфризом, карточки разработчиков с часами работы,
аномалии в данных, вердикты AI и remediation. Таблицу ведёт процесс: строки делает
тулза `vulnsheet`, колонки `Разработчик`, `Статус`, даты и
`Принятая мера` заполняют люди.

Тулзу применяют, когда нужно показать, где встала работа, на ком сколько
висит и успеваем ли к релизу. Страница — один файл, его можно переслать или
открыть без сервера.

**Версия:** 1.26.1 (номер — в `cvesummary/__init__.py`, выводится по
`python3 -m cvesummary --version`; история — [CHANGELOG.md](CHANGELOG.md)).

## Требования

- Python 3.9+, только стандартная библиотека. `openpyxl` не нужен: xlsx
  разбирается своим кодом.
- Для просмотра страницы — браузер. Шрифты подключаются с Google Fonts; без
  сети страница открывается на запасных шрифтах и остаётся читаемой.

## Запуск

Из каталога тулзы:

```sh
python3 -m cvesummary таблица.xlsx
python3 -m cvesummary таблица.xlsx -o сводка.html
python3 -m cvesummary таблица.xlsx --as-of 2026-10-19
python3 -m cvesummary таблица.xlsx --release 9.3.2
python3 -m cvesummary таблица.csv
```

- Таблица с расширением `.csv` (регистр не важен) читается как CSV, любая
  другая — как xlsx. Что и как берётся из CSV — в разделе «Что читается из
  CSV».

- Без `-o` страница ложится рядом с таблицей: `таблица.html`. Существующий
  файл перезаписывается, с `-o` или без него; в журнал идёт предупреждение. Писать поверх самой
  таблицы тулза отказывается.
- `--as-of` — дата отчёта, по умолчанию сегодня. От неё считаются часы
  открытых задач, окно темпа и прогноз.
- `--release` — название релиза: в шапке пишется перед датой отчёта
  («9.3.2 на 19.10.2026») и попадает в заголовок вкладки. Без него — только
  дата.
- Код возврата `0` — страница записана; `2` — таблица не читается, нет
  шапки или обязательных колонок, неверная дата в `--as-of`, страницу не
  удалось записать.
- В stderr идёт журнал: лист и строка шапки (для CSV — разделитель,
  кодировка и строка шапки); найденные («колонки: …») и
  отсутствующие необязательные колонки; сколько строк прочитано, сколько
  пропущено без `CVE ID`, сколько дат не разобрано; дата отчёта и релиз,
  если задан; куда записана страница.

## Что читается из xlsx

Только первый лист. Шапка — первая строка листа, где есть ячейка `CVE ID`;
всё выше (например, строка группировки `AG21` / `SberLinux` / `RedHat`)
пропускается.

Колонки ищутся по имени: регистр и крайние пробелы не важны, пробелы и
переносы строк внутри имени считаются одним пробелом (`SL NVR⏎(latest build)`
— та же колонка). Порядок любой, лишние колонки игнорируются. Если имя
повторяется, берётся первая колонка, в журнал идёт предупреждение.

- **Обязательные:** `CVE ID`, `Компонент`, `RHEL state`, `RHEL severity`.
  Без любой из них код 2 и список недостающих.
- **Необязательные:** `Разработчик`, `Статус`, `Start date`, `End date`,
  `Принятая мера`, `Task ID`, `Task date`, `Исполнитель`, `P`, `D`,
  `SL NVR (latest build)`, `RHEL NVR (if fixed)`, `Fix date`, `RHEL CVSS`,
  `Advisory (RHSA)`, `CVE link`, `Комментарий`, `ai_verdict`,
  `ai_confidence`, `ai_remediation`, `ai_run` (их пишет `vulnsheet --ai`,
  см. «AI и Remediation»). Отсутствующая читается
  пустой, журнал называет её.
- `Task state` не читается и нигде не используется.

`-`, `—` и пустая ячейка означают «нет значения». Полностью пустая строка
пропускается молча; строка без `CVE ID` пропускается и считается (число — в
журнале и в блоке аномалий).

**Даты** (`Task date`, `Start date`, `End date`, `Fix date`, `ai_run`) принимаются как
дата Excel (ячейка со стилем даты, учитывается `date1904`), как текст
`дд.мм.гггг` (допустимо время после даты: `дд.мм.гггг чч:мм`) или
`гггг-мм-дд` и как серийный номер Excel. Время в дате отбрасывается.
Правдоподобными считаются даты с 01.01.2000 по 31.12.2099 включительно;
остальные (опечатка вроде `01.10.0206`, число `5` вместо даты) не
разбираются. Нераспознанная дата остаётся текстом и попадает в аномалии.

## Что читается из CSV

CSV читается так же, как первый лист xlsx: шапка — первая строка с `CVE ID`,
колонки по именам, те же обязательные колонки, пустые значения и даты. Все
значения в CSV — текст, поэтому даты нужны в виде `дд.мм.гггг` или
`гггг-мм-дд`; CSV из `vulnsheet` читается как есть.

- **Кодировка:** UTF-8, с BOM или без; если файл не читается как UTF-8 —
  cp1251, в ней сохраняет CSV русский Excel.
- **Разделитель:** `;`, `,` или табуляция — тот, при котором в файле
  находится шапка с ячейкой `CVE ID`, а если таких несколько — с большим
  числом колонок в шапке. Шапки нет ни при каком — берётся `;`, как пишет
  `vulnsheet`.
- Длина поля не ограничена: длинный комментарий читается целиком.
- Поле в кавычках может содержать разделитель и перевод строки. Номер строки
  в журнале и аномалиях — номер записи, как его покажет Excel.
- Файл с нулевыми байтами (xlsx с расширением `.csv`, «Юникод-текст» Excel в
  UTF-16) не читается: код 2.

## Роли статусов

Роль задачи определяется по `Статус` разработчика, без учёта регистра и
лишних пробелов. Для «Убрано из эпика» учитываются также разработчик и даты;
`Task state` тасктрекера в расчётах не участвует.

| Роль | Правило |
|---|---|
| не взята | `Разработчик` пуст, задача открыта |
| готово (закрыта) | «Готов», с разработчиком или без; либо «Убрано из эпика» по правилам ниже |
| на ревью | «Ожидает ревью» |
| на паузе | «На паузе» |
| требует внимания | «Есть проблема», «Нужна доработка» |
| в работе | разработчик есть, задача открыта (включая ревью, паузу, внимание, пустой и неизвестный статус) |

Открытая задача — любая, не признанная закрытой. «Ожидает ревью» открыта
и для часов не отличается от «В работе». Статус вне набора показывается как есть.

«Убрано из эпика» сохраняется в таблицах и CSV исходным статусом:

| Разработчик и даты | Расчётная роль |
|---|---|
| SecOps, с любыми датами или без них | закрыта |
| Другой разработчик, распознаны Start date и End date | закрыта |
| Другой разработчик, есть Start date, нет End date | в работе |
| Другой разработчик, нет Start date или дата ошибочна | открыта, с обычной диагностикой дат |
| Разработчик пуст | открыта, не взята |

Убранные строки сохраняются во всех итогах, разрезах, AI и экспорте.
Закрытые уменьшают остаток, открытые участвуют в работе и прогнозе.
Без распознанной End date нет датированного закрытия и вклада в скорость;
ошибочная End у SecOps сохраняется в аномалиях. Часы SecOps
без End date неизвестны. В накопительном графике закрытая задача без End
учитывается с поступления, как обычная «Готов» без даты завершения.
Открытая задача со Start date продолжает работу и препятствует личному перерыву.

В шапке и личной полосе статусов убранные показаны отдельным графитовым
сегментом всегда слева, независимо от расчётной роли. В зелёном и остальных
сегментах они повторно не учитываются. Подписи и подсказки общей полосы
не содержат приписки «без убранных».

В блоке «Состояние» убранные вынесены в отдельный счётчик «Убрано из эпика».
«Готов», «В работе» и «Не взято» показывают только остальные задачи;
сумма четырёх счётчиков совпадает с общим числом задач. Каждый счётчик
открывает собственную выборку. Например, 6 готовых + 2 убранных закрытых
+ 2 в работе: в «Состоянии» убрано 2, готово 6, в работе 2, не взято 0.
Расчётные роли по-прежнему определяют готовность, скорость и прогноз:
в этом примере расчётно закрыто 8 задач.

В личных карточках смысловые счётчики «готово»/«в работе» включают убранные
по роли и показывают «из них убрано из эпика». По клику на счётчик открывается
весь его состав, на «из них» — соответствующее подмножество, на сегмент —
только строки его цвета. Подсказка графита показывает закрытую и открытую части.

## Можно закрыть

Открытую задачу можно закрыть по одному или нескольким основаниям:

| Основание | Правило |
|---|---|
| фикс в RHEL | `RHEL state` = Fixed |
| устранено ранее | `P` = `+`: патч лежит в `PATCH`, последний билд собран с ним |
| вне диапазона | `D` = `+`: версия вне уязвимых диапазонов |
| дубликат | та же пара `CVE ID` + `Компонент`, что у основной строки |

Задача — пара `CVE ID` + `Компонент` (регистр и крайние пробелы не важны);
строк с одной парой может быть несколько. Основная строка группы — «Готов»,
если такая есть, и тогда дубликаты все открытые строки группы. Иначе
основная — взятая разработчиком с самой ранней `Start date`, а если не взял
никто — с самой ранней `Task date`; строка без даты (или с неразобранной)
идёт после датированных, при равенстве — первая в таблице; взятая строка
без `Start date` всё равно основнее невзятой. Остальные
открытые строки группы — дубликаты, даже если в них кто-то работает. Строка
без компонента в группы не попадает. Какая строка основная, показывает
подсказка у пилюли «дубликат».

«Убрано из эпика» не участвует в определении дубликатов: такая строка
не бывает основной или дубликатом и не делает дубликатами другие строки.
Остальные строки выбирают основную между собой. Уникальные пары учитывают
все строки; при раскрытии пары обычная строка предпочтительнее убранной,
а для пары только из убранных остаётся представитель из этой пары.

Строки оснований в блоке «Можно закрыть» считают каждое основание
отдельно, одна задача может стоять в нескольких; число в подписи блока и
в смысловых счётчиках — задачи, у которых есть
хоть одно основание, каждая один раз. В общей полосе шапки и в легенде под
ней убранная задача стоит в графитовом сегменте, а любая другая — в одном
из остальных: готовая — в «Готово», открытая с
основаниями — по первому из них в порядке таблицы выше (Фикс в RHEL →
Устранено ранее → Вне диапазона → Дубликат), остальные — в «Без решения».
Слева направо: убрано из эпика, готово, без решения, можно закрыть.
Скобки над полосой и её легенда показывают только состав своих сегментов;
убранные открытые с основаниями остаются в общем блоке «Можно закрыть». Часы дубликат ест как
обычная задача.

Если подпись счётчика над баром шапки не помещается, её текст постепенно
сокращается с многоточием, затем остаётся только число. В легенду под баром
счётчик переходит, только когда не помещается и само число. При расширении
окна подпись восстанавливается; в подсказке всегда остаётся полное название.

В каждом сегменте общей полосы шапки диагональная штриховка слева
(светлая на графите, тёмная на остальных цветах)
показывает растриаженную долю задач этого сегмента. Задача растриажена,
если назначен любой `Разработчик` либо `Исполнитель` = `УА`. Регистр и
лишние пробелы не учитываются; статус задачи и принятая мера на триаж не
влияют. Совпадение обоих условий считается один раз.
В подсказке сегмента — сколько в нём задач всего, сколько из них
растриажено и доля растриаженных внутри сегмента. Остальные полосы страницы
штриховку не используют; на графиках по времени той же штриховкой отмечены
перерывы в работе (см. «Перерывы в работе»).

## Часы

Трудоёмкость задач оценивается в часах работы. Скорость закрытия в задачах
за рабочий день считается отдельно, по рабочему периоду и перерывам.

- Задача попадает в расчёт, если у неё есть разработчик и `Start date`.
  Интервал — от `Start date` до `End date` включительно; без `End date` — до
  даты отчёта; конец позже даты отчёта обрезается по ней.
- День разработчика рабочий, если это будний день или если в этот день у
  него `Start date` или `End date` какой-либо задачи: взял или закрыл задачу
  в выходной — значит, работал.
- 8 часов рабочего дня делятся поровну между задачами, которые в этот день
  на нём висят. Часы задачи — сумма её долей. У закрытой это итоговая
  трудоёмкость, у открытой — «вложено пока».

Пример. Разработчик берёт A в понедельник и закрывает в среду, берёт B во
вторник и закрывает в следующий понедельник, берёт C в пятницу и закрывает в
субботу.

| День | Висят | A | B | C |
|---|---|---|---|---|
| пн | A | 8 | | |
| вт | A, B | 4 | 4 | |
| ср | A, B | 4 | 4 | |
| чт | B | | 8 | |
| пт | B, C | | 4 | 4 |
| сб (закрыта C) | B, C | | 4 | 4 |
| вс | B | | нерабочий | |
| пн | B | | 8 | |
| **итого** | | **16** | **32** | **8** |

Понедельник в последней строке — понедельник следующей недели.

Время закрытия внутри дня неизвестно, поэтому день закрытия делится наравне
с остальными задачами. Разработчик взял первую задачу в понедельник (8 ч),
во вторник взял ещё три (по 8 / 4 = 2 ч на каждую), в среду сдал первую —
висят те же четыре, ей ещё 2 ч. Итого первая задача — 12 ч.

Часы дают среднее и медиану часов на задачу (в целом, по разработчику, по
критичности, по мере) и колонку «часов» в таблицах. В прогнозе часов нет.

В аномалии (с причиной и номером строки листа) уходят задачи, которые в
часы не попали:

- `End date` раньше `Start date`;
- «Готов» без `End date` — кроме `SecOps`;
- нераспознанная `Start date` или `End date`;
- разработчик есть, `Start date` нет — кроме `SecOps` (без учёта регистра
  и крайних пробелов).

Для `SecOps` отсутствие `Start date` и `End date` допустимо. У задачи без
даты старта и у закрытой задачи без даты завершения часы неизвестны и в
расчёт не входят. У открытой задачи с датой старта часы по-прежнему
считаются до даты отчёта. Проверки неразобранных дат и завершения раньше
старта сохраняются.

`Start date` позже даты отчёта аномалией не считается: интервала нет, часов 0.

Нераспознанная `Task date` или `Fix date` тоже попадает в блок «Аномалии», но
на часы не влияет: в расчёт идут только `Start date` и `End date`.

## Прогноз

Прогноз считается в задачах, не в часах. Будущий темп — сумма личных
скоростей разработчиков, которые на дату отчёта не находятся на перерыве;
`SecOps` в будущую мощность команды не входит. Каждый личный темп берётся
за выбранный период, без общих и личных перерывов. В строке периода видно,
сколько людей участвует в прогнозе и какой темп получился. Исторические
закрытия выпавшего человека остаются в данных, но в будущий темп он
вернётся после возобновления работы по `Start date`. Если все на перерыве,
будущий темп равен нулю; открытые задачи сохраняются.

Плитка «закрывается в рабочий день», шапка и исторический общий темп
показывают фактические закрытия за рабочие дни команды. Это наблюдаемый
результат периода; прогноз использует состав команды на дату отчёта.

Три поля на странице управляют расчётом:

- **период темпа** — две даты, «Темп с» и «по» (по умолчанию последние 14
  дней): за него берутся среднее поступление задач в календарный день и
  среднее закрытие в рабочий день (закрытые за период делятся на число
  рабочих дней в нём; перерывы в работе не считаются, см. «Перерывы в
  работе»). Конец позже даты отчёта прижимается к ней, начало
  раньше начала работы — самой ранней `Start date` у взятых задач — к
  началу работы: заведённые раньше задачи — стартовый бэклог. Перепутанные
  даты меняются местами. Период может кончаться и раньше даты отчёта —
  прогноз всё равно идёт от неё;
- **сканфриз** — первый день без новых задач; без
  неё поступление считается бессрочным;
- **целевая дата** — к какому сроку нужно закрыть остаток.

Если в окне нет будней, исторический темп закрытия считается на
календарный день, исключая общие перерывы; подписи плитки, шапки и
сценариев явно показывают другую единицу. Число закрытий сохраняется.
Если окно целиком находится до начала работы, пересечение пустое:
показатели и прогноз показывают «—» с пояснением. Один искусственный день
не добавляется; текущий остаток задач остаётся виден. При известном
периоде без закрытий общая и личная скорость показывают 0, включая шапку.

Завершение — закрыт весь текущий объём и все ожидаемые поступления до
сканфриза. Временный ноль в очереди не означает завершение: новые задачи
продолжают поступать, график продолжается. Если последние поступления
закрыты в последний день перед сканфризом, завершение возможно в этот день.
Без сканфриза при положительном поступлении показывается «срок не
определён», независимо от скорости закрытия. При нулевом поступлении
сканфриз для расчёта даты не нужен. Отдельные состояния — «нет закрытий»
и «за горизонтом» (завершение не найдено за 10 лет).

Каждый день сначала поступают новые задачи, затем закрывается не больше
текущего остатка. Свободная мощность не переносится на будущие дни.
Для целевой даты показываются:

- **Остаток к цели** — ожидаемая открытая очередь, даже когда срок
  завершения не определён. Доли задач сохраняются; положительный остаток
  меньше 0,1 показывается как «< 0,1».
- **Запас до цели** — рабочие дни между завершением и целью либо опоздание.
  Без известной даты завершения запас неизвестен.
- **Нулевой остаток к цели** — минимальный постоянный темп в рабочий день.
  Он учитывает, когда появятся задачи: будущие поступления нельзя закрыть
  заранее. Если после последнего рабочего дня до цели ещё поступят задачи,
  нулевой остаток недостижим при любом темпе. Нулевой остаток на дату цели
  не означает завершение всего объёма, если поступления продолжатся позже.

Под прогнозом сравниваются сценарии по фактическому темпу за 7 / 14 / 30
дней до выбранной даты «по». Начало каждого окна ограничено началом работы;
в таблице видны фактические границы и число закрытых за рабочие дни окна.
Для каждого сценария — поступление, закрытие, дата завершения, остаток и
запас к одной целевой дате. Это сравнение исторических темпов, не
статистический доверительный интервал. Цель дальше чем через 10 лет
не рассчитывается; при очищенной цели показатели на дату цели неизвестны.

Новые задачи приходят каждый календарный день, и в выходные; закрывают
только по рабочим дням — Пн–Пт, праздники не учитываются. Поэтому дата
окончания всегда рабочая. Задачи, закрытые в выходной, в темп закрытия всё
равно входят. Число баланса показывает, сколько за выбранный период
поступило минус сколько закрыто: «+4 — бэклог вырос за 14 дней»; сами
поступление и закрытие — средние за период, в подсказке — сколько это
задач.

Тот же темп закрытия — в шапке, в «Рисках и темпе», строкой «Задач в
день»: крупно — закрыто в рабочий день за всё время с начала работы,
рядом — за выбранный период темпа (меняется вместе с ним), в подсказке —
сколько задач за сколько рабочих дней и сколько рабочих дней перерывов не
учтено.

### Перерывы в работе

Исторический темп закрытия считается без общих перерывов в работе.
Прогноз, сценарии 7 / 14 / 30 дней и «На одного» по умолчанию в «Когда
начать» также учитывают личные перерывы и текущий состав команды.
Иначе несколько CVE, сделанных задолго до
основной работы, сдвигают начало работы назад, и все пустые рабочие дни
между ними и основной работой занижают темп.

- **День работы** — день, когда на ком-то из разработчиков висит задача, как
  в «Часах»: будний день внутри интервала `Start date` … `End date`
  (открытая — до даты отчёта), выходной — если в этот день задачу взяли или
  закрыли. `SecOps` не наша команда: их задачи днями работы не считаются.
- **Перерыв** — 5 и больше рабочих дней подряд без дней работы, вместе с
  выходными между ними, от начала работы до даты отчёта; хвост перед датой
  отчёта — по тому же правилу. Короткий простой — обычные рабочие дни, он в
  темпе остаётся.
- Рабочие дни перерыва вычитаются из знаменателя, закрытое в перерыве
  (например, `SecOps`) — из числителя. Поступление перерывы не трогают:
  задачи приходят и в них. Баланс («бэклог вырос») считает все закрытые за
  период, в том числе в перерыве, — это реальное изменение очереди.
- Если дней работы нет вовсе, перерывов нет.
- Общий и личный перерывы исключаются из личной скорости объединением:
  один день не вычитается дважды.

Сколько рабочих дней перерыва вычтено — в подсказках «Задач в день» и
«закрывается в рабочий день», в строке периода темпа и в сценариях.

### Личные перерывы и скорость

Личный перерыв — **пять и больше рабочих дней подряд** без начатых задач:
на пятом рабочем дне весь простой становится перерывом задним числом.
Начало — день после последнего дня с начатой задачей; конец — день перед
следующим `Start date`, у незаконченного перерыва — дата отчёта. Порог
общего и личного перерыва одинаков — пять рабочих дней. Выходные не приближают порог.

Открытая задача со `Start date` означает продолжающуюся работу, даже если
разработчик давно ничего не закрывал. Назначение без `Start date` работой
не считается. Длинный простой до первого старта тоже исключается; если
общего начала работы ещё нет, скорость неизвестна.

Личная скорость — все закрытые задачи активных частей выбранного окна,
делённые на все рабочие дни этих частей. Короткий простой входит в дни,
даже когда на человеке нет задач. Учитываются также выходные, в которые
он работал по правилам раздела «Часы». «Всего» считается от общего начала
работы до даты отчёта. Окно без закрытий, но с активными рабочими днями,
даёт 0; окно целиком в перерыве — «—», с пояснением в подсказке.
Перерывы определяются по всей истории до даты отчёта: изменение окна
меняет только учитываемую часть перерыва, но не отменяет его.

Например, пять задач в первый день и три рабочих дня без задач дают
5 / 4 = 1,25 (на странице 1,3). После пяти рабочих дней простоя весь
простой исключается: 5 / 1 = 5. Если после возвращения за один день
начаты и закрыты ещё три задачи, общий результат — (5 + 3) / (1 + 1) = 4.
Скорости отдельных периодов без весов не усредняются.

Личные перерывы видны только на графике соответствующего разработчика:
фиолетовая штриховка другого направления, подпись «личный перерыв»,
легенда и подсказка дня. Общие перерывы сохраняют свою штриховку;
на пересечении видны обе встречные диагонали, образующие сетку, а подписи
разнесены по высоте. В личной карточке видно, если человек
на перерыве сейчас, а в подсказках скорости — закрытия, активные дни и
число исключённых дней.

График темпа переключается: «Поток» — поступило и закрыто по дням со
скользящим средним за 7 дней; «Burn-up» — всего поступило и всего закрыто
нарастающим итогом, расстояние между линиями — открытый бэклог; «Burn-down»
— сколько открыто на каждый день. После даты отчёта линии продолжаются
пунктиром по той же модели, что строки прогноза (до завершения всего объёма
или до горизонта в год, включая временные нули); на burn-down ещё и идеальная прямая от сегодняшнего остатка к нулю в
целевую дату. Отмечены дата отчёта, сканфриз и цель; на всех трёх видах
закрашено окно расчёта — выбранный период темпа. Задача без `Task date`
считается в бэклоге с самого начала, «Готов» без `End date` — закрытой, как
только поступила, поэтому остаток на дату отчёта совпадает с «открыто
сейчас».

Режим и вид графика темпа, период темпа, сканфриз, целевая дата,
разработчики и темп на одного для «Когда начать», разбивка «Компонентов» (по
критичности, вердикту RHEL или принятой мере) и шаг «Поступления задач» и
сжигания в «Разработчиках» (по дням или по неделям) запоминаются в браузере (`localStorage`)
и остаются при следующем открытии страницы. Если хранилище недоступно, поля
просто не запоминаются.

### Когда начать

Переключатель справа в шапке «Темпа и прогноза» — «Прогноз» или «Когда начать».
Второй режим нужен, пока работа не началась: вместо периода темпа во
второй строке задаются «Людей» и «На одного» — сколько разработчиков и
сколько задач в рабочий день закрывает каждый (по умолчанию — сколько людей
сейчас вне перерывов, кроме SecOps, и их средняя личная скорость за период;
если участников нет — один, если нет оценки темпа — одна задача на человека).
Это гипотетический состав для планирования, даже когда фактический
прогноз показывает нулевую мощность. Автоматические значения обновляются
при смене периода и данных. Только явно введённые вручную параметры
сохраняются между открытиями страницы; каждое поле независимо. Очистка
поля возвращает автоматическую оценку, «По текущим данным» сбрасывает оба
ручных параметра. Подпись симуляции поясняет источник значений.
Старые сохранённые значения версий до 1.25.1 не используются: они не
различали автоматический расчёт и ручной ввод. Ручной план при необходимости
нужно задать заново. Плановый темп — произведение людей и темпа в рабочий
день. Поступление — реальное, за период темпа (он в этом режиме спрятан, но
не сбрасывается), до сканфриза; без сканфриза новые приходят всё время.

Галка «Без задач с готовым решением» рядом с ними считает, что открытые
задачи с готовым решением (см. «Можно закрыть») закрываются сразу: весь
прогноз (три колонки под числами темпа) и симуляция на графике считаются
по остальным, на
burn-графиках остаток падает ступенькой в день после отчёта. Сколько таких
задач — в подсказке у галки; числа темпа по-прежнему по факту.

До старта задачи только поступают, со старта закрываются плановым темпом.
Нулевой текущий остаток, в том числе после исключения задач с готовым
решением, не отменяет будущие поступления. Без сканфриза при положительном
поступлении неизвестны и дата завершения, и самый поздний старт, и число
людей для завершения всего объёма. Если поступления ожидаются после цели,
никакое число людей не обеспечит завершение всего объёма к этой дате.
Справа три строки:

- **Начать не позднее** — самый поздний день старта (не раньше завтра), при
  котором открытые и новые до сканфриза закрываются к целевой дате; «не
  успеть», если не выйдет и со старта завтра; цель дальше чем через 10 лет
  не считается;
- **Если начать завтра** — когда закончим и какой запас или опоздание
  относительно цели;
- **Разработчиков нужно** — сколько людей при заданном темпе на одного
  нужно, чтобы со старта завтра успеть к цели.

Плитки «по плану в рабочий день» и «бэклог за неделю по плану» (изменение
очереди за следующие 7 дней при старте завтра, с учётом сканфриза и галки
исключения задач с готовым решением) считаются по заданному темпу,
поступление и «открыто сейчас» — по факту. Графики те же три вида: до даты
отчёта факт, после — симуляция пунктиром от дня старта, с отметкой «старт».
Остаток и запас под прогнозом в этом режиме — при старте завтра; сравнение
фактических окон 7/14/30 скрыто. Остальные блоки страницы режим не трогает — они считаются по фактическим
данным и периоду темпа.

## AI и Remediation

Два последних блока страницы — по данным AI: колонкам `ai_*`, которые
`vulnsheet --ai` переносит из `results.json` плагина `rhel-security`.
Считаются пары `CVE ID` + `Компонент`, как в счётчике задач шапки: повторы
пары — одна пара, строка без компонента — отдельная. Если у строк одной
пары разные данные AI, берётся строка с самой поздней `ai_run`, при равной
или неразобранной — первая строка с вердиктом. Значения сравниваются без
учёта регистра.

Обе полосы разбиты на три группы по вердикту пары, слева направо:
«возможно затронуто» (`affected`, `unclear` и незнакомые вердикты), «не
затронуто» (`not affected`, `invalid CVE`, `rejected CVE`) и «не прогнано»
(`not processed` и пары без вердикта). Над полосой — скобки групп с числом
пар и долей, как в шапке: скобка встаёт ровно над сегментами своей группы,
подпись рисуется, только если влезает, иначе уходит в легенду под полосой.
Строки под полосой идут в том же порядке, что и сегменты.

**AI** — что сказал AI и сколько прогнано. Крупно — сколько пар
прогнано из всех, рядом — доля и сколько осталось. Прогнана пара с
настоящим вердиктом; `not processed` (пара была в прогоне, но AI её не
разобрал) и пара без вердикта ещё остались. Полоса — сегмент на каждый
вердикт, затем `not processed` и серое «не прогнано». Под ней строки в
порядке `affected`, `unclear`, незнакомые значения (серым, как пришли),
`not affected`, `invalid CVE`, `rejected CVE`, `not processed` и «не
прогнано»; в каждой — пары, уверенность `high` / `medium` / `low`
(`ai_confidence`) и доля от всех пар. Пара с другой или пустой уверенностью
входит в число пар, но ни в одну из трёх колонок. В подписи — последний
прогон, самая поздняя `ai_run` в таблице.

**Remediation** — что делать по парам, по `ai_remediation`. Полоса — та же
серая часть «не прогнано», а прогнанная поделена по значениям remediation,
и в конце — `not processed`, у которого remediation нет. Remediation пары
стоит в группе её вердикта, поэтому скобки здесь той же ширины, что в
блоке AI. Внутри группы строки — пары и доля от всех, в порядке: сначала
фикс есть или готов (`backport prepared`, `vendor update available`,
`rebuild required`), потом ручная работа (`manual integration required`,
`manual remediation required`), блокеры (`upstream fix unavailable`,
`pending`), затем `not determined` и `not required`; незнакомые — следом,
«не указана» — у прогнанной пары без remediation, последней в группе.

Если колонки `ai_verdict` (для Remediation — и `ai_remediation`) в таблице
нет, блок пишет «В таблице нет данных AI», остальная страница строится как
обычно.

## Списки задач по показателям

Клик по числу или сегменту открывает окно с исходными строками выбранного
показателя. Это работает в шапке, разрезах критичности, мер, RHEL и статусов,
основаниях «Можно закрыть», компонентах, карточках разработчиков, аномалиях
и AI/remediation. Число открытых или готовых в разрезе открывает именно
открытые или готовые строки. У оснований закрытия можно отдельно открыть
взятые и невзятые задачи.

Столбики «Поступления задач» и общего графика «Разработчики» открывают все
задачи за выбранный день или неделю (Пн–Вс), независимо от цвета сегмента.
Поступление — по Task date; закрытия — расчётно закрытые задачи с назначенным
разработчиком, по End date (включая убранные с датой завершения). Личный график открывает закрытия только этого
разработчика за выбранный день. Даты позже даты отчёта исключаются, в том
числе из последней недели; пустой период открывает пустую выборку.
Столбик можно открыть кликом, касанием, Enter или пробелом; перетаскивание
для прокрутки окно не открывает.

В окне — поиск по всем полям строки (включая комментарий), сортировка по
заголовкам колонок и страницы по 50 строк. Несколько слов в поиске должны
встретиться в одной строке; регистр не важен. По умолчанию сначала высокий
CVSS; неизвестные значения при сортировке идут последними. CVE ведут на
ссылку из входной таблицы; Task ID становится ссылкой, если сам содержит
HTTP(S)-адрес. Обычный Task ID тоже становится ссылкой:
`https://portal.works.prod.sbt/swtr/units/current/unit/<task-id>`.
Видна только айдишка, полный адрес открывается по клику в новой вкладке.
Так же оформлены ссылки на основную задачу дубликата. В CSV сохраняется
исходный Task ID.

«Скачать CSV» выгружает всю найденную выборку в текущем порядке, включая
строки на других страницах. В CSV также есть даты, расчётные часы, принятая
мера, NVR, комментарий, данные AI и ссылки. Формат — UTF-8 с BOM и `;`;
ячейки, начинающиеся с символа формулы, защищены апострофом.

Единица учёта сохраняется: обычные показатели раскрывают строки таблицы,
AI/remediation — по одной строке на пару CVE + компонент с выбранным
вердиктом. Сегменты шапки показывают первое основание закрытия, строки
разреза оснований — все подходящие задачи. Подпись окна поясняет выборку.

Окно закрывается крестиком, Escape или кликом по фону. Фокус возвращается
к вызвавшему элементу; счётчики доступны через Tab, Enter и пробел.
Фон затемняется без размытия, чтобы прокрутка таблицы оставалась плавной.

## Строка разделов

Под шапкой — строка с якорями на все разделы страницы; при прокрутке она
прилипает к верху окна. У «Требует внимания», «Можно закрыть» и «Аномалий» —
бейдж с числом задач, тем же, что в самом разделе. Подсвечен раздел, чей верх
уже ушёл под строку; внизу страницы — последний; пока видна шапка — ни один.
По клику подсвечен выбранный раздел сразу. Строка занимает всю ширину окна,
якоря стоят по центру и целиком помещаются примерно с 1300 px; в окне уже
строка листается вбок, и подсвеченный якорь сам встаёт в её середину.

## Графики по времени

Дневные и недельные графики (темп, поступление, сжигание, закрытия в
карточке разработчика) показывают весь период: от первой даты в данных до
даты отчёта. Перерывы в работе на всех них заштрихованы во всю высоту поля
— той же штриховкой, что «растриажено» в шапке, по дням и на недельных
графиках тоже; по центру штриховки — подпись «перерыв», если она влезает, в
легенде — «перерыв в работе», в подсказке дня или недели — что она в темп
закрытия не идёт. После даты отчёта перерывов нет. Если период в карточку не помещается, график листается внутри
неё по горизонтали, без видимой полосы прокрутки: перетаскиванием мышью,
Shift+колесом, тачпадом или пальцем. Вертикальное колесо без Shift
прокручивает страницу как обычно.

При открытии график стоит в конце, на последних днях. При изменении ширины
окна он сохраняет расстояние до правого конца, на которое его промотал
пользователь.

Графики показывают, на что указывает курсор: на линейном графике темпа —
пунктирная направляющая дня и точки на всех линиях; в столбиках и полосах
блок под курсором остаётся ярким, соседние приглушаются (неделя целиком, день
в карточке разработчика, сегмент полосы). Подсказка с числами — как раньше.

В разрезах со строками (CVE, принятые меры, «Можно закрыть», состояние в
RHEL, статус задач, AI, Remediation) курсор на любой части строки —
названии, минибаре, числах — оставляет её яркой целиком, остальные строки
бледнеют. Строка и сегмент полосы над ней связаны: курсор на сегменте
оставляет яркими его и его строку, курсор на строке — её и её сегмент,
остальное в полосе и строках бледнеет.

## Разработка

Все команды — из каталога тулзы:

```sh
python3 -m unittest discover -s tests -v
node --test tests/js/*.test.js
python3 -m tests.example пример.xlsx
python3 -m tests.example пример.csv
```

Дополнительная проверка в Chromium (для разработки, нужен установленный
Node-пакет `playwright` и его Chromium):

```sh
node tests/browser/drilldown.cjs
node tests/browser/charts.cjs
node tests/browser/activity.cjs
node tests/browser/speed.cjs
node tests/browser/removed.cjs
```

Проверки сами создают вымышленные таблицы и HTML во временном каталоге,
проверяют состав выборок по счётчикам и графикам, поиск, сортировку, CSV,
клавиатуру, узкий экран, касание, перетаскивание и данные AI.
Путь к артефактам выводится в результате. Если Playwright установлен вне
обычного пути Node, его путь задаётся `CVESUMMARY_PLAYWRIGHT`; путь к
Chromium можно задать `CVESUMMARY_CHROMIUM`. Зависимостей при запуске самой
тулзы это не добавляет.

Первая команда запускает тесты Python, вторая (нужен Node.js) — тесты чистых
JS-модулей без браузера. Третья пишет пример таблицы на 100 вымышленных строк
(с колонками `ai_*`: примерно половина пар прогнана через AI, вердикты и
remediation — токены плагина) для ручной
проверки страницы, четвёртая — те же строки в CSV через `;`.
Страницу из примера собирает `python3 -m cvesummary пример.xlsx --as-of 2026-10-19`
(или `пример.csv`); результат открыть в браузере.

| Модуль | Назначение |
|---|---|
| `cvesummary/xlsx.py` | zip → лист → строки ячеек, типы, даты по стилю |
| `cvesummary/csvfile.py` | CSV → те же строки ячеек: кодировка, разделитель |
| `cvesummary/table.py` | шапка, колонки по именам, нормализация строк, ошибки входа |
| `cvesummary/page.py` | сборка HTML из `assets/` и JSON с данными |
| `cvesummary/cli.py` | командная строка, журнал, запись файла |
| `cvesummary/assets/js/` | роли, часы, активные периоды и личные перерывы (`activity.js`), темп и прогноз, даты, графики, строка разделов, данные AI, списки задач, отрисовка |
| `tests/`, `tests/js/` | тесты Python (`unittest`) и JS (`node --test`) |

Python отдаёт странице нормализованные строки, все расчёты делает JS.
