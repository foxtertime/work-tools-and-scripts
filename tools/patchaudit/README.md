# patchaudit

Подсказывает, какие CVE-патчи потеряли актуальность при обновлении RPM.
Находит последний билд пакета в Koji-теге, читает `PATCH` **текущей ветки**
из `extra.source.original_url` этого билда, для CVE из имён файлов
запрашивает Red Hat CSAF/VEX и пишет JSON. Патчи не удаляет.

**Версия:** 1.0.0, источник номера — `patchaudit/__init__.py` и `--version`.
История — [CHANGELOG.md](CHANGELOG.md), задачи — [TODO.md](TODO.md).

## Два режима

1. `--package NAME`: показать, для каких патчей Red Hat уже выпустил фикс
   и до каких версий нужно обновиться. Решение `fixed` означает, что
   патч может потерять актуальность при таком обновлении; текущий билд
   с версией фикса в этом режиме не сравнивается.
2. `--nvr NAME-VERSION-RELEASE`: NVR — **целевая версия обновления**.
   Тулза по-прежнему ищет последний билд по имени в теге. Если цель
   включает фикс, патч получает `remove`; если цель старше фикса —
   `remove_on_upgrade`, а версия следующего обновления видна в `fixes`.
   Целевому NVR не обязательно существовать в Koji.

## Требования и запуск

- Python 3.9+; `koji` — системный `python3-koji` или `pip install koji`.
- PyYAML нужен только с YAML-конфигом: `python3-pyyaml` или `pip install pyyaml`.
- Доступ к Koji, GitLab REST v4 и `https://security.access.redhat.com`.
  Все запросы — на чтение.
- Для закрытого GitLab нужен токен с правом `read_api` в поле `gitlab.token`
  YAML-конфига; токен в JSON и журнал не попадает.

Из каталога этой тулзы, без установки:

```bash
# Все доступные исправления для CVE-патчей текущей ветки
python3 -m patchaudit --package vim --tag sl9-updates --rhel 9 \
    --koji-url https://koji.example.com/kojihub \
    --gitlab-url https://gitlab.example.com -o vim-fixes.json

# Что можно убрать при обновлении до конкретной версии Red Hat
python3 -m patchaudit --nvr vim-8.2.2637-26.el9_8 --tag sl9-updates --rhel 9 \
    --koji-url https://koji.example.com/kojihub \
    --gitlab-url https://gitlab.example.com -o vim-upgrade.json

# Основные настройки уже в YAML
python3 -m patchaudit --config patchaudit.yaml --package vim
python3 -m patchaudit --config patchaudit.yaml --nvr vim-8.2.2637-26.el9_8

# Свой SL-релиз: для сравнения 26.sl9_8^3 соответствует 26.el9_8
python3 -m patchaudit --config patchaudit.yaml --nvr vim-8.2.2637-26.sl9_8^3
```

Без `-o` JSON идёт в stdout, журнал — в stderr. Существующий выходной файл
заменяется атомарно: фатальный сбой не испортит прежний отчёт. Символическая
ссылка и права существующего файла сохраняются.

Можно установить команду `patchaudit`:

```bash
pip install --no-build-isolation -e .
patchaudit --version
```

## Настройки

Шаблон — [patchaudit.example.yaml](patchaudit.example.yaml).
Путь к конфигу: `--config` или `PATCHAUDIT_CONFIG`. Флаг главнее конфига.

Токен задаётся значением в конфиге:

```yaml
gitlab:
  token: "glpat-your-token"
  hosts:
    gitlab.example.com:
      api: https://gitlab.example.com/api/v4
```

Пробелы по краям обрезаются. Отсутствующее поле, `null`, пустая или
пробельная строка означают запросы без токена. Нестроковое значение — ошибка.
С версии 1.0.0 токены из env не читаются: замените `gitlab.token_env`
на `gitlab.token` и запишите сам токен вместо имени переменной.
`PATCHAUDIT_CONFIG` по-прежнему задаёт путь к файлу.

| Флаг | Назначение |
| --- | --- |
| `--package`, `--nvr` | ровно один из двух входов |
| `--koji-url`, `--tag` | хаб и тег; в конфиге `koji.hub`, `koji.tag` |
| `--rhel` | точная версия RHEL; в конфиге `rhel` |
| `--gitlab-url` | сервер или адрес API v4; иначе обязательна секция `gitlab` |
| `--patch-dir` | каталог патчей; иначе `gitlab.patch_dir` или `PATCH` |
| `--stream` | явный стрим VEX; иначе `vex_streams` для пакета и точной версии RHEL |
| `--vex-name` | дополнительное имя пакета в VEX; флаг можно повторять, он заменяет `vex_names` пакета |
| `-o`, `--output` | JSON-файл; `-` и значение по умолчанию — stdout |
| `--log-level` | `error`, `warning`, `info`, `debug`; по умолчанию `info` |

Секции `koji`, `rhel`, `gitlab`, `vex`, `vex_streams`, `vex_names` можно
перенести из конфига vulnsheet. Его секцию `ranges` переносить не нужно.
`gitlab.jobs` принимается для совместимости, но каталог здесь один, поэтому
параллельность настраивается только для загрузки CVE (`vex.jobs`).

Кэш VEX — `$XDG_CACHE_HOME/patchaudit` или `~/.cache/patchaudit`, TTL — час.
`vex.cache_dir`, `cache_ttl`, `jobs`, `retries`, `timeout` меняют это;
`cache_ttl: 0` заставляет перечитывать документы из сети.

## Формат результата

Примеры полного JSON на условных данных: [по целевому NVR](examples/result.json)
и [по имени пакета](examples/result-package.json).

`format: 1`. В `request` — режим, пакет, цель, тег, RHEL, stream и aliases;
`latest_build` — NVR, по которому найдена ветка; `source` — host, project,
branch; `patch_directory` — путь и наличие каталога (`null`, если не выяснено).

`cves` содержит по одной записи на уникальную CVE:

```json
{
  "cve": "CVE-2026-1000",
  "status": "Fixed",
  "vex_url": "https://security.access.redhat.com/data/csaf/v2/vex/2026/cve-2026-1000.json",
  "fixes": [
    {
      "nvr": "vim-8.2.2637-26.el9_8",
      "fix_date": "2026-10-01",
      "advisory_url": "https://access.redhat.com/errata/RHSA-2026:1234",
      "products": ["cpe:/a:redhat:enterprise_linux:9::appstream|vim||x86_64"]
    }
  ],
  "action": "remove",
  "reason": "target_includes_redhat_fix",
  "fixed_in_target": [
    {
      "nvr": "vim-8.2.2637-26.el9_8",
      "fix_date": "2026-10-01",
      "advisory_url": "https://access.redhat.com/errata/RHSA-2026:1234",
      "products": ["cpe:/a:redhat:enterprise_linux:9::appstream|vim||x86_64"]
    }
  ],
  "fixed_after_target": []
}
```

Это иллюстрация формата, идентификаторы и даты в примере условные.
`fixes` перечисляет все подходящие исправленные NVR, которые есть в VEX,
с их собственными errata и датами. Для одного NVR берётся самая ранняя
указанная дата `vendor_fix`; неизвестные дата/ссылка — `null`.
`products` — устойчивые ключи покрытия (CPE, имя пакета, stream,
архитектура, разделённые `|`): фикс должен покрывать каждую подходящую
группу. Более поздний фикс другого бинарного пакета не скрывается ранним
фиксом первого. Если у Fixed-продукта в VEX нет версии, `nvr` — `null`,
а решение — `review`. В режиме имени оба списка сравнения пусты.

`patches` связывает решения с файлами:

```json
[
  {
    "path": "PATCH/vim-CVE-2026-1000.patch",
    "cves": ["CVE-2026-1000"],
    "action": "remove"
  }
]
```

| `action` | Значение |
| --- | --- |
| `fixed` | Red Hat выпустил фикс; режим имени, конкретная цель ещё не выбрана |
| `remove` | целевой NVR включает фикс Red Hat |
| `remove_on_upgrade` | целевой NVR старше фикса, потребуется дальнейшее обновление |
| `keep` | CVE ещё не исправлена, фикс отложен/не планируется либо идёт исследование |
| `review` | данных для рекомендации недостаточно или нужна ручная проверка |

Если в одном файле несколько CVE, удалить его рекомендуется только при
исправлении всех. Для смешанных решений приоритет: `keep`, `review`,
`remove_on_upgrade`, `fixed`, `remove`. CVE ищутся в **имени файла**, без
чтения его содержимого, включая сокращение `CVE-2026-1000-2000`.
Файлы без CVE попадают в `ignored_files`. В `summary` — число CVE,
патчей и решений по файлам. `problems` описывает сбои по этапам;
`complete` показывает, удалось ли выполнить весь сбор данных.

## Правила и границы проверки

- RHEL сравнивается точно: `9`, `9.2` и `10` — разные продукты; без
  заданного стрима не используются модульные версии. Бинарные имена
  задаются через `vex_names`. При конфликте статусов побеждает более опасный.
- `Fixed` в другой версии RHEL, модуле или надстройке вроде Fast Datapath
  не даёт основания удалить патч.
- Сравниваются `Version` и `Release` по правилам RPM, включая бэкпорты,
  `~` и `^`. Эпоха не входит в NVR; при изменении эпохи требуется ручная
  проверка. Цель задаётся без эпохи, архитектуры и `.rpm`.
- Автоматическое сравнение поддерживает обычные Red Hat release
  `N.el9_6.M` и модульные `N.module+el9.5.0+ID+HASH` (также `module_el`),
  внутри одного семейства и major RHEL. В целевом release `sl` преобразуется
  в `el`, а конечный суффикс пересборки `^<номер>` отрезается: например,
  `26.sl9_8^123` сравнивается как `26.el9_8`. Правило работает и для модульных
  SL-релизов. Имя пакета, upstream-версия и исходный NVR в JSON сохраняются.
  `.custom`, неподдерживаемые формы release и разные major получают `review`.
  В режиме имени эти метки не мешают получить список исправлений Red Hat.
- `Not affected`, отсутствие записи или компонента в VEX — `review`,
  поскольку это не доказательство включения фикса в ваш пакет.
- Ветка берётся из источника последнего билда; её текущее содержимое может
  отличаться от коммита сборки. Если известен только коммит или SRPM,
  тулза сообщает проблему, не угадывает ветку.
- Это рекомендации по версии Red Hat. Применимость конкретного патча,
  локальные изменения и содержимое обновлённого SRPM проверяет разработчик.

## Коды выхода и разработка

| Код | Смысл |
| --- | --- |
| `0` | JSON записан, источники проверены; пустой PATCH, нет CVE или нет VEX-записи — нормальные ответы |
| `1` | JSON записан, но сбор неполон: сбой VEX/GitLab, нет билда/деталей либо невозможно определить ветку |
| `2` | неверный вход/конфиг, недоступен хаб, неизвестен тег, нет зависимости либо выход не пишется |

Неопределённый вердикт `review` сам по себе не делает отчёт неполным:
`complete` относится к доступности источников.

```bash
python3 -m unittest discover -s tests -v
```

Клиенты Koji/GitLab/HTTP/VEX, конфиг, разбор source URL/CVE и rpmvercmp
перенесены из vulnsheet самостоятельными копиями с офлайн-тестами.
Отдельные `audit.py`, `decisions.py`, `cli.py` связывают их в эту тулзу.
