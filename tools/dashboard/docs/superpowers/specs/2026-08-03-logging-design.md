# Логирование kojipatch

Дата: 2026-08-03

## Задача

Сейчас в проекте нет логирования. Весь вывод — двенадцать прямых
`sys.stderr.write` в `kojipatch/cli.py`; библиотечные модули (`collect`,
`kojiclient`, `gitlabclient`, `render`) молчат. Следствия проявились на первом
же боевом прогоне: GitLab отвечал `404 invalid revision or path Not Found` на
каждый репозиторий без каталога `PATCH`, но увидеть это удалось только по
симптому в дашборде — в логе не было ни запроса, ни ответа.

Логирование должно решать две задачи, названные заказчиком:

1. **Разбор полётов по боевому прогону** — видеть каждый запрос к GitLab и koji:
   адрес, параметры, код ответа, тело при ошибке, длительность, номер попытки.
2. **Наблюдение за долгим прогоном** — на 800 билдах понимать, где сбор сейчас
   и не завис ли он.

## Решения

| Вопрос | Решение |
|---|---|
| Куда пишем | stderr; файл и JSON не нужны — хватает `2>run.log` |
| Управление подробностью | только `--log-level {error,warning,info,debug}`, по умолчанию `info` |
| Судьба `-v/--verbose` | удаляется полностью, вместе со своей логикой трейсбека |
| Прогресс | `\r`-строка удаляется; периодические обычные строки |

Отказ от `\r` осознан: перерисовываемая строка не грепается, а в
перенаправленном выводе превращается в кашу из управляющих символов. Живой
счётчик заменяется строкой примерно каждые 5% работы.

## Архитектура

Библиотека логирование **не настраивает**, только пишет:

- каждый модуль заводит `logger = logging.getLogger(__name__)`;
- `kojipatch/__init__.py` вешает `logging.NullHandler()` на логгер `kojipatch`,
  чтобы импорт пакета из чужого кода не сыпал в чужой вывод и не вызывал
  `No handlers could be found`;
- настраивает единственное место — `kojipatch/cli.py`, вызовом
  `logs.configure(...)` сразу после разбора аргументов.

### `kojipatch/logs.py`

```python
LEVELS = {"error": ERROR, "warning": WARNING, "info": INFO, "debug": DEBUG}
DEFAULT_LEVEL = "info"

def configure(level: str, stream=None) -> None
```

`configure` ставит на логгер `kojipatch` один `StreamHandler` (по умолчанию
`sys.stderr`), выставляет уровень и формат, и снимает ранее поставленные
хендлеры, чтобы повторный вызов в тестах не дублировал строки. Имя логгера в
сообщении печатается коротким — без префикса `kojipatch.`.

Форматы различаются по уровню, потому что при `--jobs 8` дебажный лог без имени
потока нечитаем:

```
info и выше:  20:41:02 INFO  collect: os-9.2: 400/800 (50%), 9 проблемных
debug:        20:41:02 DEBUG [w_0] gitlab: GET .../tree ref=c9s path=PATCH → 404 за 0.12 с
```

## Уровни

**ERROR** — фатальное, прогон на этом заканчивается: нечитаемый или невалидный
конфиг, недоступный koji-хаб, ошибка записи выходного файла, нечитаемый
снапшот. Код возврата 2.

**WARNING** — то, что не останавливает прогон, но требует внимания, и пишется
**в момент возникновения**, а не постфактум:

- проблема по билду, с именем компонента: `nginx: gitlab: ref not found`,
  `curl: no source url`, `rpm-ostree: internal error: ...`;
- ретрай запроса к GitLab после `429`/`5xx`, с указанием паузы;
- фолбэк клиента koji на последовательные вызовы;
- превышение порога `--max-problems`.

**INFO** (по умолчанию) — ход работы: параметры запуска (хаб, список тегов,
`--jobs`, задан ли токен — сам токен не печатается никогда), число билдов в
теге, периодический прогресс, итог по тегу, имя записанного файла, общее время
прогона.

**DEBUG** — то, ради чего всё затевается:

- каждый HTTP-запрос к GitLab: метод, URL, `ref` и `path`, код ответа,
  длительность, номер попытки; при коде ≥ 400 дополнительно тело ответа,
  обрезанное до 200 символов;
- вызовы koji: имя метода, размер пачки, длительность;
- попадания в кэш мемоизации `(host, project, ref)`;
- трейсбеки фатальных ошибок — `logger.debug(..., exc_info=True)`, а не
  `logger.exception`: пользователю нужна одна строка ERROR, а трейсбек должен
  появляться только тогда, когда его попросили уровнем.

## Прогресс

`collect_tag` больше не принимает параметр `progress`: механизм остаётся один —
логирование. Строка пишется на уровне INFO каждые `max(1, total // 20)`
обработанных билдов и обязательно на последнем, то есть примерно двадцать строк
за прогон независимо от размера тега:

```
os-9.2: 400/800 (50%), 9 проблемных, 12.3 билда/с, ~32 с осталось
```

Счётчик уже защищён блокировкой (`collect.py`), она сохраняется: с неё теперь
читается и значение для строки лога.

Пул потоков создаётся с `thread_name_prefix="w"`, иначе в дебажном логе вместо
`[w_0]` будет `[ThreadPoolExecutor-0_0]` и строка перестанет читаться
(`ThreadPoolExecutor` склеивает имя как `<префикс>_<номер>`).

Оценка остатка считается от прошедшего времени через `time.monotonic()`.
Тесты проверяют факт и шаг появления строк, а не значение оценки.

## Что логирует каждый модуль

| Модуль | Что пишет |
|---|---|
| `cli` | INFO: параметры прогона, записанные файлы, общее время. ERROR: фатальные ошибки. DEBUG: трейсбек. WARNING: превышение `--max-problems` |
| `collect` | INFO: старт тега, число билдов, прогресс, итог. WARNING: каждая проблема билда с именем компонента |
| `gitlabclient` | DEBUG: каждый запрос и его результат, попадания в кэш. WARNING: ретраи |
| `kojiclient` | DEBUG: вызовы с размером пачки и таймингом. WARNING: фолбэк на последовательный режим |
| `render`, `diff` | DEBUG: сколько строк и пар построено |

## Гигиена секретов

Токен GitLab не должен попадать в лог ни на одном уровне. Логируются URL и
параметры запроса; заголовки не логируются вовсе. На это заводится отдельный
тест: прогон с токеном на уровне `debug`, проверка, что ни значение токена, ни
строка `PRIVATE-TOKEN` в выводе не встречаются. Такие утечки происходят молча,
поэтому проверка автоматическая, а не «мы аккуратные».

## Совместимость

`-v/--verbose` удаляется. Команды со старым флагом упадут с ошибкой argparse —
это осознанный выбор заказчика в пользу единственного явного способа. README и
тесты CLI правятся соответственно.

Поведение по умолчанию меняется: раньше без флагов печатались только итог по
тегу и имя файла, теперь на уровне `info` добавляется ход сбора. Кому нужно
прежнее молчание — `--log-level warning`.

Вместе с параметром `progress` уходят два теста в `tests/test_collect.py`
(`test_progress_callback_is_called`, `test_progress_reaches_total_under_concurrency`):
они переписываются на `assertLogs`, проверяя то же самое — что счётчик доходит
до общего числа и что при `jobs > 1` он не теряет инкрементов.

## Тестирование

Через `unittest.assertLogs`, без сети, на существующих подделках из
`tests/fakes.py`:

- `429` пишет WARNING с указанием паузы;
- проблема билда пишется WARNING в момент возникновения и содержит имя
  компонента;
- на уровне `info` записи о запросах не появляются, на `debug` появляются;
- ни на одном уровне в выводе нет ни токена, ни строки `PRIVATE-TOKEN`;
- шаг прогресса считается от размера тега: на 40 билдах строк прогресса 20;
- `configure` при повторном вызове не дублирует хендлеры;
- `--log-level` с неизвестным значением даёт ошибку argparse, а не падение;
- фатальная ошибка пишет ERROR, а трейсбек — только на `debug`.

## Вне объёма

- запись в файл (`--log-file`), ротация;
- JSON-формат для сборщиков логов;
- логирование в `model`, `classify`, `sourceurl`, `rpmvercmp` — это чистые
  функции, их поведение полностью раскрывается тестами.
