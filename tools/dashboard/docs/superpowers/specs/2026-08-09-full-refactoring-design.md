# Полный рефакторинг

**Дата:** 2026-08-09

## Задача

Три выпуска подряд наращивали смысл, и наросло не только его. Аудит всего
производственного кода — тринадцать модулей Python и двадцать JS — нашёл
долг трёх разных пород, и мешать их в одну работу нельзя: у каждой свой
способ проверки.

**Разрезание** — три файла доросли до размера, на котором их перестаёшь
держать в голове целиком. **Схлопывание** — шесть мест, где одно правило
записано дважды. **Уборка** — мёртвое, устаревшее и одно место про будущий
Python.

Сразу оговорка, задающая тон всей работе: кодовая база в хорошем
состоянии. Границы модулей честные, каждое неочевидное решение объяснено
там, где его принимали, DOM не течёт за пределы `ui.js`. Это долг зрелого
кода, а не аварийная уборка, и правки должны выглядеть соответственно:
ничего не переписывается «заодно», ни один комментарий не пропадает.

Одно исключение из «поведение не меняется» — колонка «Δ патчей», см.
раздел «Три исхода в колонке».

## Что не трогаем — и почему

Это часть замысла, а не умолчание.

**Блок имён снапшотов и диапазонов в `page.js`** (`snapKey`,
`snapIndexByKey`, `snapNamed`, `lastEndsNamed`, `endsFromName`,
`currentEnds`, `pairKey` — около восьмидесяти строк) выглядит готовым
модулем и им не является: он весь замкнут на `SNAPS`, то есть на само
состояние страницы. Вынести его можно только протащив массив доводом в
каждую функцию или заведя фабрику с обратным вызовом. В обоих случаях кода
станет больше, а понятнее не станет.

**Сводка дашборда** не трогается ничем из этой работы.

**Формат снапшота** остаётся `SCHEMA = 1`, и ни одно поле модели не
меняется. Форма данных страницы тоже прежняя: `patches_rewritten` лежит там
с 2.3.0.

## Пять новых модулей

Все — в том же виде, в каком уже написаны `rail`, `files`, `tips`,
`toasts`, `filters`: UMD-обёртка, `create(deps)`, свои узлы и свои
слушатели, наружу минимум. Исключение — `search.js`: он ничем не владеет и
остаётся простым модулем без фабрики, как `text.js` и `rpms.js`.

Договоры, чтобы их не пришлось угадывать:

```js
copy.create({ button, rowsOf })          // rowsOf() → массив самих строк,
                                         // уже отсортированных и отфильтрованных,
                                         // а не пар {row, open}
viewport.create({ controls, toTop, onResize })
address.create({ page, hash, dom: { search, clear }, onExternal })
notices.create({ store, toasts })
```

`copy.js` получает строки не сам: разворачивать пары `{row, open}` — дело
корня, который их и завёл. Знать про `page` копированию незачем — оно
превращает список строк в текст и кладёт его в буфер.

`viewport.js` не знает про карточки: пересчёт их ширины приходит доводом
`onResize`, потому что мерить раскладку умеет только тот, у кого есть узлы
рядов.

`notices.js` не рисует рельс. Сегодняшняя `renderSources` делает два дела
сразу, и в корне от неё остаётся ровно это:

```js
function renderSources() {
  rail.render();
  notices.sync();
}
```

`address.js` и `hash.js` — не одно и то же, и в шапке нового модуля это
будет сказано прямо: `hash.js` знает **формат** строки и не знает про
страницу, `address.js` владеет самим `location.hash` и решает, **когда**
его читать и писать. Разделение существует и сегодня, просто вторая
половина размазана по корню. Слушатель `hashchange` переезжает вместе с
`hashLock`: замок нужен ровно затем, чтобы отличить собственную запись от
чужой, и держать замок в одном месте, а его единственного читателя — в
другом значит приглашать расхождение. Ссылка, приехавшая снаружи,
возвращается в корень обратным вызовом `onExternal`.

## `_attach_patches` — четыре фазы четырьмя функциями

Девяносто девять строк с четырьмя последовательными фазами, каждая из
которых выходит из функции своим `return`, — единственное место в проекте,
где при чтении теряется нить. Тело становится оглавлением:

```python
def _attach_patches(build, info, gitlab_client, classifier,
                    branch_check: bool = True) -> None:
    parsed = _parse_source(build, info)
    if parsed is None:
        return                      # читать нечего, причина уже записана
    commit = _describe_source(build, info, parsed, gitlab_client)
    ref, tree = _collect_patches(build, gitlab_client, parsed, commit,
                                 classifier)
    if ref != commit:
        # откат на ветку: коммита в репозитории нет, и точка отсчёта
        # пропала вместе с ним
        commit = None
    if branch_check and commit and parsed.ref_kind == "branch":
        _branch_drift(build, gitlab_client, parsed, commit, tree, classifier)
```

Договоры помощников:

**`_parse_source(build, info) -> Optional[ParsedSource]`** — разбирает
источник настолько, чтобы было что читать. `None` значит «дальше идти
незачем, причина уже записана в билд», и покрывает все три сегодняшних
случая: нет `original_url`, URL не разобрался, сборка из готового SRPM. Три
разбросанных ранних выхода становятся одним договором.

**`_describe_source(build, info, parsed, gitlab_client) -> Optional[str]`**
— заполняет `build.source` целиком и возвращает хеш коммита сборки.

**`_collect_patches(build, gitlab_client, parsed, commit, classifier) ->
Tuple[str, TreeResult]`** — читает дерево патчей и записывает
`patches_ref`, `patch_dir_present`, `patches` и проблему чтения. Возвращает
ref, с которого дерево снято, и сам результат: он нужен снаружи, чтобы
посчитать ghost-и. `_read_patch_dir` остаётся как есть — он уже отдельная
функция со своим договором.

**`_branch_drift(build, gitlab_client, parsed, commit, tree, classifier)`**
— сравнение с веткой: `compare`, `branch_head`, `commits_ahead` и ghost-и,
вместе со всей охраной вокруг `tree.present is None`. Условие «есть ли
вообще что сравнивать» остаётся снаружи, в теле: оно про то, звать ли эту
фазу, а не про то, как она устроена.

**Все существующие комментарии переезжают целиком.** Они объясняют не
строки, а решения — почему суффикс, а не равенство; почему
`commits_ahead` не трогается при непрочитанном дереве; почему у сборки с
коммита откатываться некуда, — и решения не меняются ни одно.

**Параметр `cfg` исчезает.** Он не используется ни в одной строке тела;
зовут функцию из единственного места — `handle` в `collect_tag`.

## Один источник правила «переписан»

Сегодня вердикт «путь тот же, содержимое другое» вычисляется дважды:
`diff.js:rewritten()` считает `patches_rewritten` для метки и карточки, а
`markup.js:223` выводит тот же вердикт заново, чтобы покрасить строку.
Правило одно, записей две, слои разные, имена разные — и оговорка про
молчание при неизвестном sha живёт в обеих. Изменись правило, вторую запись
забудут: она не называется словом «rewritten» и лежит этажом ниже.

`patchesChangeHtml` перестаёт выводить вердикт и начинает его **принимать**:

```js
patchesChangeHtml(oldPatches, newPatches, rewritten, q)
```

`rewritten` — список путей, тот самый `row.patches_rewritten`; передаёт его
`tables.diffDetail`. Читается через `|| []` по той же причине, что и
`row.ghosts` рядом: данные страницы приходят из файла, который выбрал
человек.

Дубль исчезает не выносом общей функции, а тем, что нижний слой перестаёт
знать правило, которое ему знать незачем. Разметка красит то, что ей
сказали, — как она уже поступает с «пришёл» и «ушёл».

Побочно у поля `row.patches_rewritten`, которое с 2.3.0 писалось и не
читалось никем, появляется первый читатель.

## Три исхода в колонке

Единственное видимое изменение всей работы.

Колонка «Δ патчей» считает пришедшие и ушедшие файлы; переписанный патч в
ней не виден никак. Компонент, у которого переписан единственный CVE-патч,
стоит в колонке с прочерком и по ней же сортируется вниз — то есть ровно
тот случай, ради которого 2.3.0 и делалась, из этой колонки не читается.

`markup.delta` получает третий довод:

```js
function delta(added, removed, rewritten) {
  if (!added && !removed && !rewritten) return '<span class="zero">—</span>';
  return (added ? `<span class="plus">+${added}</span> ` : '')
       + (removed ? `<span class="minus">−${removed}</span>` : '')
       + (rewritten ? `${removed ? ' ' : ''}<span class="tilde">~${rewritten}</span>`
                    : '');
}
```

Третья часть **строго дописывается**: при вызове с двумя доводами разметка
обязана получиться байт в байт прежней. Это не педантизм — той же функцией
рисуется колонка Δ RPM, где третьего исхода не бывает и не будет.

Цвет — `--major`, тот же янтарный, которым уже покрашены `.is-rewritten` в
списке «стало», «сменил ветку» и «ветка +N». Новой легенды не заводится:
на этой странице янтарный значит «разъехалось, но ничего не потеряно», и
переписанный патч — ровно этот случай. В `table.css` появляется `.tilde`
рядом с `.plus` и `.minus`.

Сортировка по колонке (`page.sortValue`, ключ `dpatch`) считает сумму трёх.
Подсказка на заголовке переписывается: сейчас она обещает «пришло и ушло»,
и обещание перестало бы быть правдой.

Колонка Δ RPM остаётся двухзначной.

## Пять оставшихся дублей

**Обход списка патчей в поиске.** В `scanState` цикл по патчам билда и цикл
по ghost-патчам — побайтово одно тело, отличается только массивом; в
`scanDiff` тот же обход написан в третий раз, через список из двух списков.
Одна функция «есть ли совпадение в этом списке патчей» на все три места.
Раннего выхода она не теряет: сегодняшние `!deep &&` в условии цикла и
`||` в вызовах останавливаются одинаково.

**Выбор строк текущей вкладки.** Две строки про `curPair()/curSnap()` и
`host.rows/host.builds` стоят в `page.js` четырежды — в `filterCounts`,
`knownFilter`, `visibleRows` и `totalRows`. Один `rowsOf(tab)`.

**Сторона билда в `viewmodel.diffRow`.** Около тридцати строк вида
`old ? orNull(old.x) : null` и те же тридцать для `fresh`. Заводится
`sideOf(build, tag, kojiWeb)`, считающая десять значений одной стороны со
всей их охраной от `null`.

Перечисление двадцати полей `old_x`/`new_x` в теле `diffRow` при этом
**остаётся явным**, а не собирается приписыванием приставки в цикле.
Дублируется здесь не перечисление, а правило вывода каждого значения; форма
строки — это договор с дашбордом, и её надо уметь найти поиском по
`old_project`. Эталон `page-data.golden.json` сверяется через
`deepStrictEqual` по разобранным объектам, так что порядок ключей свободен —
но свобода порядка не повод прятать сам список.

Что эталон и правда сторожит — это `null` против отсутствующего ключа:
данные прогоняются через `JSON.stringify`/`JSON.parse`, и `undefined`
превращается в пропавший ключ, расходящийся с `null` эталона. Дисциплина
`orNull` в `sideOf` обязана уцелеть вся до последнего поля.

**Мемоизация в `GitlabClient`.** Проверить кэш под локом, сходить, положить
под локом — написано дважды, в `patch_files` и в `compare`. Один
`_cached(key, note, compute)`.

Строка лога обязана остаться прежней, поэтому пояснение приходит уже
собранным: `"%s %s@%s" % (host, project, ref)` и
`"сравнение %s %s %s..%s" % (...)`. Цена — форматирование перестаёт быть
ленивым и происходит даже на уровне INFO, где строка никуда не уйдёт. На
теге в восемьсот билдов это порядка полутора тысяч склеек коротких строк за
прогон; на фоне самих запросов в GitLab незаметно, и платить её честнее,
чем городить передачу шаблона с доводами.

**Постройка `TreeResult`.** Кортеж собирается в одиннадцати местах
позиционно, и в восьми из них это `TreeResult(None, [], причина, {})`.
Заводится `_tree_problem(причина)`. Это не косметика: в 2.2.0 добавление
поля `blobs` стоило правки одиннадцати мест, и следующее поле будет стоить
того же.

## Тесты

**Ни один тест не удаляется без замены.**

Тесты выделенного поведения **переезжают** в файлы новых модулей: там они
обходятся без полного стука DOM и проверяют предмет, а не его окружение. В
`ui.test.js` (сейчас 1988 строк) остаётся то, что и правда проверяет связку
корня — «адрес пишется после рендера», «карточки не перерисовываются на
каждое нажатие клавиши». Тест, который проверяет и то и другое сразу,
делится, а не переезжает целиком.

Новые файлы: `tests/js/copy.test.js`, `viewport.test.js`,
`address.test.js`, `notices.test.js`, `search.test.js`.

Для схлопывания дублей правило строже обычного: **правка, которая ничего не
меняет, обязана оставить сюиту зелёной без единой правки теста.**
Понадобилось поправить тест — значит поведение всё-таки поехало, и это
находка, а не помеха.

Что проверяется сверх переезда:

**`test_collect`** — у `_attach_patches` после разрезания та же наружность:
билд без URL, билд с неразбираемым URL, сборка из SRPM, откат на ветку,
непрочитанное дерево при ушедшей вперёд ветке. Все эти случаи в сюите уже
есть; задача — убедиться, что ни один не потребовал правки.

**`test_gitlabclient`** — кэш отдаёт тот же объект и пишет ту же строку
лога; `_tree_problem` даёт кортеж, неотличимый от собранного вручную.

**`tests/js/markup.test.js`** — `patchesChangeHtml` красит по
переданному списку, а не по собственному выводу: патч с разными sha,
которого нет в списке, остаётся непомеченным, и наоборот. Это и есть
проверка того, что правило переехало, а не размножилось.

**`tests/js/markup.test.js`** — `delta` с двумя доводами даёт ровно ту же
строку, что и раньше, во всех четырёх сочетаниях нулей; с тремя —
дописывает янтарный `~N` и разделители в нужных местах.

**`tests/js/tables.test.js`** — колонка «Δ патчей» показывает три исхода;
колонка Δ RPM — два.

**`tests/js/page.test.js`** — сортировка по `dpatch` считает сумму трёх.

**`tests/js/search.test.js`** — совпадение в патчах билда, в ghost-патчах и
в обеих сторонах диффа; в каждом случае строка не просто остаётся в выдаче,
а разворачивается.

Обе сюиты зелёные после каждой задачи:

```
python3 -m unittest discover -s tests
node --test tests/js/*.test.js
```

Точка отсчёта: 359 тестов Python, 501 JS.

## Порядок

Разрезание, схлопывание и уборка независимы почти везде, кроме одного узла:
единый источник правила «переписан» и три исхода в колонке трогают
`markup.js`, `tables.js`, `page.js`, `cards.js`, шаблон и `table.css` — их
разумно делать подряд, пока эта часть кода в голове.

Разрезание `ui.js` идёт после уборки в нём: незачем перевозить в новый файл
устаревший комментарий.
