# Разделение данных и представления в дашборде

**Дата:** 2026-08-04

## Задача

Сейчас `kojipatch render` считает в Python весь вид — диффы, счётчики,
порядок RPM по архитектурам, сортировку меток, перевод времени в МСК — и
запекает готовый результат внутрь HTML. Чтобы посмотреть другой тег, надо
запустить сборку заново; чтобы сравнить два снапшота, надо перечислить их
в одной командной строке.

Нужно разделить: снапшот — данные, дашборд — представление. Дашборд
открывается сам по себе, в него подгружают файлы снапшотов. Загружен один —
работает вкладка «Состояние». Загружено несколько — они переключаются в
«Состоянии» и между ними включается вкладка «Изменения».

Требование «сравнить то, что человек только что подгрузил» означает, что
дифф должен считаться в браузере: взяться готовому диффу между двумя
произвольными файлами больше неоткуда. Это и есть основная работа —
перенос вычислительного слоя представления из Python в JS.

## Контракт данных

`snapshot.json` (схема 1) становится единственным форматом обмена между
сборщиком и дашбордом. В снапшот добавляется одно необязательное поле:

```json
"patch_classes": ["AUTOGEN", "CVE", "SAST", "DAST", "COVERAGE", "SPEC",
                  "CHANGELOG", "FILES"]
```

Список имён классов патчей в порядке классификатора. Сейчас он берётся из
конфига в момент отрисовки и задаёт порядок карточек классов и порядок
меток в строке. Дашборду, читающему голый снапшот, взять его больше
неоткуда.

Версия схемы не меняется. Поле необязательное — ровно как `tag_name` и
`tags` до него, и по той же причине: снапшоты, собранные прежней версией,
обязаны продолжать читаться. В снапшоте без `patch_classes` порядок
классов выводится из самих патчей по алфавиту. Это честный ответ:
конфигурационный порядок в таком файле просто не записан, и выдумывать его
нельзя.

## Что переезжает в браузер

Весь вычислительный слой представления:

| Python | JS |
|---|---|
| `rpmvercmp.py` | `assets/js/vercmp.js` |
| `rpms.py` | `assets/js/rpms.js` |
| `diff.py` | `assets/js/diff.js` |
| `render.py` (`build_page_data` и всё вокруг) | `assets/js/viewmodel.js` |

В Python остаётся то, что производит данные: `collect`, `classify`,
`config`, клиенты koji и GitLab, `model`.

Принцип, по которому проект жил до сих пор — «порядок и семантику решает
Python, JS только рисует» — сохраняется, но граница переезжает: решает не
Python, а модуль представления, и он теперь один. Важно, что решение
по-прежнему принимается в одном месте и покрыто тестами, а не размазано по
месту отрисовки.

## Файловая структура

```
kojipatch/assets/dashboard.html   разметка, стили, плейсхолдер скриптов
kojipatch/assets/js/vercmp.js     сравнение версий по правилам rpm
kojipatch/assets/js/rpms.js       архитектуры и порядок NVRA
kojipatch/assets/js/diff.js       пара, цепочка пар, выравнивание RPM
kojipatch/assets/js/viewmodel.js  строки, счётчики, метки, МСК, ссылки
kojipatch/assets/js/store.js      загруженные снапшоты: разбор, порядок
kojipatch/assets/js/ui.js         рендер таблиц, фильтры, поиск, hash
kojipatch/build.py                склейка одного HTML из шаблона и js/
```

Нынешний `dashboard.html` — 1727 строк, из них около 1300 скрипта. Он
давно перерос один файл, и разделение данных с представлением — подходящий
повод его разложить.

Каждый файл в `js/` — обычный скрипт с коротким хвостом совместимости:
`module.exports` для node, глобальный объект для браузера. Так тесты грузят
модуль напрямую, а не выковыривают функции регуляркой из HTML.

Собранный `dashboard.html` остаётся одним самодостаточным файлом: скрипты
инлайнятся при сборке. Данных внутри нет — инлайнится только код.

## Командная строка

- `collect` — без изменений, в снапшот добавляется `patch_classes`
- `dashboard -o dashboard.html` — новая команда: положить дашборд на диск
- `render` и `run` — удаляются

## Экран загрузки

Пустой дашборд показывает зону на всю ширину: «Перетащите снапшоты сюда
или выберите файлы». Вкладок и таблиц нет — показывать нечего.

После загрузки над вкладками появляется строка источников:

```
снапшоты: os-9.1 → os-9.2 → os-9.3        [добавить] [изменить]
```

Стрелки показывают направление цепочки диффов. «Изменить» раскрывает
список: у каждого снапшота время сбора, число сборок, кнопки ↑ и ↓ для
перестановки и ✕ для удаления. Список свёрнут по умолчанию — переставляют
редко, а знать, на что смотришь, нужно всегда.

Селектор тега на вкладке «Состояние» остаётся как есть: он отвечает на
вопрос «какой снапшот сейчас в таблице», а не «что вообще загружено».
Пересечение с панелью источников осознанное — убрав селектор, мы бы
заставили переключать снапшот через панель, которая живёт над обеими
вкладками и переключением не занимается.

Загрузка работает только через выбор файлов и перетаскивание. Это
единственный способ, доступный при открытии HTML прямо с диска
(`file://`), а именно так дашборд и используют. Загрузка по URL и чтение
списка снапшотов с сервера в задачу не входят.

## Поток данных

1. Файл → `FileReader` → `JSON.parse` → проверка структуры (схема, `tag`,
   `generated`, `koji_hub`, `builds`).
2. `store` держит список загруженного. Новый снапшот встаёт на место по
   времени сбора (`generated`). Как только человек нажал ↑ или ↓, порядок
   становится ручным и автосортировка больше не вмешивается: иначе
   следующая загрузка сбросила бы расстановку.
3. Любое изменение набора или порядка вызывает один пересчёт
   `buildPageData(snapshots)`. Результат лежит в памяти; рендер таблиц
   читает готовое — ровно как сейчас читает запечённый `DATA`.
4. Выбранный снапшот и выбранная пара запоминаются именами тегов, а не
   номерами: после перестановки взгляд остаётся на том же месте.

koji-ссылки строятся по `koji_web` каждого снапшота отдельно. Сейчас
берётся общий, по первому снапшоту — при одном прогоне это безопасно, при
подгрузке файлов из разных прогонов уже нет.

Загруженное живёт только в памяти вкладки. После перезагрузки страницы
файлы выбирают заново; хранилища нет, а с ним нет и риска показать
вчерашние данные как сегодняшние.

## Ошибки

- Файл не разбирается, не похож на снапшот или несёт чужую версию схемы —
  строка ошибки рядом с именем файла в списке источников, остальные
  выбранные файлы загружаются. Одна опечатка в имени не должна отменять
  загрузку пяти.
- Один и тот же тег из разных прогонов (вчерашний и сегодняшний) — законный
  случай: грузим оба, различаем временем сбора.
- Точный дубликат (тот же тег и то же время сбора) — отклоняется с
  пояснением: иначе повторный клик по тому же файлу молча удвоил бы
  цепочку.
- Снапшоты с разных `koji_hub` — предупреждение, но не запрет. Сравнивать
  такие обычно бессмысленно, но решать это не дашборду.

## Адресная строка

Работает как сейчас: вкладка, тег, пара, фильтры, поиск, сортировка.
Данные в hash не попадают. После перезагрузки состояние восстанавливается
и применяется к снапшотам, как только их выберут заново.

## Тесты

`node --test` в `tests/js/` — node v22 в системе есть.

Тесты `test_diff.py`, `test_render.py`, `test_rpms.py` и
`test_rpmvercmp.py` переезжают в JS вместе с кодом. Тесты на `collect`,
`model`, `config`, `classify` и клиентов остаются питоновскими.

Отдельно — паритетный гейт. До удаления питоновского слоя снимается
эталон: результат `build_page_data` по фикстурам `snapshot-os-9.1.json` и
`snapshot-os-9.2.json`, сохранённый как
`tests/js/fixtures/page-data.golden.json`. JS обязан выдать ровно тот же
JSON. Питоновский код удаляется только после зелёного паритета, а эталон
остаётся в репозитории регрессионной страховкой. Без него «переписал
шестьсот строк, вроде работает» пришлось бы проверять глазами.

## Порядок миграции

Каждый шаг заканчивается зелёными тестами и коммитом.

1. `patch_classes` в снапшоте (Python, TDD). Старые снапшоты читаются
   по-прежнему.
2. Снять эталон паритета с нынешнего Python-рендера.
3. Порт ядра: `vercmp` → `rpms` → `diff` → `viewmodel`, каждый модуль со
   своими тестами; в конце — сверка с эталоном.
4. Разложить HTML: шаблон, `ui.js`, `build.py`, команда `dashboard`. Вид и
   поведение прежние, снапшоты пока вставляются в файл — чтобы сравнить
   «до» и «после».
5. `store.js` и экран загрузки. Данные приходят из выбранных файлов,
   вставка снапшотов убирается, вкладка «Изменения» включается от числа
   загруженных.
6. Удалить `render.py`, `diff.py`, `rpms.py`, `rpmvercmp.py`, их тесты и
   команды `render` и `run`.
7. Обновить README и `kojipatch.example.yaml`.

Шаг 4 стоит перед шагом 5 намеренно. Если разложение файлов и смена
источника данных попадут в один коммит, при поломке будет не видно, какое
из двух её принесло.
