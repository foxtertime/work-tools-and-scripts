# Дашборд патчей: Koji + GitLab

Дата: 2026-08-03

## Задача

Python-скрипт получает на вход один или несколько koji-тегов, собирает по каждому
тегу последние билды (с учётом наследования), для каждого билда выясняет из поля
`extra` ветку GitLab, из которой билд собран, ищет в корне этой ветки каталог
`PATCH`, классифицирует лежащие там файлы (CVE, SAST, DAST, прочее) и генерирует
самодостаточный HTML-дашборд.

Дашборд отвечает на два вопроса:

1. Какое состояние у тега сейчас — что в нём есть, из каких веток собрано, какие
   патчи наложены.
2. Что изменилось между тегами — какие патчи ушли и пришли, как изменились версии
   билдов и состав RPM внутри них.

## Ограничения и решения

| Вопрос | Решение |
|---|---|
| Доступ к живым koji/GitLab при разработке | Нет. Разработка на фикстурах, тесты офлайн |
| Классификация патчей | По имени файла, правила в конфиге |
| 3+ тега | Пары по цепочке (T1→T2, T2→T3) плюс сводная пара T1→Tn |
| Масштаб | Сотни–тысячи билдов; дисковый кэш не нужен |
| Конфигурация | Один YAML-конфиг, оверрайды флагами и env |
| Снапшоты | Раздельные шаги: collect → snapshot.json → render |
| Дизайн | Наследует `ref.html`, точечные улучшения |
| Окружение | Python 3.9, есть `koji`, `requests`, `PyYAML`; нет `jinja2`, `python-gitlab`, `pytest`, `tomllib` |

Зависимости ограничены `koji`, `requests`, `PyYAML`. Шаблонизатор — собственный
(подстановка плейсхолдеров), тесты — stdlib `unittest`.

## Архитектура

Пакет `kojipatch/`, запускается как `python -m kojipatch`.

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `cli.py` | argparse, подкоманды, коды возврата | все остальные |
| `config.py` | загрузка YAML, слияние с env и флагами, валидация | — |
| `sourceurl.py` | `original_url` → `(host, project, ref, ref_kind)` | — |
| `kojiclient.py` | список билдов тега, детали, RPM-листинги | `model` |
| `gitlabclient.py` | дерево `PATCH/` для `(host, project, ref)` | — |
| `classify.py` | имя файла → класс патча, извлечение CVE-ID | `config` |
| `collect.py` | оркестрация сбора одного тега в `Snapshot` | клиенты, `classify`, `sourceurl` |
| `model.py` | dataclass'ы, сериализация снапшота | — |
| `diff.py` | дифф пары снапшотов, цепочка, сводка | `model`, `rpmvercmp` |
| `rpmvercmp.py` | сравнение version-release по алгоритму RPM | — |
| `render.py` | снапшоты + диффы → HTML | `assets/dashboard.html` |

Границы: `sourceurl`, `classify`, `rpmvercmp`, `diff` — чистые функции без
ввода-вывода, тестируются напрямую. Клиенты принимают транспорт в конструкторе,
что позволяет подменять его в тестах. `render` не знает про сеть и получает
готовые объекты модели.

## CLI

```
kojipatch collect --tag TAG [--tag TAG2 ...] [-o snapshot.json]
kojipatch render snap1.json [snap2.json ...] -o dashboard.html
kojipatch run --tag T1 [--tag T2 ...] -o dashboard.html
```

`collect` с несколькими тегами пишет массив снапшотов в один файл. Порядок тегов
в командной строке задаёт порядок цепочки диффов и не сортируется.

Общие флаги: `--config PATH` (или `$KOJIPATCH_CONFIG`), `--koji-hub URL`,
`--gitlab-api URL`, `--patch-dir NAME`, `--jobs N` (по умолчанию 8),
`--max-problems N` (по умолчанию выключено), `-v/--verbose`.

Токен GitLab читается только из переменной окружения, имя которой задано в
конфиге (`gitlab.token_env`, по умолчанию `GITLAB_TOKEN`). Флага для токена нет:
он попал бы в историю шелла и в списки процессов. Если переменная не задана,
запросы идут анонимно — это рабочий режим для публичных репозиториев; ответы
`401`/`403` тогда попадают в `problems` конкретных билдов, а не роняют прогон.

`render` принимает один или несколько файлов; каждый файл содержит один снапшот
или их массив. Порядок цепочки — порядок аргументов, а внутри файла — порядок
элементов массива.

## Конфиг

```yaml
koji:
  hub: https://kojihub.example.com/kojihub
  web: https://kojihub.example.com/koji
gitlab:
  default_host: gitlab.example.com
  token_env: GITLAB_TOKEN
  hosts:
    gitlab.example.com:
      api: https://gitlab.example.com/api/v4
      web: https://gitlab.example.com
patch_dir: PATCH
patch_classes:
  - { name: CVE,  pattern: 'CVE-\d{4}-\d{4,}' }
  - { name: SAST, pattern: '(?i)^sast[-_]' }
  - { name: DAST, pattern: '(?i)^dast[-_]' }
  - { name: other, pattern: '.*' }
```

Правила классификации применяются по порядку, побеждает первое совпадение.
Отсутствие в конфиге хоста, встреченного в `original_url`, — не ошибка прогона:
такие билды получают запись в `problems` (`gitlab: unknown host X`).

Валидация при загрузке: обязателен `koji.hub`; каждый элемент `patch_classes`
имеет непустые `name` и компилируемый `pattern`; последний элемент должен быть
всеохватным, иначе класс патча может остаться пустым — при отсутствии такого
элемента добавляется неявный `other: '.*'`.

## Модель данных

Снапшот одного тега, `schema: 1`:

```json
{
  "schema": 1,
  "tag": "os-9.2",
  "generated": "2026-08-03T13:20:00+03:00",
  "koji_hub": "https://kojihub.example.com/kojihub",
  "koji_web": "https://kojihub.example.com/koji",
  "builds": [
    {
      "nvr": "nginx-1.24.0-3.el9",
      "name": "nginx",
      "version": "1.24.0",
      "release": "3.el9",
      "epoch": null,
      "build_id": 12345,
      "task_id": 9876,
      "owner": "builder",
      "completed": "2026-05-14",
      "source": {
        "raw": "git+ssh://git@gitlab.example.com/group/repo?#origin/br-9.2",
        "host": "gitlab.example.com",
        "project": "group/repo",
        "ref": "br-9.2",
        "ref_kind": "branch",
        "web_url": "https://gitlab.example.com/group/repo/-/tree/br-9.2"
      },
      "patch_dir_present": true,
      "patches": [
        {
          "path": "PATCH/CVE-2024-7347.patch",
          "name": "CVE-2024-7347.patch",
          "class": "CVE",
          "cves": ["CVE-2024-7347"],
          "web_url": "https://gitlab.example.com/group/repo/-/blob/br-9.2/PATCH/CVE-2024-7347.patch"
        }
      ],
      "rpms": ["nginx-1.24.0-3.el9.x86_64", "nginx-core-1.24.0-3.el9.x86_64"],
      "problems": []
    }
  ]
}
```

`source` равен `null`, если у билда нет `extra.source.original_url`.
`patch_dir_present` равен `null`, если до GitLab не удалось достучаться —
это отличается от `false` («каталога нет»). `problems` — список строк; пустой
список означает, что данные по билду полные.

## Сбор

### Koji

Анонимная `koji.ClientSession(hub)`; чтение аутентификации не требует.
`listTagged(tag, latest=True, inherit=True)` даёт актуальный список билдов тега.
Детали (`getBuild(build_id)`, откуда берётся `extra`) и списки RPM
(`listRPMs(buildID=...)`) добираются пачками через `session.multicall(batch=100)`.
Если контекстный менеджер `multicall` недоступен на старом хабе — последовательный
фолбэк с тем же интерфейсом.

`completed` берётся из `completion_time`, приводится к `YYYY-MM-DD`.

### Разбор original_url

Вход: `git+ssh://git@host/group/sub/repo?#origin/feature/x`.
Отбрасываются схема (`git+ssh`, `git+https`, `ssh`, `https`), user-info (`git@`),
суффикс `.git`, query-строка. Результат: host `host`, project `group/sub/repo`,
ref `feature/x` (префикс `origin/` снимается, внутренние слэши сохраняются).

Обрабатываемые формы:

| Вход | project | ref | ref_kind |
|---|---|---|---|
| `git+ssh://git@h/g/r?#origin/br` | `g/r` | `br` | branch |
| `git+https://h/g/r.git#br` | `g/r` | `br` | branch |
| `git+ssh://git@h/g/sub/r?#origin/feat/x` | `g/sub/r` | `feat/x` | branch |
| `git+ssh://git@h/g/r?#a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0` | `g/r` | sha | commit |
| `git+ssh://git@h/g/r` | `g/r` | `null` | none |
| любой неразбираемый | — | — | ошибка разбора → `problems` |

`ref_kind: commit` определяется по виду ref: 7–40 шестнадцатеричных символов.
Для дерева это ничего не меняет — GitLab принимает sha там же, где имя ветки, —
но в дашборде такой билд помечается отдельно, потому что «собран не с ветки».

### GitLab

REST v4, заголовок `PRIVATE-TOKEN`. На каждую уникальную тройку
`(host, project, ref)` — один запрос:

```
GET {api}/projects/{urlencode(project)}/repository/tree
    ?ref={ref}&path=PATCH&recursive=true&per_page=100
```

Пагинация по заголовку `x-next-page`. Ответ `404` означает, что каталога `PATCH`
нет, либо нет проекта или ветки; эти случаи различаются по телу ответа
(`message: 404 Tree Not Found` против `404 Project Not Found`) и записываются
по-разному: в первом случае `patch_dir_present: false` без проблемы, во втором —
`patch_dir_present: null` и запись в `problems`.

Результаты мемоизируются в памяти по ключу `(host, project, ref)`: в одном теге
десятки билдов часто собраны из одной ветки. Дисковый кэш не используется.

Параллелизм — `ThreadPoolExecutor(max_workers=--jobs)`, по одной
`requests.Session` на поток. На `429` и `5xx` — до 3 попыток с экспоненциальным
бэкоффом (1с, 2с, 4с), с учётом заголовка `Retry-After`, если он есть.

### Классификация патчей

Файлы (не подкаталоги) из дерева `PATCH/` классифицируются по basename первым
совпавшим правилом конфига. CVE-идентификаторы извлекаются регуляркой
`CVE-\d{4}-\d{4,}` из basename — их может быть несколько в одном имени.
Файлы во вложенных каталогах учитываются; в таблице показывается путь
относительно корня репозитория.

## Дифф

Ключ сопоставления — имя компонента (`build.name`). Для пары снапшотов (A, B)
каждому компоненту присваивается ровно один статус:

- `added` — есть в B, нет в A;
- `removed` — есть в A, нет в B;
- `unchanged` — version-release совпадают;
- `upgraded` — version-release в B больше;
- `downgraded` — version-release в B меньше.

Сравнение — собственная реализация `rpmvercmp` (алгоритм RPM: сегменты цифр и
букв, разделители, тильда как «меньше всего»). Epoch учитывается, если задан в
обоих снапшотах. Причина отказа от `rpm.labelCompare`: python-биндинги `rpm` не
гарантированы в окружении запуска, а поведение должно быть детерминированным
и покрытым тестами.

Дополнительно для компонентов, присутствующих в обоих снапшотах, считается:

- **патчи**: пришедшие и ушедшие (сравнение множеств по относительному пути),
  с разбивкой по классам;
- **RPM**: добавившиеся и убравшиеся подпакеты (по `name.arch`, без версии);
  непустая разница даёт признак `repackaged`;
- **ветка**: изменилась ли `source.ref` — признак `branch_changed`.

Признаки `repackaged`, `branch_changed` и изменения патчей ортогональны статусу:
компонент может быть `unchanged` по версии и при этом `patches+`.

Цепочка из n тегов даёт n−1 пар подряд идущих снапшотов плюс сводную пару
(первый, последний). Сводка считается сравнением крайних снапшотов, а не
суммированием шагов: компонент, который был удалён на втором шаге и вернулся на
третьем, в сводке обязан выглядеть неизменным.

## Дашборд

Один HTML-файл без внешних ресурсов: данные встроены как `var DATA = {...}`,
логика — ванильный JS. Визуальный язык наследуется от `ref.html`: те же
CSS-переменные, автоматическая тёмная тема через `prefers-color-scheme`,
карточки-счётчики, sticky-шапка таблицы, тултипы по `data-tip`, сортировка кликом
по заголовку, поиск с подсветкой совпадений, «Expand all», счётчик отфильтрованных
строк.

### Навигация

Две вкладки верхнего уровня: **Состояние** и **Изменения**. Вторая отображается
только при двух и более тегах. Состояние вида — вкладка, выбранный тег или
переход, активные фильтры, поисковый запрос, сортировка — сериализуется в hash
URL (`#state/tag=os-9.2/f=cve/q=nginx`), чтобы конкретный срез открывался по
ссылке.

### Вкладка «Состояние»

Селектор тега (при нескольких тегах). Крупные карточки: всего билдов · с PATCH ·
без PATCH · проблемных. Ниже плотный ряд карточек по классам патчей
(CVE · SAST · DAST · other), в каждой два числа: сколько билдов и сколько файлов.
Все карточки кликабельны и работают как фильтр.

Колонки таблицы: компонент · version-release · ветка · патчи (бейджи классов с
числами) · RPM · собран · теги · ссылки (koji, gitlab).

Раскрытие строки показывает: блок Koji (build id, task id, владелец, дата,
ссылки), блок GitLab (проект, ветка, ссылка на дерево), патчи, сгруппированные по
классам, каждый со ссылкой на файл и бейджами найденных CVE-ID, список RPM,
и список `problems`, если он непустой.

### Вкладка «Изменения»

Сегментированный переключатель переходов: `T1→T2`, `T2→T3`, … и отдельно
выделенный `T1→Tn (итог)`. Карточки: added · removed · upgraded · downgraded ·
unchanged · repackaged · patches+ · patches− · branch changed.

Таблица по умолчанию содержит только изменившиеся компоненты; клик по карточке
`unchanged` переключает её на компоненты, версия которых не менялась (в том числе
те, у которых изменились только патчи, RPM или ветка). Колонки: компонент · было · → ·
стало · Δ патчей (`+2 −1`) · Δ RPM (`+3 −0`) · теги · ссылки. Раскрытие строки —
две колонки «было / стало» с версией, веткой, патчами и RPM; пришедшее
подсвечивается цветом `--added`, ушедшее — `--removed`.

### Теги строк

Вычисляемые чипы, не имеющие отношения к koji-тегам.

- Состояние: `cve`, `sast`, `dast`, `other`, `no-patch`, `no-source`,
  `gitlab-error`, `from-commit` (собран не с ветки).
- Изменения: `added`, `removed`, `upgraded`, `downgraded`, `repackaged`,
  `patches+`, `patches-`, `branch-changed`.

Клик по чипу в строке добавляет его в фильтр. Активные фильтры отображаются
строкой чипов с крестиками; несколько тегов комбинируются по И.

### Поиск

Ищет по имени компонента, NVR, ветке, именам файлов патчей, CVE-ID и именам RPM.
Совпадения подсвечиваются (`--hit`). Поиск учитывает и свёрнутые детали строки:
строка, у которой совпадение только внутри раскрывающегося блока, остаётся видимой.

### Отличия от ref.html

Четыре добавления, визуальный язык не меняется: вкладки верхнего уровня,
чипы-теги строк, состояние вида в hash URL, кнопка «скопировать список NVR» для
текущего фильтра.

## Ошибки и коды возврата

Прогон завершается всегда, кроме отказа koji-хаба: без списка билдов работать не
с чем. Остальные ошибки деградируют по строкам и попадают в `problems`
конкретного билда.

| Код | Условие |
|---|---|
| 0 | Успех, в том числе с частичными проблемами |
| 1 | Проблемных билдов больше `--max-problems` |
| 2 | Фатальная ошибка: недоступен koji-хаб, нечитаемый или невалидный конфиг, нечитаемый снапшот |

В stderr печатается прогресс сбора и итоговая сводка вида
«1042 билда, 17 проблемных: 12 без source, 5 недоступных веток».

## Тестирование

Фреймворк — stdlib `unittest` (`pytest` в окружении отсутствует). Разработка по
TDD: тест, красный прогон, реализация. Сети в тестах нет.

- `sourceurl` — таблица форм URL из раздела «Разбор original_url», включая
  неразбираемый мусор.
- `rpmvercmp` — набор из спецификации RPM: `1.0` vs `1.0.1`, `1.0a` vs `1.0`,
  тильда, разные разделители, ведущие нули, epoch.
- `classify` — порядок правил, несколько CVE в одном имени, регистр, фолбэк
  в `other`.
- `kojiclient` — на fake-сессии koji, включая ветку без `multicall`.
- `gitlabclient` — на fake-транспорте: пагинация, `404 Tree Not Found` против
  `404 Project Not Found`, ретраи на `429`, мемоизация повторной тройки.
- `diff` — все пять статусов, `repackaged`, `branch_changed`, дифф патчей,
  цепочка из трёх снапшотов и корректность сводной пары, включая случай
  «ушёл и вернулся».
- `render` — HTML из фикстуры-снапшота: данные разбираются как валидный JSON,
  плейсхолдеров не осталось, последовательность `</script>` в данных экранирована.

Фикстуры (`tests/fixtures/`) написаны по формату реальных ответов koji и GitLab;
живого доступа при разработке нет. Они фиксируются как контракт: при расхождении
с реальным хабом правятся фикстура и код, а не тесты в обход них.

## Вне объёма

- Дисковый кэш ответов API.
- Чтение содержимого патчей (классификация — только по имени файла).
- Аутентификация в koji (только анонимное чтение).
- Матрица «компоненты × теги» как отдельный вид: цепочка пар покрывает
  практический сценарий; матрица добавляется, если появится реальный спрос.
