# cvereview: самостоятельная HTML-страница ревью CSV

Дата: 2026-11-14. Статус: утверждён пользователем после уточнения статусов
пула и чеклистов по принятой мере. Реализация разрешена сообщением «делай».

## Задача и выбранный интерфейс

Ревьювер проверяет решения разработчиков по CVE из таблицы процесса
`vulnsheet`. Пользователь выбрал вариант №1 из прототипов, затем уточнил его:
карточки идут одним компактным столбиком; примерно 3/4 карточки слева занимает
контекст, 1/4 справа — чеклист и кнопки решений. На узком экране чеклист
переносится под контекст. Основа визуального языка — cvesummary.

Принятый образец: `prototypes/01-cards.html`. Это визуальная и интерактивная
референсная страница, а её вымышленные строки, индексы записей, демонстрационные
адреса и прототипное хранилище не являются моделью готовой тулзы.

Пользователь уточнил, что в рабочей версии чеклист подставляется по значению
`Принятая мера`; четыре общих пункта прототипа были временной заглушкой.
Пользователь согласовал вход только CSV, обработку внутри страницы,
отдельный JSON состояния с ручной загрузкой/сохранением и дополнительное
автосохранение в браузере. Работа с выбранной папкой и автозапись соседнего
JSON обсуждались и были отклонены.

## Подходы и ограничения

Рассмотрены три подхода:

1. Python читает XLSX/CSV и генерирует HTML, как cvesummary. Позволяет взять
   существующие ридеры, требует запуска генератора после изменения таблицы.
2. Один HTML сам читает выбранный CSV. При ограничении входа CSV обходится
   без стороннего XLSX-парсера, генератора и сервера. **Выбран пользователем.**
3. Доступ к рабочей папке средствами Chrome: поиск CSV/JSON и автозапись
   состояния. Требует разрешений браузера. **Отклонён пользователем.**

Результат первой версии: `tools/cvereview/cvereview.html`, версия 0.1.0.
Файл открывается через `file://` в актуальном настольном Chrome. CSS, JS,
иконки, шрифты и лицензии встроены; загрузка CSV/JSON не отправляет данные
в сеть. Сервер, установка пакетов и Python для использования не нужны.

Исходники организованы локально в каталоге тулзы. Разрешён простой сборщик
на стандартной библиотеке Python, чтобы разработчик собирал один HTML из
читаемых CSS/JS/шаблона. Это сборка приложения при разработке, а не пребилд
пользовательской таблицы. Готовый HTML хранится в репозитории. Никаких импортов
из соседних тулз при сборке или использовании; полезные решения можно
перенести внутрь cvereview с указанием происхождения.

В первой версии не реализуются: XLSX, GitLab/Jira API, изменение исходного
CSV, совместное редактирование, доступ к папке, автозапись JSON на диск.
«Сохранить HTML со снимком данных»
обсуждалось как предложение агента; в эту версию не включается. Перенос
результатов обеспечивается CSV и JSON, а HTML остаётся универсальной тулзой.

## Рабочий процесс

1. При первом открытии — пустое состояние с «Загрузить CSV» и краткой
   инструкцией. Демонстрационные данные не подмешиваются в рабочие данные.
2. Пользователь выбирает или перетаскивает CSV; страница проверяет файл,
   показывает имя, сводку чтения, карточки и счётчики пулов.
3. «Загрузить состояние JSON» применяет явно выбранный файл к таблице.
   До загрузки CSV кнопка недоступна. Результат импорта виден в уведомлении.
4. В карточках отмечаются проверки, принимаются решения, вводятся замечания.
   Изменения автоматически кешируются в браузере.
5. «Сохранить состояние JSON» скачивает файл `<имя-CSV>.review.json` с
   текущими решениями. Страница не перезаписывает существующий файл на диске.
6. Новый CSV можно загрузить в ту же рабочую сессию; решения сопоставляются
   с обновлёнными строками. Невалидный вход не заменяет текущую работу.

Панель явно различает «сохранено в браузере» и «JSON содержит несохранённые
изменения». При недоступности/переполнении хранилища работа продолжается,
показывается сообщение о том, что нужно сохранить JSON.

## Чтение CSV

Адаптировать семантику cvesummary/csvfile.py и table.py в локальный JS-модуль:

- UTF-8 с BOM и без; при ошибке строгого UTF-8 — Windows-1251. UTF-16 и
  файлы с нулевыми байтами отклоняются с понятной ошибкой.
- Разделители `;`, `,`, табуляция: выбрать разбор, в котором найдена шапка
  с отдельной ячейкой `CVE ID`; при нескольких вариантах — самую широкую.
- Поддержать CRLF/LF/CR, кавычки, удвоенные кавычки, разделители и переводы
  строки внутри поля, завершающий разделитель и пустую последнюю строку.
  Нельзя разбирать CSV простым split по строкам/разделителю.
- Шапка — первая CSV-запись с ячейкой `CVE ID`; строки группировки выше
  шапки пропускаются. Имена колонок сравниваются без учёта регистра,
  крайних пробелов и повторов/переносов пробелов. Порядок произвольный.
- Обязательны колонки `Task ID`, `CVE ID`, `Компонент`, `Разработчик`,
  `Статус`. Остальные необязательны: отсутствие не запрещает ревью.
  Одинаковые названия колонок: первая колонка, явное предупреждение.
- Пустая строка, `-`, `—` — отсутствие значения. Но исходные поля хранятся
  отдельно и доступны в подробностях без потери пользовательского текста.
- Все 27 стандартных колонок vulnsheet и дополнительные колонки доступны
  в раскрытии. Число полей в подписи соответствует реальному входу.
- В сводке: записей прочитано, взято на ревью, исключено по статусу/роли,
  пропущено без идентификатора, отсутствующие необязательные колонки.
  Пустой валидный пул — нормальный результат.
- Пустые значения критичности/CVSS/дат отображаются нейтрально. Нераспознанная
  дата показывается исходным текстом и не ломает сортировку. Для дат учитывать
  ISO и дд.мм.гггг; исходное значение остаётся в подробностях.

Чтение файла и замена рабочей сессии атомарны: при ошибке CSV текущие данные,
решения, настройки, кеш и признак несохранённых изменений остаются прежними.

## Пул и идентичность задачи

**Состав пула — уточнён пользователем:** `Статус = Ожидает ревью` или
`Статус = Готов`, непустой `Разработчик`, разработчик не `SecOps`.
Сравнение статусов и SecOps без учёта регистра и лишних пробелов. Статус
тасктрекера `Task state` сохраняется как поле строки, но пул не определяет.
Другие статусы, включая «Убрано из эпика», в активный пул не входят.
«Готов» — статус разработчика, а не решение ревьювера: новая задача с таким
статусом начинает ревью в pending со всеми пунктами своего чеклиста в unseen,
как «Ожидает ревью».

Идентичность: тройка `[Task ID, CVE ID, Компонент]`. Ключ сериализуется как
JSON-массив, а не склейка с потенциально встречающимся разделителем.
Task ID и компонент очищаются от крайних пробелов, CVE также приводится
к верхнему регистру. Регистр компонента и Task ID сохраняется. Номера строк,
порядок CSV и имя файла не используются как идентификатор.

Без любого из трёх идентификаторов строка не становится карточкой; показывать
количество и номера пропущенных записей. Точные дубликаты одной тройки после
нормализации объединяются с предупреждением. Если одна тройка имеет разные
данные, CSV отклоняется с номерами конфликтующих записей: нельзя угадывать,
какая версия должна получить решение ревьювера.

Карточки и счётчики показывают только задачи текущего активного пула.
Состояние ранее известных задач, исчезнувших из CSV или сменивших роль/статус,
сохраняется в JSON как не сопоставленное с активным пулом и не влияет на его
счётчики. Это позволяет не терять историю при смене снимка.

## Карточка и действия

Взять компактный вариант №1 с последними правками:

- Заголовок: компонент, CVE, критичность/CVSS, принятая мера, дата сдачи,
  Task ID. Поля и комментарии берутся только из реальной строки.
- Слева: разработчик, исходный статус, RHEL state, оба NVR, P/D,
  комментарий разработчика, замечание ревьювера при наличии.
- P `+` означает наличие патча в PATCH коммита сборки, D `+` — версию вне
  известных диапазонов. `-` не превращается в уверенный вывод об уязвимости.
- Внизу слева: кнопки тикета, GitLab, CVE и условная RHSA; исходные поля
  раскрываются одним действием. Длинные комментарии не обрезаются.
- Справа: проверки по принятой мере и действия. Примерная пропорция 3:1 на
  широком экране; перенос под контекст на узком. Компактность сохраняется.

### Чеклисты по принятой мере

Это обязательная функциональность первой версии. Точное исходное название
меры показывается в карточке. Выбор профиля — по справочнику из cvesummary
с нормализацией регистра и пробелов, без нечёткого угадывания и без изменения
самой CSV-ячейки. Ревьювер видит название чеклиста и число пунктов;
служебные ID и версии нужны для сопоставления JSON и не загромождают карточку.

Ниже — предлагаемый агентом начальный справочник проверок, подлежащий
согласованию с пользователем. Подписи короткие; пояснения задают смысл
проверки и отображаются как доступные подсказки.

| Принятая мера | ID профиля | Пункты в порядке отображения |
| --- | --- | --- |
| Патч из апстрима | upstream-patch | Источник патча; Патч закрывает CVE; Применён в сборке; Регрессии проверены |
| Импорт новой версии | version-import | Версия содержит фикс; Обновление собрано; Наши изменения сохранены; Совместимость проверена |
| Тег свежего билда | build-tag | Нужный NVR выбран; Фикс входит в билд; Целевой тег проверен; Результат проверен |
| Пакет пересобран (если в зависимостях) | dependency-rebuild | Зависимость исправлена; Пересборка подтверждена; Исправление в результате; Проверки пройдены |
| Обоснована неприменимость | not-applicable | Условия CVE разобраны; Наша конфигурация сверена; Неприменимость доказана; Обоснование в тикете |
| Патч из прошлой ветки | previous-branch-patch | Исходный фикс найден; Перенос корректен; Применён в сборке; Регрессии проверены |
| Самописный патч | custom-patch | Причина CVE устранена; Изменения кода проверены; Применён в сборке; Тест на CVE пройден |
| Было исправлено ранее | already-fixed | Прежний фикс найден; Покрывает эту CVE; Есть в нашем билде; Подтверждение в тикете |
| Закрыто SecOps | secops-closure | Основание закрытия; Применимость сверена; Доказательства проверены; Решение зафиксировано |
| Написана мера компенсации | mitigation | Мера перекрывает риск; Применима у нас; Ограничения описаны; Результат проверен |
| Другое | other | Действие описано; Мера обоснована; Доказательства проверены; Результат подтверждён |

Уточнения смысла:

- Источник апстрим-патча — ссылка/коммит, соответствующий заявленной CVE.
  «Применён в сборке» — патч включён в spec/процесс сборки и реально входит
  в NVR, а не только лежит в PATCH. Для прошлой ветки также проверяется
  адаптация к текущему исходному коду.
- Для новой версии проверяются наличие исправления, сборка, сохранность
  необходимых локальных изменений/настроек и совместимость. Одного D `+`
  для автоматической отметки недостаточно.
- Для тега проверяются NVR с исправлением и его наличие в целевом теге;
  сведения о теге ревьювер проверяет по материалам задачи. Тулза не имеет
  доступа к Koji/GitLab API и не заявляет о проверке тега по одному CSV.
- Для пересборки подтверждается исправленная зависимость в окружении
  сборки, факт пересборки и попадание исправления в результирующий пакет
  с учётом статической/динамической зависимости.
- Для неприменимости не требуются фиктивные патч/сборка. Нужны разбор
  условий CVE, сверка с нашей версией/конфигурацией и проверяемое обоснование
  отсутствия уязвимого пути или условий эксплуатации в задаче.
- Для компенсации проверяются конкретный механизм, применимость,
  ограничения и подтверждение действия меры, а не наличие исправления в коде.
- «Закрыто SecOps» не исключает строку автоматически: исключение из пула
  относится к значению `Разработчик = SecOps`, а не к принятой мере.

При пустой мере используется профиль `unspecified`, при неизвестном значении —
`unknown`, оба с четырьмя пунктами профиля other, но с собственными ID.
Рядом явно показывается «Мера не указана» или «Нет специального чеклиста».
Они не получают молча профиль апстрим-патча/обновления. В частности,
прототипные «Пропатчено», «Обновлено», «Не затронуто» не доказывают
соответствие конкретной мере из производственного справочника.

Справочник живёт в отдельном локальном модуле данных: у каждого профиля
стабильный ID, версия 1, исходная мера и список `{id, label, description}`.
У пунктов стабильные семантические ID, например `source`, `cve-coverage`,
`build-inclusion`, `regression` для upstream-patch. ID пункта имеет смысл
только внутри определённого ID и версии профиля. Число пунктов и прогресс
вычисляются из списка профиля; UI и JSON не завязаны на константу 4.

Каждый пункт: `unseen` (пусто), `ok` (✓), `bad` (✕). Управление доступно
мышью и клавиатурой, текущее состояние различимо не только по цвету.
P/D, RHEL state, AI-поля или принятая мера не выставляют отметки автоматически:
чеклист фиксирует ручную проверку ревьювера.

Три пула: `pending` — на ревью, `problem` — проблемы, `done` — ревьювед.
Новая задача начинается с pending и всех пунктов выбранного профиля в unseen.

«Ревьювед» доступна только после отметки всех пунктов своего профиля **ok или bad**.
Наличие bad само по себе не запрещает завершить ревью: так работает принятый
прототип. Есть явное красное указание количества bad и отдельная кнопка
«Есть проблема». Это правило проверяется и в обработчике действия.

«Есть проблема» открывает обязательный непустой комментарий; только после
сохранения переводит задачу в problem. Отмена/пустой комментарий ничего не
меняют. В problem можно изменить комментарий, закончить ревью после отметок
или вернуть задачу в pending. Проверки и замечание при возврате сохраняются.
В done проверки доступны для чтения; есть возврат на ревью.

Отмена последнего изменения пула/замечания восстанавливает и проверки,
и предыдущее решение. Загрузка CSV или JSON сбрасывает отмену, чтобы не
восстанавливать решение поверх новых исходных данных.

Поиск по CVE, компоненту, Task ID, разработчику и комментариям. Фильтры
разработчика и критичности, сортировка по критичности/CVSS или старшинству
даты сдачи. При пустой/неправильной дате задача идёт после датированных.

## Ссылки и настройки

- Тикет: если `Task ID` уже является абсолютным HTTP(S)-URL, использовать
  его. Иначе шаблон по умолчанию как в cvesummary:
  `https://portal.works.prod.sbt/swtr/units/current/unit/{task}`.
- GitLab: в vulnsheet нет координат репозитория; пользователь задаёт шаблон
  с `{component}`. Реальный внутренний namespace нельзя выводить из NVR.
  До настройки ссылка недоступна с подсказкой «Настройте ссылку GitLab».
  Не отправлять пользователя в демонстрационный `.example.internal`.
- CVE: URL из `CVE link`, при отсутствии — страница Red Hat по CVE ID.
- RHSA: отдельная кнопка рядом с остальными только при валидном HTTP(S)-URL
  в `Advisory (RHSA)`. Не придумывать advisory по CVE/компоненту.
- Пользователь может настроить шаблоны тикета и репозитория с `{task}`,
  `{component}`, `{cve}`; подстановки кодируются как части URL. Ссылка
  сохраняет понятную подпись; открытие — новая вкладка, noopener/noreferrer.
- Протоколы кроме HTTP(S), пустые/невалидные адреса не становятся ссылками.

Настройки ссылок и необязательная подпись релиза сохраняются с состоянием.
CSV-ячейки и импортированный JSON — данные: их содержимое не выполняется
как HTML/JS, включая комментарии и подписи. Сетевых API/токенов нет.

## JSON состояния и обновление CSV

Самостоятельный JSON: `app: "cvereview"`, `schemaVersion: 1`, `savedAt`,
`sourceName` (информационно), `settings`, `records` (массив). Запись содержит:

- identity: task, cve, component;
- basisVersion: 1 и basis — нормализованные существенные поля исходной
  строки на момент, к которому относится ревью;
- checklistId, checklistVersion и checks по ID пунктов этого профиля со
  строковыми enum; pool, reviewComment, updatedAt;
- checklistSnapshot: список ID и подписей пунктов на момент ревью, чтобы
  историю из старого профиля можно было прочитать без старого кода приложения;
- needsRecheck и previousReview при изменении исходных данных.

**Выбор агента:** для первой версии basis хранится как объект значений,
сравнивается детерминированно; это исключает коллизии короткого хеша и
позволяет показывать изменённые поля. Существенные поля: разработчик,
статус разработчика, Start/End date, мера, P/D, оба NVR, Fix date, RHEL state,
severity/CVSS, RHSA, комментарий разработчика и все ai_* поля.
Идентичность сравнивается отдельно. Task state, Task date, Исполнитель,
CVE link, порядок строк/колонок и дополнительные неизвестные колонки
не сбрасывают ревью. Пробелы вокруг обычных значений и эквивалентные даты
нормализуются; содержание комментария внутри текста сохраняется.

При повторном CSV или импорте JSON:

- Совпали identity, basis, ID и версия профиля: восстановить/сохранить
  pool, checks, замечание.
- Совпала identity, изменился basis, ID или версия профиля: pending,
  все пункты актуального профиля unseen, needsRecheck=true.
  Прежние проверки, пул, замечание, дата и basis остаются в previousReview;
  в карточке «Изменилось после ревью» с перечнем изменённых полей и раскрытием
  предыдущего решения. Новое замечание изначально пустое.
- Изменение принятой меры выбирает новый профиль; прежние галочки/крестики
  не переносятся по позиции или совпадению подписи. previousReview сохраняет
  прежний ID/версию профиля и подписи пунктов, чтобы историю можно было
  прочитать после изменения справочника. Обновление состава/смысла профиля
  требует увеличения его версии и повторной проверки затронутых задач.
- Если уже нужна повторная проверка и после сброса ревьювер ещё ничего
  не менял, следующий CSV не заменяет previousReview пустыми отметками.
- Новой identity соответствует новая pending-задача. Не сопоставленные
  записи JSON сохраняются отдельно и включаются в следующий экспорт.
- После явного завершения повторного ревью needsRecheck снимается,
  previousReview остаётся доступным для сравнения.

**Политика импорта, выбор агента:** выбранный JSON переопределяет текущие
решения для содержащихся в нём identity, с проверкой basis. Остальные решения
сессии остаются. Не применять автоматический выбор по более поздней дате:
явный выбор файла — источник пользовательского намерения. Настройки из
валидного JSON тоже применяются; об этом сообщает итог импорта.

Весь JSON валидируется до применения. Неверные app/schemaVersion, повторяющиеся
identity, неправильные checks/pool, done с unseen или problem без непустого
замечания — ошибка импорта без частичного применения и потери текущих данных.
Для известной версии профиля checks должен иметь ровно её набор ID:
пропущенный/посторонний пункт не считается пройденной проверкой. Корректную
запись со старой версией/другим профилем можно принять только как прежнее
ревью с needsRecheck; отсутствие актуального справочника не разрешает done.
Для такой записи проверяется непустой checklistSnapshot с уникальными ID,
точное соответствие ключей checks этому списку и допустимые enum. Снимок
не добавляет новый исполняемый профиль: используется только для истории.
Неподдерживаемая версия объясняется пользователю. Объекты хранилища строятся
по проверенным полям, а не копированием произвольных ключей из JSON.

Экспорт включает все известные записи, активные и архивные, без исходных
CSV-строк целиком; basis содержит только перечисленные поля. Текст JSON
остаётся пригодным для ручного просмотра. JSON и кеш прототипа не импортируются
автоматически: рабочая схема имеет собственные app/schemaVersion и ключ кеша.

## Кеш и целостность

Автосохранение в браузере содержит одну последнюю рабочую сессию: разобранные
CSV-данные, решения активных/архивных задач, настройки, информацию об источнике
и признак изменений после экспорта JSON. При открытии HTML валидный кеш
восстанавливает карточки без повторного выбора CSV; указан источник и время.

Кеш — удобство, JSON — переносимый файл. Страница никогда не сообщает о
записи JSON на диск после одного только кеширования. Открытие в другом
браузере/профиле или перенос HTML не переносит кеш. Для file:// не обещать
общий кеш между разными путями HTML; повреждённый/недоступный кеш не мешает
загрузить CSV/JSON вручную. Ошибка кеширования не откатывает сделанное ревью.

## Что остаётся исполнителю

Исполнитель выбирает разбиение JS-модулей и подход к отрисовке. Предпочтение —
обычный JavaScript без зависимостей, изолированная модель CSV/состояния для
содержательных тестов через Node, сборщик Python stdlib. Размер DOM нужно
удерживать разумным для нескольких тысяч строк: порционная отрисовка или
простая пагинация — выбор исполнителя, при сохранении фильтров и решений.

Локальные исходники и сборщик должны воспроизводить готовый HTML без сети.
Прототипы остаются внутри каталога тулзы как история выбора, без UI LAB и
переключения пяти вариантов в рабочем HTML. README становится основной
инструкцией использования и разработки; TODO актуализируется, появляется
локальный CHANGELOG, корневые индекс/история обновляются по правилам репо.
Другие тулзы и их поведение не меняются.

## Приёмка

1. Один HTML работает через file:// без внешних запросов; нет демострок.
2. CSV с 27 колонками vulnsheet и CSV после Excel читаются: UTF-8/BOM/cp1251,
   три разделителя, кавычки, многострочный комментарий, плавающий порядок
   колонок и строки до шапки. Ошибки не портят открытую сессию.
3. В активном пуле задачи со статусами «Ожидает ревью» и «Готов»,
   с указанным разработчиком, кроме SecOps; обе группы требуют ревью.
   отсутствие/конфликт идентичности не переносит решения на чужую строку.
4. Карточка соответствует принятому варианту, полный контекст доступен,
   RHSA условная, GitLab настраивается, пустые значения не выдумываются.
5. Проверены все три состояния чеклиста, блокировка done при unseen,
   завершение при всех отмеченных (включая bad), обязательный комментарий,
   переносы между пулами, отмена, независимость соседних карточек. Для всех
   мер из справочника подставляется свой профиль; неизвестная/пустая мера
   явно обозначена. P/D/AI не проставляют отметки. Смена меры или версии
   профиля сбрасывает актуальные проверки и сохраняет прежние для сравнения.
6. JSON round-trip восстанавливает решения и настройки; перестановка строк
   не влияет; изменённый basis требует повторного ревью с прежним контекстом;
   архивные записи сохраняются. Невалидный JSON не применяется частично.
7. Кеш переживает перезагрузку; при его недоступности остаются рабочие
   CSV/JSON-кнопки и понятное сообщение. Данные строк безопасно отображаются.
8. Фильтры/поиск не теряют отметки, управление чеклистом доступно клавиатурой,
   на 360–1440 px нет горизонтального переполнения всей страницы.
9. Содержательные модульные тесты парсера/переходов/сопоставления, браузерный
   прогон реального собранного HTML с загрузкой CSV/JSON, проверка автономности
   и воспроизводимости сборки. Тесты чужих тулз без причины не расширять.
