# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение репозитория

Коллекция рабочих тулз и скриптов. Каждая тулза — самостоятельный каталог
`tools/<имя>/`, не связанный с остальными. Общего кода, общей сборки и общего
пакетного менеджера в репозитории нет и заводить их не нужно.

## Структура тулзы

```text
tools/<имя-тулзы>/
├── README.md     # назначение, зависимости, точка входа, версия
├── TODO.md       # задачи по этой тулзе (см. «Список задач»)
└── ...           # остальное — на усмотрение самой тулзы
```

Обязательны только `README.md` и `TODO.md`. Всё остальное внутри каталога —
внутреннее дело тулзы: она может быть одиночным скриптом, а может быть
многокомпонентной, с собственным деревом каталогов, своим пакетным
менеджером, своими тестами и на любом языке.

**Единого шаблона внутренней раскладки нет и он не вводится.** Не приводите
устройство одной тулзы к устройству другой, не выносите «общее» в корень и не
заводите каталоги вроде `lib/` или `common/` на уровне репозитория. Тулза
должна переноситься или копироваться целиком, одним каталогом, и продолжать
работать.

Ссылки внутри `README.md` и `TODO.md` тулзы — относительные. Наружу ведёт
только ссылка на документы самого репозитория (`../../CLAUDE.md`,
`../../README.md`); она же — единственное, что придётся поправить, если тулзу
когда-нибудь вынесут обратно в отдельный репозиторий. Всё прочее остаётся
внутри каталога, иначе тулза перестанет переноситься целиком.

### README тулзы

`README.md` тулзы — единственная точка входа для человека. Он отвечает на
четыре вопроса:

- что тулза делает и когда её применяют;
- что ей нужно для работы (зависимости, доступы, переменные окружения);
- как её запустить: точка входа и типичные примеры вызова;
- какая у неё сейчас версия.

## Версионирование: два независимых уровня

- **Версия репозитория** — в `CHANGELOG.md` и git-тегах (`v0.1.0`).
- **Версия тулзы** — своя у каждой тулзы, по семантическому версионированию.

Они не синхронизированы. При изменении тулзы поднимается её собственная
версия, и отдельно добавляется запись в корневой `CHANGELOG.md`.

Где физически лежит номер версии тулзы, решает сама тулза: шапка скрипта,
`VERSION`, `package.json`, `pyproject.toml`. Названа она в `README.md` тулзы —
это то место, куда смотрит человек. Если у тулзы есть CLI, версия выводится по
`--version`.

Корневой `README.md` версии тулз намеренно **не** перечисляет: продублированный
номер расходится с настоящим, и таблицу пришлось бы чинить при каждом
изменении.

## Рабочий процесс

### Git Flow

Ветвление по модели Git Flow:

- `main` — только релизы, каждый коммит помечен тегом версии вида `v1.2.0`
- `develop` — интеграционная ветка, куда вливается вся текущая работа
- `feature/<название>` — ответвляется от `develop`, вливается обратно в `develop`
- `release/<версия>` — ответвляется от `develop`, вливается в `main` и `develop`
- `hotfix/<версия>` — ответвляется от `main`, вливается в `main` и `develop`

Напрямую в `main` и `develop` не коммитим.

### Коммиты

Сообщения коммитов пишутся **на английском** в формате [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.

- `description` — в императиве, с маленькой буквы, без точки в конце
- `scope` — имя каталога тулзы, например `feat(cve-triage): add --json output`;
  для правок уровня репозитория скоуп опускается
- Ломающее изменение помечается `!` после типа/скоупа (`feat(api)!: ...`) и/или футером `BREAKING CHANGE: <описание>`

Связь с версионированием: `fix` → `PATCH`, `feat` → `MINOR`, `BREAKING CHANGE` → `MAJOR`.

### Changelog

`CHANGELOG.md` ведётся **на русском** по формату [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).

- Сверху секция `## [Unreleased]`, ниже выпущенные версии в обратном хронологическом порядке
- Заголовок версии: `## [1.2.0] - 2026-09-02` (дата в ISO 8601)
- Категории внутри версии, только непустые: `Добавлено`, `Изменено`, `Устарело`, `Удалено`, `Исправлено`, `Безопасность`
- Запись про тулзу начинается с её имени и новой версии: «`cve-triage` (1.3.0): …»
- Записи пишутся для людей, а не копируются из `git log`
- Внизу файла — ссылки на диффы между тегами

### Версионирование

Семантическое версионирование `MAJOR.MINOR.PATCH`:

- `MAJOR` — несовместимые изменения
- `MINOR` — новая функциональность с обратной совместимостью
- `PATCH` — исправления с обратной совместимостью

## Список задач

Списки задач (баги, фичи, технический долг, идеи) ведутся на двух уровнях:

- корневой `TODO.md` — задачи уровня репозитория: соглашения, документация,
  инфраструктура, новые тулзы;
- `tools/<имя>/TODO.md` — задачи по конкретной тулзе; переезжает вместе
  с каталогом тулзы и перечислен в индексе корневого `TODO.md`.

Задача про тулзу пишется в список тулзы, а не в корневой. Пополнять оба может
и пользователь, и Claude.

### Формат пункта

Один пункт — одна задача, чекбоксом `- [ ]`; формулируйте так, чтобы через
месяц было понятно без контекста беседы. Сделанный пункт удаляется из
файла, след остаётся в `CHANGELOG.md` и в git.

```markdown
- [ ] **BUG-M-2610-01**
      Область: `ranges.py`, `_fetch`.
      Что не так, где, как воспроизвести, что предложено.
      Источник: прогон по 859 CVE (2026-10-15).
      Приоритет средний (2026-10-15): почему именно такой.
```

- Код `ТИП-П-ГГММ-NN` — сразу после чекбокса:
  - `ТИП` — раздел: `BUG` (баги), `FEAT` (фичи), `DEBT` (технический
    долг), `IDEA` (идеи);
  - `П` — текущий приоритет: `H` высокий, `M` средний, `L` низкий; у
    пункта с частями разного приоритета — наивысший;
  - `ГГММ` — год и месяц заведения пункта: `2610` — октябрь 2026;
  - `NN` — порядковый номер внутри типа и месяца, двузначный; в новом
    месяце нумерация типа начинается с `01`.

  `ГГММ` и `NN` постоянны: не меняются при переоценке и перестановке и не
  переиспользуются после удаления пункта. При переоценке меняется только
  буква приоритета, поэтому ссылаться на пункт надёжнее без неё:
  `BUG-2610-01`. У корневого списка коды с префиксом `REPO-`
  (`REPO-BUG-H-2610-01`), чтобы не путать их с пунктами тулз.
- Под кодом — строка «Область: …»: затронутые модули, файлы, функции.
  Область, в отличие от кода, меняется вместе с содержанием пункта.
- Пункты, заведённые до этого формата, несут строку «Бывш. …» — прежний
  код, под которым они упоминаются в git и `CHANGELOG.md`.
- Строка «Источник: …» — откуда пункт: ревью, прогон, замечание
  пользователя, с датой.
- Строка «Приоритет … (дата оценки): почему». Внутри раздела пункты идут
  по убыванию приоритета; переоценка — отдельная правка с новой датой.
- У каждого списка свой счётчик — строка «Последние выданные номера» в его
  шапке, обновляется при добавлении пункта.

Claude **не берёт пункты из этих файлов в работу по своей инициативе**. Ни
попутно с соседней правкой, ни потому что пункт выглядит однострочным. Работа
над пунктом начинается только тогда, когда пользователь явно указал на него.
Без такого указания файлы разрешено читать и дополнять, но не исполнять.

## Проверки

Общего тестового фреймворка, сборки и линтера в репозитории нет: у каждой
тулзы свои, если они ей вообще нужны, и описаны они в её `README.md`. Корневые
проверки касаются только того, что общее для всех тулз, и запускаются из корня
репозитория перед коммитом:

```sh
# синтаксис bash-скриптов там, где они есть
find tools -name '*.sh' -exec bash -n {} \;

# файл с шебангом, но без исполняемого бита: его собирались запускать
# напрямую, а запустить нельзя. Модули, которые только импортируют или
# подключают через source, шебанга не несут и сюда не попадают
git ls-files -s tools | grep -v '^100755' | cut -f2 | while read -r f; do
  if [ "$(head -c2 "$f" 2>/dev/null)" = '#!' ]; then echo "NOT EXECUTABLE: $f"; fi
done

# обязательные файлы на месте
for d in tools/*/; do
  for f in README.md TODO.md; do
    [ -e "$d$f" ] || echo "MISSING: $d$f"
  done
done

# относительные ссылки в документации тулзы резолвятся
for d in tools/*/; do
  grep -oh '](\.\?/\?[^):]*)' "$d"README.md "$d"TODO.md 2>/dev/null |
    sed 's/](//;s/)$//' | grep -v '^#' | sort -u | while read -r f; do
      [ -e "$d$f" ] || echo "BROKEN: $d$f"
    done
done
```

Собственные тесты и линтеры тулзы корневой процесс не подменяет и не
перечисляет — их знает сама тулза.
